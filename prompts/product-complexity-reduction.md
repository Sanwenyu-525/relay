## 目标与事实基线

用户要解决的是：普通 Agent 操作不应该要求用户理解、逐项配置底层能力、连接、受管资源和策略。减少实际步骤与重复配置，同时保留真实权限、撤销和恢复能力。

工作区：`D:/Develop/Relay-Agent`。所有回复中文。先读 `AGENTS.md`、`CODEX_NEXT_STEP.md`、`docs/README.md` 和统一验收表相关行，检查 `git status` 与目标文件 diff。当前共享工作树有大量未提交改动，不回退、不覆盖、不顺手格式化；不 commit/push，不操作用户正在使用的桌面实例，不外发项目材料。默认当前 Agent 完成。

本任务书依据工作树源码，包括未提交内容，不把历史记录当作已交付事实：

- `apps/api/src/application/local-directory-access.ts` 已在显式打开目录时编排本地只读配置，并提供四档写入权限；不是仍需从头实现“本地目录免配置”。
- `apps/api/src/application/open-working-directory.ts` 已能为无归属目录建立最小项目；不能直接声称每次选目录都必须手动创建项目。
- 自动推进已在 2026-10-20 收归服务端 Worker，旧 `planExecutionPreference.ts` 已删除；接续以 `CODEX_NEXT_STEP.md` 与运行架构 §2.10.1 为准，不恢复前端推进 Owner。
- 文件 CRUD 的真实模型、活动桌面产物与 Windows 验收边界按统一验收表读取；源码存在不能证明用户当前窗口已经加载。

## 已发现的减负点，按优先级处理

### P0：普通工具仍暴露通用权限配置器

证据：`apps/workbench/src/views/ConnectionsView.tsx` 的 `capabilities`、`policyActions` 与连接/受管资源/权限策略三段表单。用户要分别选择能力、连接根、受管资源、动作和 AUTO/ASK/DENY；FILE_QUERY 的列出、查找和搜索还提示分别配置。测试能力 `FAKE_WRITE`、`FAKE_PUBLIC_READ` 也进入正常能力选项。

目标：日常入口按用户要用的工具或目录操作，内部由 Application 编排已有 Gateway 配置。通用逐动作配置收进高级管理，测试能力只留测试或显式开发入口。文件工作流延续已有选目录与权限档位实现，不再创建一套管理机制。

验收：新目录、零预置 FILE 配置，经真实 HTTP 打开目录后可以列出/查找/搜索/读取；切换写入档位后按原规则写入。用户不需要操作上述三种表单。高级入口仍能检查实际配置及撤销状态。只隐藏表单不算完成。

### P0：内置插件与项目连接登记绑定过紧

证据：`AssistView.tsx` 的 `connectorsNeedProject`、`builtinPlugins`、`pluginState`。电脑、浏览器、GitHub 三行都通过 `window.location.assign('/settings/connections')` 跳到通用配置页；无项目时读不到登记，已有项目也要按项目登记。`ConnectionsView.tsx` 以项目为入口管理这些能力。

目标：分开“本机插件安装/配对/登录是否可用”与“本次动作是否获准”。电脑或浏览器运行时不应因为换项目重新安装、配对；GitHub 登录不应因为换项目重新做。点击插件进入该插件自己的状态与接入面板，缺少什么只补什么，然后回到原会话。项目和动作范围继续由既有 Gateway 约束。

先追踪各插件的 API、Adapter、配对/登录与授权真实消费者，列出可复用事实与需要修改的 Owner。优先保留当前项目级准入，在其上简化入口与必要配置；不要为了全局显示状态立即迁移全部授权模型。只有证据表明项目级存储造成不可消除的重复配置，才提出有界迁移方案；架构变更需先说明兼容和撤销影响，不擅自给予全局权限。

验收：运行时可用、缺配对、未登录、未授权、已撤销分别呈现。切换项目不重复安装/配对/登录，也不继承其他项目的动作授权。无项目会话可以查看插件真实状态；需要目标范围时在当前流程补齐，不把用户送去通用表单猜配置。

### P1：同目录的 Git 只读还要单独登记连接

证据：`apps/api/src/application/conversation-execution.ts` 的 `planToolLoop` 只有找到 `GIT_READ` 连接才加入 `git_status/git_diff/git_log`；`local-directory-access.ts` 的 `READ_ACTIONS` 只覆盖文件读取与检索。

目标：显式打开目录时，可识别其 Git 仓库状态；Git 只读能力通过同一目录授权动作自然取得，不要求用户手工新建 GIT_READ 连接和逐项策略。若当前打开目录与 Git 仓库根不同，必须先限定返回范围；无法保证时，仅提示并在原地请求对仓库根的只读授权，不自动扩大文件范围。

验收：新仓库零手工 GIT 配置可以查 status/diff/log；普通目录正常提示非仓库；子目录、仓库外根、明确 DENY/撤销分别验证。不能顺带开放 stage/commit/push 或任意 Shell。

### P1：用户被要求理解恢复协议

证据：`apps/workbench/src/components/WritePermissionControl.tsx` 在失败恢复中显示原 `command_id`、查询原回执、按原命令重试；`ViewConfigurationPanel.tsx` 也暴露原 ID、修订和 kind 等术语。

目标：协议由程序执行。用户看“正在核对是否保存成功”“重新核对”“重试保存”；底层标识只放可展开诊断。优先使用已有查询与重试逻辑完成有界自动核对，不能仅换文案、也不能新建全站通用恢复框架。对于结果未知且可能已经提交的操作，先核对，原 ID 与原载荷保持冻结。

验收：模拟响应丢失但后端已提交、确实未提交、并发 revision 变化、切目录和组件重挂载；不重复提交、不把旧结果投影到新范围。仅自动核对当前可证明安全的操作，不自动重做外部副作用。

### P1：模型配置分散，图片能力需要单独补声明

证据：`SettingsView.tsx` 的 `ModelPortCard` 明确配置来自环境变量、页面不可修改密钥；`ImageInputDeclaration` 为独立能力声明入口。`apps/api/src/application/chat-image-input.ts` 按目录、声明、环境变量、拒绝四层判定。不是所有配置项都属于无用设计，问题是用户完成一次接入却需要跨多个来源补齐。

验收：目录内模型、自定义端点模型、已声明支持/不支持、未知能力都有一致的预检与发送结果；页面可说明配置来源和生效范围；密钥不出现在响应、日志或 Context 中。真实 Provider 与 Windows 验收独立报告。

### P2：未实现入口和测试概念占据日常界面

### 本轮不据此判定为过度设计

- 当前聊天同时有“普通 Agent”与“普通讨论”，确有术语学习成本，但它们分别控制会话模式和本次消息意图；当前会话模式还关系冻结身份。不能因两处名字相近直接删一项或在原会话偷换权限。本轮只记录候选，后续如需合并入口须单独比较模式、Skill 与历史接续的语义。
- 审批的确切版本绑定、Task/Run 分离、必要验收标准、定时授权期限和结果未知核对均继续保留；减负的是手工搬运、无必要的填写和默认界面层级。
- 旧聊天历史里的“无法写文件”只证明当时的回复，不能当作当前文件链路仍失败的复现。当前窗口缺目录/权限的提示也不能证明底层授权应被删除。

### R3-01 / P1：插件管理跳转丢失当前范围

实机路径：已绑定 Relay-Agent 的会话 →「+」→「连接器与插件」→「电脑操控」→ 运行环境就绪、本项目未授权 →「管理连接与权限」→ `/settings/connections` 全局项目选择页。明明已有项目，还要重新选择；进入项目后，工具状态又提示回会话插件面板。源码 `AssistView.tsx` 两处 `window.location.assign("/settings/connections")` 可直接定位。

修改：已知项目时直达该项目、该插件对应配置区域，保留原会话和返回位置；无项目时保留真实范围选择。普通站内导航复用既有路由，不为这次操作整页重载。连接页插件状态给出实际可执行的下一步，避免只有一句“去另一页”；优先复用既有面板、参数和 Gateway，不新建授权模型。跳转、查看状态不产生授权；涉及新授权交互的部分先核对现有契约，只接现有明确授权动作。

验证：当前项目 A → 电脑/浏览器/GitHub 各自定位 → 返回原会话；切项目 B 不带入 A 的授权；未归属会话不猜项目。往返后保留草稿、会话 ID、目录、阅读位置；当前实机尚未验证草稿丢失，不可将它写成已复现根因。覆盖刷新、前进后退、撤销、未配置、检测失败与状态未知。

### R3-02 / P1：同一目录的页面状态互相矛盾

实机初始 `/agent?new=…&dir=…`：输入区目录为 Relay-Agent、已归入项目，权限显示完全访问；顶栏仍显示“尚未绑定目录”。这是**展示语义不一致**，尚未证明后端绑定错误。已有会话稳定后顶栏目录正常。

修改：追踪 `CollaborationView.tsx`、`FolderScopeBar.tsx`、顶栏数据来源及新会话创建时机，区分“本次新对话已选择的目录”和“持久化会话已绑定目录”。可复用同一目录投影，或在尚未落会话时明确标为“已选目录，发送后绑定”；不要为了消除文案矛盾提前创建会话或放宽权限。

验证：带目录新对话、无目录新对话、已有会话、更换目录、归属多选、目录打开失败、只读及拒绝策略。顶栏、输入区和权限提示不互相否定；陈旧异步响应不覆盖新范围。

### R3-03 / P1：人工待处理缺少可读对象，路径重复

实机路径：铃铛 →“需人工介入 1 项”→ `/tasks?tab=attention` →“打开原处理入口”→ `/reviews?id=…`。中间页面把同一 Review 放在“必须介入”和“待判断 Review”两组，首屏直接出现 `CRITERION: AWAITING_HUMAN_EVIDENCE`，随后展示 Project/Task/Run UUID；用户需要辨认内部身份才能判断事项。

修改：`InterventionNotifications.tsx` 的浮层呈现可识别的事项和直达原请求入口，保留全部待处理入口。`AttentionQueue.tsx` 普通卡片先显示真实项目/任务或产物名称、需要用户做什么、原因及一个明确主入口；编码和 UUID 放可展开技术详情，未知标题不编造。可以保留分组，但同一项跨组时必须说明关系，避免看起来重复计数。继续保留读取不完整和事实过期提示。

验证：单项/多项、同一 Review 被多来源引用、已处理或目标不存在、项目名读取失败、分页不完整、权限不足。计数保持原事实范围，不批量批准、不从聚合页直接绕过版本核对。直达正确请求后仍重新读取确切版本。

### R3-04 / P2：审批正文与决策相距过远

本机约 1162×782 窗口下，审批页按请求列表→产物正文→判断详情单列排列；完整正文之后才出现“作出决定”。首屏没有决定区定位入口，判断依据还直接展开英文键名和 JSON。单列本身符合既有窄窗设计，不改回挤压多列。

修改：`ReviewsView.tsx` 及其样式提供“查看判断条件 / 前往决定”页内定位，保留先阅读对象与条件的能力；普通判断依据用用户语言，原 JSON 保留在技术详情。可采用简短导航，不必强加悬浮批准按钮。不能在缺对象、版本未确认、读取失败或决定已过期时开放提交。

验证：长/短正文、有/无产物、多个请求、目标 ID 非法、窄窗与宽窗、Tab/Enter/Escape。页内定位可见且焦点正确；切换阅读版本不改变判断绑定；实际提交只在受控测试数据中进行。

### R3-05 / 待核实：权限不能点击

实机完全访问菜单经鼠标可正常展开，四档显示为可操作；没有切换档位，不能宣称保存链通过。首次 UIA 索引点击无变化、鼠标坐标点击成功，**这是自动化方式差异，不能直接报成人类点击失效**。当前源码还已有禁用原因与“重新核对”补丁，接续时先复验，不能重复实现。

检查 `WritePermissionControl.tsx` 的 `canChoose`、readiness、scopeMissing、pending 与错误分支。在受控环境复现无目录、无项目、只读、正常可选、正在保存、读取失败、未知回执和撤销等状态。真正不可操作时必须有可见原因及与原因匹配的下一步；不能通过删 disabled、伪造 READY 或忽略撤销来“修好”。未复现就交付检查结果，不制造修复。
