## 4. 阶段 B：应用管理基础配置与真实准入

实际源码导航（开工时重新定位，不能机械覆盖）：

| 入口 | 责任 |
|---|---|
| `apps/api/src/application/open-working-directory.ts` | 主动目录选择、根/项目关联、readiness；当前只关联并投影，不具备完整自动设置 |
| `apps/api/src/application/gateway-commands.ts`、`gateway-configuration.ts`、`gateway-repository.ts` | 复用连接/策略与资源 Owner，已有版本、权限、回执；不直接 SQL 伪造已授权事实 |
| `apps/api/src/application/assistant-readonly-round.ts` | 基础会话读工具接线与连接选择；无 Task/Run 读取保持原来源身份 |
| `apps/api/src/application/conversation-execution.ts` | 原候选→Task/Run、写意图、工具信封和连接选择；既有自动 Apply 与阶段命令身份保留 |
| `apps/api/src/application/gateway-actions.ts`、`run-scope-grant.ts` | 原策略排序、scope grant、确切动作 Review，prepare/dispatch 均重查 |
| `apps/api/src/files/`、`worker/tool-loop-action.ts`、`application/tool-loop.ts` | Windows 句柄边界、changeset/基线/回执、停止/恢复，不另造写文件旁路 |
| `apps/api/src/api/gateway-api.ts` 及实际目录接口、Workbench client/DTO | 新设置命令及只读实际状态，GET 不产生权限写入 |

实施要求：

1. 新目录主动选择成功后，配置该 canonical root 的最小 FILE_QUERY/FILE_READ 及既有读动作准入。复用匹配的 ACTIVE 配置，可合并同根能力；不能因有三个能力就固定建三条连接。
2. 写档位应用前校验真实根、归属、版本及旧限制；在原 Owner 下落实 FILE_WRITE/ASK 或 AUTO，返回实际状态。不能为绕过 DENY、停用/撤销而造新 ID；不能在有上层限制时用更长前缀自作覆盖。
3. readonly 是有效禁止后续文件写的状态。旧「不开放写入」兼容这个目标；不要只撤销当前条目而意外露出旧 AUTO。区分应用自己管理的拒绝与用户/上层显式限制，不能为切档解除后者。
4. 就绪投影、会话读取、Run 准备都按实际受管根/连接边界匹配；多个连接时顺序不影响结果，错误根缺能力时如实拒绝。只提取有当前调用方的最小公共判断，不做通用解析框架。
5. 查询与恢复只消费现有事实。默认配置只在可追溯的主动用户命令发生；已停用/撤销或历史授权不完整时，原入口明确说明并给出有界重新设置动作，不能重开会话自动恢复权限。
6. 检查配置变更后的在途动作：后续未准入写应受新只读/撤销约束；已派发/UNKNOWN 按原控制、核对与资源隔离处理，界面不能假称已停止。既有确切 Review 的适用性按原政策版本与批准规则复核。

阶段出口：LA-01/02/06–10 的相关真实 PG 断言与原 Gateway 不变量通过；说明实际 API Breaking Change Yes/No、兼容与必要数据库影响，再进入 UI 链路，不把“能生成配置”当作整个出口。
