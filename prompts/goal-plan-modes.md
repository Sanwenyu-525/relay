## 3. 不可改写的产品行为

### `/plan`

- 调查、读取、必要的只读验证、聚焦澄清和方案比较；默认不修改项目。只读必须落实到工具准入，不能只靠提示词。禁止的操作不能通过浏览器、电脑或命令工具间接写入。
- 形成结构化、有版本、可继续修改的计划：目标、范围、步骤、验证方式、待定事项。正常讨论保持聊天，形成计划后呈现计划卡。
- 默认保存在会话；支持需要时导出计划文件，导出是用户明确请求后的独立写操作，不能成为规划时自动写项目的理由。
- 写入试验或原型先解释范围、取得明确授权；普通消息不能让模型自行越过只读限制。不得为只展示计划强建正式 Task/Run。
- 计划卡可查看、通过自然语言修改；「按此计划执行」沿选定版本进入 `/goal`，保留上下文，不重复询问已有需求。

### `/goal`

- 整理成功条件，能确定的先推进；关键目标、权限和不可逆行动有歧义时先澄清。简单目标自动整理条件，复杂目标与用户确认。
- 持续实施、验证、发现缺口后修正。**不设置应用额外的总时间、总轮次、总调用次数上限。** 不能在 UI 隐藏上限而后端仍以固定总轮次结束目标；也不能未经审计删除现有所有预算约束。
- 保留单次模型请求、单次工具调用的必要技术边界。局部轮次耗尽不自动等于目标额度耗尽或目标完成；沿持久状态组织后续推进，不能用一个永不返回的请求、前端 timer 或递归调用伪造持续执行。
- 直到目标完成或可用额度耗尽；用户暂停、取消、真实阻塞、必要人工决定及连续无进展可使其等待，不无限重试。
- 关闭页面后服务端继续；重启后核对现场再恢复。额度耗尽保存进度，恢复额度后由用户点击「继续」，不自动执行。
- 已授权操作自行推进，不逐步确认；改变目标、扩大范围、增加权限时先问。调整方法和步骤可自行进行，展示原因与剩余工作。
- 完成依据实际成功条件和证据；模型声称完成、步骤全部打勾、代码写完不能直接提交业务完成。需要人工验收时沿原流程等待，验证器错误或未运行不算通过。

### 命令、消息与 UI

- `/plan 内容`、`/goal 内容` 发送后生效；命令菜单仅预填。输入框旁可选择并显示模式；新会话默认普通模式，旧会话恢复其持久状态。
- 模式选择中的未发送草稿与服务端生效状态明确区分；选择器不得绕过活动目标安全暂停或默默启动执行。
- 补充要求融入后续执行；进度询问只回答状态；冲突要求先暂停受影响行动并澄清；暂停、取消、先讨论按控制意图处理。
- 运行中的目标转 `/plan` 先持久保存控制意图、安全处理在途行动，再显示已切换。不能只有 Loading 或本地状态。
- 会话内固定一张目标卡，显示目标、真实状态、当前步骤、简短进展，详情折叠；运行时有暂停/取消，暂停或额度耗尽后有继续。卡片随会话恢复。
- 完成显示结果与验证依据；等待人工验收、暂停处理中、已暂停、阻塞、额度耗尽、取消和失败有可理解的区别。继续请求处理中防重复提交，失败保留现场和具体原因。
- 取消不表示撤销已发生修改或外部操作。暂停和恢复不重新收集原目标，也不创建第二条重复执行链。

## 4. 先核定薄设计，再落地代码

先给出简短现状/缺口表：已实现、已有但未接线、必须新增、外部阻塞；每项附具体文件/符号。不要把存在组件或接口当成闭环。核对后说明最小方案、成功条件与检查，再直接继续实施；只有真实业务歧义或不可安全合并的冲突才请求用户决定。

优先定位已有会话、命令、conversation-execution、Worker、控制、Gateway、工具账本、用量记录及 Workbench 入口。候选路径包括 `apps/api/src/application/`、`apps/api/src/assist/`、`apps/api/src/worker/`、`apps/api/src/workflow/`、`apps/workbench/src/views/AssistView.tsx`、`components/ChatCommandInput.tsx`、`components/ExecutionSummary.tsx`、`api/`；它们是定位线索，按实际代码决定，不预设全部必须改。

具体核定：

1. 会话模式、当前活动目标、成功条件/范围修订、计划版本、执行引用、进度和停止原因由谁写入、如何持久恢复。聊天目标模式与已有 Workspace Goal 不同；不得创建第二套 Task/Run 状态机。
2. 模式/计划/目标更新的版本冲突、幂等回执、同会话活动执行排他，以及旧会话/旧 Run 的兼容。计划更新不静默改已冻结执行契约。
3. 原 Worker 或现有服务端调度怎样承担推进；一次有界 tick/工作单元怎样提交进展并接续。沿现有执行框架，不引入新通用编排器或并行 loop。
4. 现有总预算与单次技术限额逐项分类；如何满足目标无额外总上限，同时保留原权限、外部效果核对、异常保护。不能直接套 N06 固定任务数/期限。
5. 可用额度来自哪个真实 Provider/账户或已接入额度事实；哪些响应可靠表示额度耗尽，哪些只是暂时限流、网络错误或未知。没有余额 API 时不能编造余额/重置时间；不把任意 429、错误字符串或模型解释当作账户额度证据。不借自动换账户/服务商绕过耗尽后的人工继续语义。

身份、版本、最小 API 和 migration 在上述核对后确定，不照抄本任务书预造端点/表。重要架构取舍写 ADR，普通接线不为格式制造 ADR。

## 5. 恢复与业务不变量

- 每份事实只有一个逻辑写入 Owner；UI 只呈现和提交命令，关闭前端不得停止目标推进。当前状态从服务端重读，不信任 localStorage 的运行状态。
- 必要业务状态、幂等回执和关键审计在短事务提交；模型、网络、工具执行及人工等待不能放长事务。
- 同命令同载荷重放原回执，异载荷拒绝；CAS/锁顺序沿已有契约。并发点击继续、重复 Worker 扫描、事件丢失不能重复启动。
- 重启先检查原 Run/工具调用/资源执行权。租约过期不等于旧进程已停止；UNKNOWN 先核对，不能重放副作用、换动作 ID 或换 Adapter 规避。
- 暂停/取消/转模式与完成竞争要有确定处理；迟到模型/工具结果不能覆盖新控制状态或新修订。
- 工具计划与成功条件分开，工具调用成功不等于任务完成。目标达成协调原 Verification/Review/完成用例，不直接写 DONE/PASS。
- 目标没有额外总上限，不等于无限上下文；复用现有上下文/压缩机制，保留恢复所需事实与证据，不另造记忆系统。

## 6. 实施顺序与验收证据

按完整垂直链分步完成，内部可分片，但本任务交付包含 UI，不把客户端接线称作前端完成：

1. 复现缺口并新增核心失败检查 → 验证不存在模式准入、持久目标、后台推进或恢复链的具体缺口，不写无意义的固定失败占位。
2. 最小持久模型、用例、权限与有界推进接线 → 领域/工具检查和真实 PG/HTTP 验证通过。
3. 命令、client、计划卡、目标卡和控制接入 → 浏览器实际操作完成规划、修改、执行、暂停、继续、取消和重开恢复。
4. 故障与回归 → 覆盖额度耗尽、断页、服务重启、重复继续、在途暂停/取消、迟到结果和 UNKNOWN；修复后复验。
5. 文档与实际桌面验证 → 完成受影响检查；如涉及桌面暂存包，按现有脚本刷新并核对实际加载身份，避免旧窗口冒充新实现。

必要验证绑定[测试计划 §41](../docs/testing/verification-plan.md#41-聊天目标与计划模式验收规格)，至少给出以下证据：

- `/plan` 尝试写文件及其他副作用被实际准入拒绝；仅模型口头拒绝不算。
- 一份计划两次修改、选定版本执行、冲突拒绝与原上下文接续；不得靠标题匹配版本。
- 目标跨多个局部模型/工具轮持续推进，不以局部限额偷偷结束；成功条件失败时继续修正，缺证据不完成。
- 只运行服务端 Worker、无页面请求时仍推进；重启后原身份恢复，重复请求/扫描不产生重复效果。
- 可控额度故障下落为额度耗尽、持久进度；恢复额度不自动执行，按钮继续一次，仍耗尽时保留现场。故障注入只证明恢复协议，真实 Provider 识别另报。
- 暂停/取消/模式切换与在途结果/完成竞争，资源排他及 UNKNOWN 核对；常规聊天、原执行、学习/人设等受影响入口不回归。
- 卡片真实状态、按钮 Loading/错误、窄窗可用、会话重开不丢；Windows/WebView2 实窗单独验证。

运行变更涉及项目的类型检查及必要测试，不扩大成无关压力测试或全仓重构。修 Bug 给出失败→修复→通过的证据。自动化、真实 PG/HTTP、浏览器、Provider、Windows、安装态和独立验收分别汇报；未运行写明原因。缺真实 Provider 凭据时继续完成其余链及可控故障验证，不用 Fake 冒充真实 Provider。
