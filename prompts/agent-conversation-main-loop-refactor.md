## 1. 任务与授权范围

你负责在 `D:/Develop/Relay-Agent` 实施普通 AGENT 对话主流程重构。由当前 Agent 单独开发、验证和维护文档，不派子代理、不创建其他聊天；遵守 AGENTS.md，保护共享工作区已有未提交改动，不 commit/push，不升级、重置或清空用户数据库，不覆盖桌面配置和凭据。

交付目标：**原用户消息＋应用核对的当前上下文 → Agent 请求必要工具 → 原应用用例校验和执行 → 实际结果返回同一逻辑轮次 → 原会话回复**。移除新普通消息固定经过无工具聊天、执行解释、状态维护解释三个独立模型分支的机制。

这是一项完整开发任务，不是仅给方案或调整回复措辞。分阶段连续推进，阶段之间自行检查，不为例行读取、测试或已授权的可逆修改反复询问用户。确实影响既定权限、业务承诺或无法兼容的决定才提出聚焦问题，先完成不依赖该决定的部分。

## 4. 不可改变的产品与架构边界

1. 纯讨论、列目录、读文件和解释文件不制造占位 Task/Run。复用会话消息领取、租约、CAS、只读工具账本和 Gateway；适配合法的普通 AGENT 来源，不能伪造人设快照或绕过原来源校验。
2. 修改文件、运行检查沿原 Task/READY/Delegate/Run；主流程可提交类型化任务候选，但不能为了进入 Run 再固定调用一个独立的意图解释模型。原始用户请求是授权依据，仍校验范围、必要验收要求和当前准入。
3. 项目状态维护由主流程请求有限的类型化应用工具，复用原 Owner、确定性校验、变更组、决定、版本和撤回。不能把旧 `interpretStateMaintenance()` 原封不动隐藏在每次工具调用后，继续做重复模型分类；可以拆出、复用其中无模型的确定性准备和应用能力。
4. 没有原 Owner 的未来能力仍不可写。不新增任意 SQL、任意 Shell、通用写对象工具、通用意图 DSL、多 Agent Router、第二执行引擎或 Harness 依赖。
5. `selectRuntimePrompt()` 继续做纯模板选择。ASSISTANT/LEARNING、冻结 Skill/方法、专用提案、语义验收与连接验证维持各自身份、输出协议和权限，不能全部合成一个通用 schema。
6. 用户明确只读请求且目录唯一、权限允许时直接读取；不要求重复目录、不要求说明之后要维护什么业务状态、不固定再次开始。写入/检查也遵循原明确请求直接执行规则，必要审批与冲突决定保留。
7. 原会话可以看到真实进度、结果和失败，Task/Run 是详情来源，不强制跳任务才能获得唯一结果。单主流程是一个逻辑推进/回复责任，不等于只调用一次模型。
8. 权限、资源排他、执行权、控制、UNKNOWN、Artifact 不可变、Verification、人工接受和 Business Commit 不变。聊天回复完成不等于 Task 完成。

## 5. 阶段 A：复现与最小工程协议

先用隔离临时目录建立可重复反馈回路，放入 README、子目录及包含随机验证标记的文件。从真实应用/HTTP入口发送原句，记录原消息、模式、作用域、实际模型请求、执行请求、工具调用和可见结果，证明失败发生在哪个边界。

不得只用预设 Fake 返回 CLARIFY 证明自然语言识别失败。可以用受控模型稳定复现“工具未暴露、上下文缺失、旧分支双触发、结果不可读”等确定性断点；真实 Provider 的自然语言表现单列。无法访问截图原记录时标记未核实，不冒充原消息根因。

修改前给出简短映射并落在相应已有协议文档中：

- 原消息/轮次的唯一推进 Owner，当前目录事实从哪里查询、冻结和重查。
- 会话只读工具来源与账本、业务用例工具、Run 接续的责任与最小类型。
- 哪些事实沿现有消息/请求/回执保存，确实缺失哪些持久关联。
- 工具/命令身份何时保存，模型或服务中断后如何读回原结果。
- 会话接续 Run 的提交边界、部分成功核对与 Worker 领取责任，避免双推进。
- 旧消息/旧请求和新消息路径的切换依据；不能只靠浏览器内存开关。
- API Breaking Change、兼容与迁移需求；不预先假定必须建新表，也不因少建表而把恢复依据留在内存。

通过条件：已有红灯反馈回路，目标能映射 AM-01–12，协议明确且无新增重复事实 Owner。完成后继续实施，不停留在方案等待用户再次确认。

## 6. 阶段 B：普通 AGENT 会话只读闭环

复用已有只读轮次和 Gateway，为普通 AGENT 的合法消息暴露本轮实际可用的只读工具。绑定目录从服务端合法会话关联取得；多个资源不取第一项，切换/撤权后重新核对。

主模型拿到：本次原指令、合法必要历史、当前目录/对象事实、有效工具以及本轮已结算结果。原用户指令、应用上下文、文件与工具正文分段，外部内容保持数据身份，不能借文件名或正文注入新授权。

至少闭合：

- “看一下这个目录下面的文件”“列一下当前目录”：默认直接子项，不递归抓全仓。
- “读取 README.md”“看看 src 里有什么”：当前目录内定位与真实读取。
- “解释一下这个文件”：只有确切目标时读取，取到结果后解释。
- 缺目录/目标歧义时一个聚焦澄清；缺连接、DENY、撤权、文件不存在或截断均返回真实原因。

保存工具请求、实际回执和必要模型轮次，刷新后可读；重放同一请求取原回执。读取不获得 FILE_WRITE/CLI_RUN、不创建写授权/Task/Run、不改业务状态。取消沿当前消息执行责任传播，UNKNOWN 不盲重发。

通过条件：真实文件随机标记由实际工具读入原模型轮次，原会话显示结果；文件未变且无写/CLI；AM-01–04 与相关 AM-07–09 定向反例通过。

## 7. 阶段 C：业务动作与 Run 接续

将现有任务准备和状态维护能力以有限类型化请求接到主流程，所有写入仍由原应用用例持有。

状态维护重点保留：原用户消息的明确授权、模型调用前的基线/适用版本、对象解析与当前 revision、必要决定、独立条目和部分成功、DECLINED/已存在/冲突语义、整组撤回预检、原命令幂等和中断恢复。不能改成“模型传某个 ID 就直接写”，不能用新主流程跳过原基线校验。

修改与检查重点保留：原 Task/Run 准备、固定命令回执、冻结范围与检查配置、FILE_QUERY/FILE_READ/FILE_WRITE/CLI_RUN 按需能力、Gateway、真实基线、run_check 失败→实际修正→复检。Agent 不直接调用 file adapter 写入或启动任意命令。

会话接续 Run 时，先持久建立原消息、执行请求、Task、Run 的确切关系与当前推进责任。准备或委托已提交但响应/阶段保存失败，查原回执再接续；不再问模型生成另一份任务。消息 Worker 与 Run Worker 不同时驱动同一动作，控制请求传给实际责任方。活动 Run 的新范围仍按原停止/重新委托要求处理。

Run 结果按原身份投影回原会话，可展开原产物、工具和检查依据。只有原验证/人工接受/完成用例才能推进业务完成，不因模型最后回复“完成了”自动提交。

通过条件：AM-05–09 通过，真实文件修改/配置检查和状态变更均沿原 Owner；不存在聊天和后台独立规划出两套相同工作。

## 8. 阶段 D：前端切换、旧请求兼容与回归

首条消息和已有会话后续消息都切到同一主流程，不再由前端每次发送额外并行启动执行解释、状态维护解释及独立自动应用。原功能不能只在一个入口恢复。

保留旧请求的查询、批准、原请求接续、撤回和失败核对；新路径不得自动重分类旧消息，也不得与旧入口双触发。不要删除历史表、旧端点或记录来“消除重复”。必要的遗留客户端行为须明确受控，防止旧客户端和新服务共同驱动。

将“按这个目标执行”从正常明确请求的固定门槛中移除；确有歧义、权限判断、审批或旧请求人工接续的场景仍给准确入口。原消息下显示读取中、执行中、等待批准、取消处理中、失败或未知，不用一个 Loading 代替真实状态。

原会话展示实际结果，不在执行时先生成“没有读取能力”的通用回复。切会话/目录时保护草稿及未决命令，迟到响应按原身份处理，不能污染新目标。沿现有组件和 tokens 做最小功能调整，不重做视觉。

通过条件：AM-10–11 及原入口回归通过；重新加载仍从持久事实恢复，浏览器内存状态不参与业务正确性。
