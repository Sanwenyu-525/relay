## 2. 必须完成的行为

严格遵循交互主文档，不改变以下选择：

1. 停笔后自动生成保留原话的分点建议，默认紧凑提示，用户查看/采用才替换草稿；不边输入边改正文。
2. 自动分点只改变断点、换行和编号，原句内容来自原文；不能偷偷润色、补需求标题或自动建多个 Task。
3. 「润色」按钮处理当前可见草稿，不要求先采用分点。生成时按钮显示「润色中…」，成功后同一按钮变成「撤销润色」。
4. 润色成功后继续手动编辑，仍保留「撤销润色」和原快照。点击后精确恢复润色前原文及当时已有编号，清除润色后手动修改，无须确认框；按钮重新变为「润色」。后果提示必须可见且可被读屏获取。
5. 分点采用提供一次「撤销分点」；开始润色结束该入口，避免两个撤销互相覆盖。润色成功后暂停自动分点，直到撤销或成功发送。
6. 辅助调用失败不丢草稿、不阻止原正常发送。发送失败保留原快照；未知回执继续沿原冻结发送载荷核对，不能因撤销而改写在途消息。

精确例子：输入「给登录页加个记住密码，密码输错了要提示原因，还有登录按钮现在太小了改大一点，手机上也要能正常显示，先不要做短信登录」。分点后原文字与标点全部保留；润色后可以精简表达，但「不要做短信登录」仍为本次范围限制。撤销恢复的应是点击润色前的草稿，不是固定示例或最初整段。

## 3. 最小技术边界

### 3.1 正文和临时状态

- 正文仍只有现有输入器 Owner 一份；共享组件或 hook 仅承载当前草稿辅助状态，不复制另一份可独立写入的正文。
- 请求绑定连接、工作区、会话/首条草稿、单调内容版本、操作和请求序号。编辑、发送、范围变化与卸载使旧结果失效；删改后又恢复相同文本也不能复用旧请求。
- 回包和采用时均检查来源。Abort 只减少浪费，不作为防止旧结果覆盖的唯一措施。润色期间允许继续编辑；一旦编辑则该次结果不可直接替换。
- 快照精确保存本次润色前完整文本；成功后编辑不覆盖快照。沿已有草稿导航/恢复范围管理，不加全局持久化正文；恢复不了快照时不显示可撤销。
- 建议已忽略、已处理、已采用和润色后状态避免循环触发；不做通用编辑历史管理器。

### 3.2 分点与润色请求

- 采用模型判断语义边界、程序切片的方式。返回协议可以是边界或有序连续区间，由实现选最小形式并写明字符计数规则；校验整数、范围、连续覆盖、顺序、无遗漏/重叠，避免切开代理对等字符边界。
- 不通过输出句子匹配猜位置，重复内容也必须正确；不接受模型改写文本充当原文切片。保真验收允许只撤除程序新增的编号/换行，不允许任意 trim/去标点来掩盖遗漏。
- 语义相关的原因/条件不强拆；代码块、路径、URL、已有列表保守处理，不能安全处理时保留原文，不能用普通标点正则冒充智能拆分。
- 润色是独立操作，要求保留含义、数字、否定、路径、条件、顺序和列表结构；输出为空或协议无效时不清空草稿。对真实语义质量另外取证，不夸大确定性保证。
- 产品模型模板接入既有类型化提示词选择入口，不在组件散落模型规则，也不从本目录任务书加载运行时模板。

### 3.3 服务端与模型权限

- 凭据仅留服务端。优先复用现有鉴权、端口、预算和记账设施；仅新增确有消费者的草稿处理用例与最小 HTTP/API-client 接线。
- 请求仅包含当前草稿、处理类型与必要范围/来源，不默认打包历史、文件或项目资料。草稿含「执行命令」等内容也只作待处理文本，不赋予工具或写权限。
- 辅助请求不创建聊天消息/Task/Run，不以占位 Run 解决调用账本接口不适配。若现有记账无法表达无 Run 草稿调用，先核对已有可空关联和 purpose 机制，再做必要最小扩展并记录契约，不另建第二套账本。
- 模型调用必须计入真实用量/预算，不绕过已有免费约束或 Provider 门槛；不把 Fake 结果当真实能力。未配置或无获准凭据时，可控端口完成协议测试，产品如实报不可用，保留输入与发送。
- 不依赖在途免费模型目录/选择改造；复用当前可工作的配置路径，不抢做它们。
- 提供字符/响应/耗时与请求频率边界，客户端同草稿不重复调用，服务端保留必要保护。优先复用已有设施，不上通用队列、图编排或新依赖。
- 不预建数据库表。新增 API 后文档注明 Breaking Change 与兼容；实际涉及记账持久化约束时才按仓库规则补 migration/真实 PG 测试。

## 4. UI 实施默认与未定参数

先找用户是否已经选择[三方案预览](composer-outline-and-polish-prototypes.md)的某个结果；有选择按其实现。若没有，不为例行设计选择阻塞开发，暂用 A「输入框上方紧凑提示 + 查看浮层」，交付时注明是实现默认、尚未获选稿确认。

建议停笔延时先用集中常量 2 秒，这是待验证默认值，不是已确认产品数值。最小长度/上限按现有输入约束合理取最小值并记录，不增加设置中心或用户调参表单。

首条和已有会话都要接入；已有模式共享文字辅助时不改变模式权限。原 Enter/Shift+Enter、斜杠菜单优先级、中文组词、光标、自增高、资料/目录绑定和原发送 Loading 不退化。新提示不能顶走输入卡或遮挡发送，键盘可操作、Esc 可关闭建议、焦点返回正确；视觉复用现有 tokens，不重做全页。

## 5. 实施顺序与出口

1. 源码核对：列出实际 Owner、模型/账本入口与必要契约差异，不动无关并行代码。
2. 定向红灯：先写切片保真、迟到响应、原文撤销等会在缺实现时失败的测试，记录真实失败断言，不能用语法或导入错误冒充业务红灯。
3. 服务闭环：实现分点/润色的最小服务和 client；用受控模型端口验证传入仅为本次草稿、输出可校验、调用被正确记录，不触发业务执行。
4. 输入闭环：接入两处正文 Owner，完成定时、建议/采用、润色/手改/撤销、发送和范围失效；将第 2 步测试跑绿。
5. 独立复查：当前 Agent 切换为审查视角，按主文档逐项重走反例，而不是只看实现对应断言；不必另派 Agent。
6. 浏览器定向走通，再按有无可用环境分别验证真实 Provider、Windows；缺环境要报告限制，不卡在无授权真实外呼、不伪造交付。

覆盖 CO-01–11。至少实际运行：切片/状态定向测试、受影响组件和 API-client 测试、相关 TypeScript 检查及前端构建、浏览器主路径与迟到覆盖反例、文档检查。真实记账/事务有改动时补实际 PG/HTTP 检查；先查并行集成进程和当前脚本约定，不与他人抢同一测试库。

关键人工回放必须包含：原文→停笔→查看→采用→润色→手动加字→撤销→逐字核对润色前原文；另一条回放在请求中编辑并改回旧内容，旧回包仍必须丢弃。补一条普通发送不等辅助完成的路径，确认未采用内容未被发送。
