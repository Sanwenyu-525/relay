## 0. 六条提示词共用基线

以下内容是每条提示词的一部分，执行者必须先读完再动手。

### 0.1 必读事实源（按顺序，只读相关部分）

1. `AGENTS.md`：协作规则、Skill 路由、验证与清理要求。
2. `CODEX_NEXT_STEP.md`：只确认当前阶段与是否有影响本页的在途工作，不读历史日志。
3. `docs/frontend/workbench-design.md` 中与本页相关的章节：业务交互、状态语义、文案口径。
4. `docs/frontend/design-system.md`：布局、层级、组件、动效与可访问性规则。
5. `docs/frontend/design-tokens.json`：颜色、字号、间距、圆角、阴影等数值唯一来源。
6. 目标页面源码、页面 CSS、其直接使用的共享组件、页面测试（Vitest 与 Playwright）。
7. 只有需要核对业务语义时才读 `contracts/README.md` 指向的 01–04；本任务不得改变业务语义。
8. 需要定位验收行时读[功能验收表](../docs/testing/overall-acceptance-2026-09-28.md#当前功能验收表)，只读相关行，不通读历史。

若提示词中的“现状”与代码不一致，以当前代码、契约和测试为准；不要为了贴合提示词改正确代码。

### 0.2 Skill 预检与使用

1. 先读 `docs/deployment/developer-skills.md` 与 `scripts/dev-skills.config.json`，按其中登记的共享目录定位 Skill（公共来源为 `%USERPROFILE%/.agents/skills`，不同工具目录可能不同）。
2. 实际打开本次要用的 `SKILL.md`，按其真实 description、When to Apply 与流程执行；不得只凭名称宣称已使用。
3. 每条提示词已指定“主设计 Skill + 辅助 Skill + 审查 Skill”。相似 Skill 只选一个主 Skill，其余只做本次检查，不重复全量执行。
4. Skill 与项目冲突时，以用户本次要求、已确认参考图、`workbench-design.md`、`design-system.md`、`design-tokens.json` 和业务契约为准；Skill 不得另造设计语言。
5. Skill 缺失、不可读或资源不完整时，报告具体路径与问题，改用现有规范继续；不得假装加载成功。

### 0.3 硬约束

**功能不砍。** 每条提示词列出的“功能不砍清单”是最低集合。可以改布局、拆组件、换呈现方式、合并重复代码，但不能删除入口、动作、状态、提示、链接、分页、筛选、深链或恢复路径。核心动作不得藏进二级菜单、悬浮层或仅剩快捷键；确有收起时，必须有等价可见入口且键盘可达。

**业务语义不动。** 不改 API、DTO、路由、query 参数语义、命令 ID、revision 核对、回执核对、权限/归档判断、服务端权威口径。不新增后端字段，不用前端推断冒充事实，不把未确认写成成功。

**两类数据链都保留。** 每个页面现有的 fixture（示例）与 live（本机 API）两条链都要保留；示例模式必须明确标注为示例，不得伪装真实数据，也不得因视觉统一删掉只读说明。

**状态必须区分。** Loading、刷新中、读取失败、空范围、筛选无匹配、待核对（UNKNOWN/pending）、成功、失权（401/403/404）不得互相冒充。错误不能渲染成空态，待核对不能渲染成成功。

**锚点与可访问性。** 保留现有 `data-testid`、`role`、`aria-label`、`aria-pressed`、`aria-current`、键盘顺序与焦点行为。允许新增锚点；确需移动时在原等价元素上保留旧 testid。图标按钮必须有可读名称，状态变化用 `aria-live`/`role="status"`。

**文案契约。** 承载业务边界的句子不得删改语义，例如“Run 结束 ≠ 检查通过 ≠ Review 通过 ≠ 正式完成”“不把本页数量当作历史总数”“收件箱只收未归属项目的人工任务”。可以压缩措辞、移入渐进披露，但不能改变含义。

**设计系统。** 只用 `design-tokens.json` 的数值与现有组件语气；不新增硬编码色板、字体、圆角体系或第二套 token。页面样式优先落在页面自己的 CSS；改全局样式或共享组件前，检查所有调用方并做跨页回归。

**依赖与范围。** 不新增运行时依赖、状态库、动画库或图标库；不顺手改其他页面、不提前建设通用布局框架。只有两个页面确实需要同一原语且两个执行批次能协调时，才允许抽共享组件。

**响应式。** 至少核对 1440×900、1162×782（项目常用验收窗口）、900×800，以及 design-system 既有窄窗断点；窄窗不得横向溢出，表格要有可读的降级形态。

**动效。** 只做有信息意义的过渡，建议 120–240ms；尊重 `prefers-reduced-motion`；不做装饰性循环动画；不因动画造成布局跳动或遮挡操作。

**并行保护。** 修改前查 `git status` 与目标文件 diff，不覆盖、不回退他人改动；禁止 `git stash`、`git reset`、整文件覆写、`git clean -fdx`。共享文件定点编辑。工作树已含大量未提交改动，不要假设 HEAD 就是当前运行版本。

**磁盘与产物。** 构建前检查目标盘剩余空间（低于 15 GiB 或分区 10% 先报告）；只清理本次任务产生的临时产物；截图与证据放 `tmp/<task-id>/`；不删除他人构建、数据库、发布包或验收证据。

**文档。** 只有交互/信息架构真的变化才更新 `workbench-design.md` 对应章节；只有视觉规则变化才更新 `design-system.md`；数值变化才动 `design-tokens.json`。同一事实只写一处。没有独立验收就写“实现者自检，未独立验收”，不得把自检写成已验收，不擅自改验收表结论。

### 0.4 验证与证据

### 1.1 范围

### 1.3 功能不砍清单

- `/reviews` 路由；`?id=` 选中指定请求、`?kind=` 初始类型筛选；点击列表项写回 URL；刷新。
- 类型筛选：`ALL` + 现有各类别，显示数量与 `aria-pressed`，只显示有数据的类别（当前类别始终保留）。
- 列表项信息：标题（服务端产物标题优先，其次示例版本 ID，再退回理由）、状态（待判断/已过期/目标已失效/已处理）、类别、项目名或“未归属项目/项目名称暂不可读”、请求时间、请求修订。
- 读取失败与空列表的区分；401/403 失权时撤下旧正文但保留请求身份与决定/回执入口的恢复壳。
- 所选请求详情：“为何需要你”理由、请求事项、请求时间、请求身份（请求 ID/修订/Project ID/Task ID）、有效期、关联任务与产物、版本来源、执行与完成状态链接。
- 绑定对象阅读区（live 且目标为产物版本时）。
- 决定区全部能力：可用决定、写阻塞原因（读取中/失败/项目归档）、待核对回执处理；不得把决定区改成不可操作的展示。
- 同一次执行的下一条待办接续链接。
- 宽窗/窄窗的页内定位与焦点移动能力（可以换成更好的结构，但必须保证键盘可达、不会替用户提交决定）。
- 示例模式只读说明；时区显示偏好。

### 1.4 允许的重构与建议方向

- 把页面拆成“请求队列 / 判断对象与证据 / 决定”三个语义区；宽窗用主从布局，队列可独立滚动，决定区在阅读区内保持可见；窄窗退回单列，决定区紧跟证据之后。
- 把“请求身份/有效期/来源链接”整理成紧凑事实区，替代散落在正文中的重复说明。
- 统一列表项的状态与类型语气；选中态、过期态、已处理态用同一套视觉规则表达。
- 可以把“查看判断条件/前往决定”改造成结构内导航或粘性决定栏，但必须保留等价入口与焦点行为，并让原浏览器测试仍能完成导航。
- 允许抽出页面内的子组件与纯展示辅助函数；不新增全局抽象。

### 1.5 Skill

- 主设计 Skill：`impeccable`，按 `critique → layout → typeset → polish` 的顺序使用；先审现状，再改结构，最后精修。
- 辅助：`ui-ux-pro-max` 只用于密度、层级、排版检查；`vercel-react-best-practices` 用于组件拆分、渲染与交互质量；`web-design-guidelines` 做可访问性与界面规范审查。

- 在交付中写明实际读取的 `SKILL.md` 路径与应用的子命令/规则。

### 1.6 验证场景

### 6.4 允许的重构与建议方向

- 统计卡改成更紧凑的状态概览，数字与状态名对齐；不新增服务端未提供的指标。
- 表格可拆页面内 `ScheduledRow`；标题与调度事实分层，下次触发用更强语气，状态 chip 与操作同列对齐。
- 待核对警告移到列表上方的固定区域，保留全部说明与按钮；不要做成会遮挡操作的浮层。
- 操作按钮保持文字可读；禁用态与忙碌态有明确区别。不要用只有图标的危险操作。
- 窄窗把每行转成“标题 + 调度事实 + 状态 + 操作”的卡片；表头可隐藏但列语义以 `data-label` 或结构保留。
- 不改变 `describeRepeat`/`formatInZone` 的输出语义；若必须移动，保持导出并更新引用。

## 7. 执行顺序、并行边界与集成

推荐顺序（先统一列表原语，再处理投影与决策页）：

1. `UI-PAGE-TASKS-01`：先定任务表格/行/工具条的呈现规则。
2. `UI-PAGE-INBOX-01`：复用任务页刚稳定的列表语言；注意 `TasksView` 会渲染 `InboxView`。
3. `UI-PAGE-TODAY-01`：今日页包含任务行与状态动作，适合在列表规则稳定后重排。
4. `UI-PAGE-REVIEWS-01`：决策工作区，独立性强，放在列表与今日之后可复用已验证的排版密度。
5. `UI-PAGE-ACTIVITY-01`：动态流与检查器，独立性强。
6. `UI-PAGE-SCHEDULED-01`：表格与状态操作，最后收口。

并行规则：

- 任务与收件箱共享 `InboxView`，默认串行，不并行改。
- 今日、待处理、动态、定时任务文件互不重叠，可在各自 `git worktree add --detach <dir> HEAD` 工作树中并行；并行期间冻结 `design-tokens.json`、全局 CSS、`PageHeader`/`StatusChip`/`EmptyState`/`ResponsiveRail` 等共享组件。
- 每个执行者只提交自己页面的 `.tsx`、`.css` 与测试改动；协调者负责合并、跨页回归和独立验收。
