## 1. P1：首条发送丢失响应后，原消息命令无法恢复

定位：`apps/workbench/src/views/AssistView.tsx` 的 `createSession`，受验基准约 194–204 行；对照普通会话的 `PendingAction`、`runAction`、`checkReceipt` 与导航状态。

复现：打开无会话目录 → 首条发送 → 建会话成功 → 消息被服务端接受但响应丢失。当前先清 `pendingCreate`、调用 `loadTarget` 增加请求版本，消息命令只保存在局部变量；catch 因版本变化返回。实际无原 command_id、回执入口或错误提示，仍可离页。

修复要求：

- 首条消息复用普通发送的未决命令、原载荷与回执核对机制，明确保留“会话已创建、消息结果待核对”的部分成功事实。
- 建会话和发消息是两个命令；各自保留原身份。查询或重试消息不能再次建会话，不能更换消息命令的 `command_id` 或把用户后来修改的文本混入原载荷。
- 请求版本隔离仍须阻止迟到响应污染新目标，同时不能吞掉当前未决动作。未核对前，离页、切会话、新对话与换目录沿既有守卫处理。
- 同 ID 重试、回执找到/未找到/读取失败、双击发送、连接变化均按既有协议处理；不把传输失败推断为业务失败，不宣称模型或任务已完成。

## 2. P2：首条未发送草稿离页丢失

复现：无会话目录填写首条输入 → 点击主导航“项目” → 无提示离开 → 返回打开同目录后草稿为空。普通 Link 导航已在真实浏览器复现，与历史 POP 偶发是两个场景。

## 3. P2：首条明确执行输入跳过执行解释

定位：首条发送约 199–200 行，对照普通发送约 644 行 `requestExecution(sent.userMessageId)`。

复现：无会话目录首次发送“帮我把这个文件的内容改成 after”。消息已发送，但 `/execution-requests` 请求为 0、摘要不存在；同目录同会话的下一条普通消息正控制请求为 1 且摘要存在。

### A. 换目录必须经过保护，恢复必须绑定原资源

核对 `CollaborationView.openFolder` 是否经过 `requestTransition`。两处FolderScope、手动/原生选择、近期目录与作用域选择都要沿既有守卫处理。未发送草稿允许明确保留或放弃，未决消息在核对前不得换目录；先守卫再发OpenWorkingDirectory，不能先登记新作用域再询问。仅选择或取消不能吞掉原文。

首条恢复保存确切workspace、project、session、目录/资源与原载荷。解释原消息时只使用其原资源，不能从当前新executionScope重新取值。迟到回调不得写入其他目标；保留业务身份与连接变化的核对边界。历史反例：res-1中的未决消息，切到res-2后查询原回执，解释向旧session发送了res-2。当前回归必须拒绝这种资源错配。

### B. 首条解释结果必须交接到当前会话

核对 `onSessionCreated` 后 AssistView 的 key、重挂载以及 `firstExecution` / `initialExecution` 的交接。历史反例中，解释已成功但结果写入旧实例，当前页面没有摘要。复用稳定的协作入口保存该首条过程和结果，按确切会话/消息交接到现有摘要Owner，不在旧实例存唯一事实、不创建第二套执行确认。

首条解释返回PREPARE或CLARIFY后，当前页面必须显示对应摘要、原因/问题与正确动作；不能只断言POST=1。纯讨论仍由服务端判定，不自动建Task；摘要与“按这个执行”保留原执行边界。

### C. 在途响应与回执核对只能完成一次

核对 `creating` / `sendingFirst` 能否跨重挂载维持同一在途阶段。历史反例中，原消息响应未到，新实例已可查回执，核对成功后原响应迟到又解释一次。把忙碌、阶段完成与原命令身份放在同一稳定Owner；原发送、核对、重试的成功/失败回调必须检查确切命令和当前阶段。一次核对完成后，迟到成功不得重复解释，迟到失败不得复活已清空pending。

同一原消息的解释只发一次，或按固定解释命令身份进行协议允许的核对/重放；不能每条迟到成功路径新造command_id。不要用删除失败断言、固定延时、强制重载或通用状态机框架规避生命周期问题。

### D. 创建回执恢复不能吞掉首条载荷

创建与发送是两个命令，但属于同一首条用户过程。保存首条原文、资料/意图与后续阶段；创建响应丢失后，按原CreateAssistSession回执恢复确切会话，并交接或续发原首条消息。该消息自己的command_id一经产生必须固定；不得重建会话、猜session/sourceMessage ID或混入后来输入。

核对成功后用户应看见首条消息的发送/待核对/错误状态，不能只出现空白普通会话。若仍待核对，保留原载荷和守卫；只有明确协议允许的终态或放弃才清理。
