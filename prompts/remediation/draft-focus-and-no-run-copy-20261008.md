## 1. 已确认的问题与边界

### A. “保留并继续编辑”没有恢复编辑位置

复现路径：在空白讨论中输入未发送中文草稿 → 窄窗打开导航 → 点击抽屉顶部“新对话” → 草稿保护弹层选择“保留并继续编辑”。

实际结果：路由和草稿保持正确，但焦点回到“打开导航”按钮。随后第一次 Tab 到“选择文件夹（可选）”，Shift+Tab 回到“打开导航”；输入框没有编辑焦点，继续写作需要再次定位它。这是编辑体验缺口，不能描述为草稿丢失或整个页面必然失焦。

目标：用户明确选择继续编辑后，返回触发保护的草稿编辑区，保留已有正文、选区或光标位置，让用户不用重新点击便能接着输入。宽窗和窄窗采用一致语义。

### B. 未关联 Run 的任务仍指引用户核对“原 Run”

复现路径：创建独立人工任务，填写中文目标与 HUMAN 条件，保存后追加一条完成条件，再阅读任务详情的“验收依据”。

实际数据：任务 `READY`、人工执行、`executor_run_id=null`，Run 与验证会话均为 0，当前验收版本有 3 条条件。实际 UI 却显示“尚未运行检查：当前 Run 没有已完成的验证会话”，逐项下一步显示“运行或核对原 Run 的当前版本检查”。它指向了不存在的当前执行记录。

目标：根据真实 `runId` 区分“当前未关联执行记录”“已有 Run、尚无验证记录”“已有历史验证记录”“读取失败或事实变化”。无 Run 时不使用“当前 Run”“原 Run”的措辞，不要求人工任务为了消除提示而创建 AI Run。下一步要指向已有任务工作区或验收方案中可实际完成的核对操作。

已核对的边界：检查计划是服务端读时生成的预览，HUMAN 条件也可以映射到 `human-evidence-v1`。因此“全部条件已关联计划项”不意味着已执行，也不是空集合导致的错误。保留预览、执行结果、版本匹配和当前适用性之间的区别；不要因此改写后端计划生成或把预览当作通过证据。

## 3. A 的实施要求

1. 沿用现有草稿注册与导航拦截，不维护第二份草稿正文或业务状态。编辑区可以按已有机制登记一个有限的恢复回调或存活目标，由保护流程调用。
2. 焦点恢复应发生在守卫弹层完成关闭之后，避免被 `AppDialog` 的默认关闭回焦覆盖。不要用任意固定延时碰运气；处理组件卸载、目标失效和待处理命令状态。
3. 草稿的光标位置或选区来自用户原来的编辑位置，不能每次强制跳到开头、末尾或全选。无需新增持久化表或全局状态架构。
4. 只有明确选择继续编辑时恢复编辑位置。保留普通抽屉 Escape 的触发按钮回焦、其他弹层的正常回焦和确认丢弃后的新对话行为。
5. 若原编辑区已不存在或不可编辑，使用仍存活的合理目标，不聚焦卸载节点、不抛错、不无限重试，也不绕过现有禁止离开的业务保护。

## 4. B 的实施要求

1. `runId=null` 是没有关联当前 Run 的事实，不由验证数组为空、页面标题或任务状态猜测它。不要据此声称任务从未有过任何历史执行。
2. 修正主阅读位和逐项“下一步”中相同问题；技术详情若在无 Run 时仍称“当前 Run”，一并对齐这一条件分支。正常有 Run 的旧行为保持。
3. 对人工核对条件使用现有人工验收/证据语义，给出任务工作区或验收方案中的实际入口方向，不能要求用户核对一个不存在的 Run。
4. 读取失败、版本变化、历史结果不适用仍需保留相应不确定提示。不能通过空数组把读取失败写成“没有运行”，也不能将计划关联写成已有执行证据或已通过。
5. 保持当前详情布局、中文字号、条件编号、单列证据正文和技术信息展开规则，避免顺手重排页面。
