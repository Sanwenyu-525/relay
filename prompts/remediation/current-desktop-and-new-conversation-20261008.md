## 三、把“新对话”做成用户能直接找到的入口

目标是让常规、窄窗和短窗都能发现并使用新讨论入口，保持既有视觉细节和行为一致。

1. 使用现有全局新对话语义和路由机制，在上下文栏隐藏时提供明确、可见、可键盘到达的入口。优先放到现有窄窗导航或工作台合适位置，保证至少一条路径无需先展开“选择文件夹”。不要每个区域重复增加主按钮。
2. 新入口与宽窗入口含义一致：进入空白讨论，不能悄悄继续当前目录、任务或旧会话。不要误用会话列表里的“新建会话”，那个入口可能保留当前目标和目录。
3. 复用现有草稿/导航保护。存在未发送内容时，用户留在当前工作区应保留正文、会话、目录和焦点；确认丢弃后才进入新讨论。若当前全局入口已有相同缺陷，先做真实反例，再用最小公共修复统一入口，不另建一套业务状态。
4. 按现有公共控件精修：图标和文字对齐、正常与悬停/按下/焦点反馈、适度点击区域、禁用语义、抽屉关闭后的焦点返回、滚动后入口不被顶栏遮挡。数值从 token 取，不写第二套尺寸和颜色。
5. 抽屉打开时背景和键盘交互正确，点击新对话后抽屉正常关闭；Escape 可关闭并回到打开按钮。不能靠隐藏标题、压缩中文字号或扩大横向滚动来掩盖布局问题。
6. 添加必要的行为回归：窄窗入口可发现、进入新讨论后上下文清空、草稿取消导航保留、确认丢弃切换、抽屉关闭与键盘回焦。使用当前既有测试体系，不写只镜像 DOM 的测试，不放松旧断言。

文件夹选择器取消已经通过。只有复验出现真实新故障才修复；不要为了“优化焦点”强行把取消后的焦点抢到输入框。确认选择目录是业务写入，必须只在下一节的自有隔离工作空间中测试。

## 五、用自有隔离实例验收，保持用户数据和服务安全

1. 先核对当前原生窗口、宿主/子进程、执行文件、配置、数据源、未发送草稿和在途任务。只有确认安全后，才通过电脑插件正常关闭旧窗口，避免丢失用户草稿或中断未处理动作。
2. 桌面各包共享单实例约束，旧窗口仍在可能使新实例退出。先正常关闭和核对退出；不要绕过 mutex、改应用身份或批量结束 node/postgres。无法安全关闭则明确记录阻塞，继续其他独立工作。
3. 使用现有 `start-acceptance-session.ps1 -InstallGraph -UseCLocale` 创建自有初始化完整的数据库、工作空间、配置与数据根。核对该脚本是否已按当前版本自动构建；依照实际实现避免无意义重复构建。读取 `session.json`，确认实际启动的是第四节核对过的产物。
4. 核对 readiness、必要 migration/Graph schema、API 端口、workspace、数据库、宿主和子 API 身份。只记录非敏感投影，不输出 bootstrap token、连接密码或用户消息正文。
5. 使用明确标记的测试目录、项目、任务、会话与 Fake/Mock 边界。目录确认可能创建 Project/State/View/ManagedResource，不能把它当纯 UI 操作。不要选择用户真实项目目录来造样例，不改用户连接、权限或会话归属，不自动调用真实 Provider。
6. 测试结束先关闭自有窗口并确认自有进程退出，再按 marker 使用匹配的 `stop-acceptance-session.ps1 -SessionRoot …` 清理。清理目标必须属于本轮实例；进程未停或身份核对失败时保留目录并记录限制。用户 PG、Vite、API 等服务不在清理范围。历史被自动审核拒绝删除的目录保持原记录，不重试或换方法规避审核。

## 六、真实 Windows 业务验收必须走产品入口

协调者用电脑插件操作真实 Windows/WebView2，先读该插件 SKILL 和要求的文档。窗口操作不能用浏览器 Playwright、PowerShell UI Automation 或其他原生工具代替。浏览器回归可以作为独立一层证据。

每个动作先读取当前窗口，按实际控件操作，再读取结果。发生截图或点击边界问题时依插件规则有界恢复，不能将工具故障自动归为产品缺陷，也不能绕过工具限制。

### A. 新对话与原生目录选择

- 常规窗、约 833×782 窄窗、约 833×591 短窗和最大化宽窗实际检查入口、中文文本、滚动、键盘和焦点。尺寸以插件实际返回为准，没得到目标尺寸就注明未覆盖。
- 从原本有会话的测试上下文进入新对话，确认新讨论不继承旧目录、任务或选中会话；“工作台继续最近会话”与“新对话”语义清楚。
- 在自有草稿上核对新对话的留在当前/确认丢弃分支，不能用用户已有消息做测试。
- 打开原生目录选择器后取消，检查草稿、上下文和键盘连续性；再确认选择自有目录并核对真实持久结果。不要把插件直接输入中文记成真实 IME 合成通过。

### B. 同一个会话的目录/项目归属

- 在隔离实例建立明确测试会话和历史，使用现有 Fake/Mock 机制产生数据，不外呼真实模型。
- 从产品入口将原未归属会话归入自有目录/项目，核对前后 session ID 相同、旧消息仍可读、归属事实真实落库；不能创建第二个会话伪装“历史保留”。
- 在受控边界覆盖真实拒绝和响应不确定，未确认时不能显示成功，旧历史不消失。核对沿用原请求身份，不重复创建或绑定。
- 只读查询与日志作为业务结果旁证，不能直接改数据库状态后宣称产品流程通过。

### C. 未知 Run 控制命令的核对与恢复

- 只使用本轮自有、有效的受控 Run，保持任务版本、执行权限和租约前置正确。不通过禁用审批、改用户权限或伪造回执绕过前置。
- 普通 202/PENDING 不等于 UNKNOWN。需要真实提交原控制请求且结果响应丢失，再通过产品恢复路径核对。
- 如现有工具不能直接在 WebView2 注入丢响应，使用范围受限的测试传输边界，仅作用于本轮实例、指定测试 Run 和原请求。优先复用现有机制，不新增生产通用代理层、不全局断网、不停止用户 API、不改系统代理。
- 对同一 Run 的 revision 更新、事件刷新和同窗口整页重读，确认原 command ID 和核对入口仍存在，回执查询沿用原 ID。未决状态不得重复提交，也不得仅凭提交意图或响应未知提前宣称已暂停/接手完成；服务端查询确认的当前状态应如实显示，原命令核对入口继续保留。
- 整页重读与页面里的“刷新事实”分别核验；关闭重开是另一种恢复语义，不能互相替代。浏览器已有 `route.fetch/abort` 证据不能直接算原生证据。
- 若本轮无法可靠制造真实 UNKNOWN，写明缺哪条前置或注入能力，将此出口保持未验收；不要伪造 UNKNOWN 行、用合成界面代替业务通过，或把它描述成产品已复现失败。
