# ADR-039 后台工作 tick 由常驻 API 驱动，不新增调度进程

- 状态：Accepted（代码已实现并经真实子进程集成验证；Windows 宿主实机生命周期未验收）
- 日期：2026-11-01
- 相关：ADR-007（Windows 桌面交付与本机服务边界）、ADR-014（维护排空准入门）、ADR-034（项目级长期 Agent 成员与跨会话协作）、[runtime-context §2.11](../architecture/runtime-context/part-02.md#211-常驻进程与后台-tick-的对应关系2026-11-01eng-sa-01-修复)

## 背景

推进责任分散在若干 `run*Tick()` 应用 Owner 里，但函数存在不等于有进程去调它。发布拓扑实际拉起的
是「常驻 API ＋ 常驻 Supervisor ＋ 按需一次性 Worker」：`--once` 只领一条 Run 命令，`--assist-once`
只做一轮会话生成，持续 Worker（`worker/main.ts` 不带标志）在桌面宿主和 `dev-stack.ps1 -WithWorker`
里都没有启动入口。成员唤醒、会话执行自动推进与网页导入三条 tick 原本只出现在持续 Worker 的分支里。

2026-11-01 用真实 API 子进程复现（关掉新执行者，其余构建、迁移、图安装、PostgreSQL 全部退出码 0）：
三条链路各自停摆，成员消息恒为 `RECORDED`、执行请求恒为 `READY`、导入 job 恒为 `QUEUED`。这不是
「关掉页面才停」，而是没有任何页面或点击能触发它们，只能等有人手工启动一个不交付的进程。同一条
消息在两个宿主同时在跑时也只产生一位结算者，说明缺的是驱动者，不是并发保护。

## 决定

1. **三条 tick 的周期驱动挂到常驻 API**（`runtime/background-work-scheduler.ts`，经 `api/routes.ts`
   注册），沿用同仓既有调度器约定：`onReady` 自挂载、`setTimeout` 自续、`timer.unref()`、readiness
   先过关、失败按签名去重记一条日志。不新增调度进程、系统服务、消息总线或第二套状态机。
2. **只调用既有应用 Owner，不复制业务判断**。派发器不含任何领域规则；准入门、领取 CAS、行锁、
   租约与尝试上限全部留在各 tick 函数内部，因此换任何驱动者都不会绕过它们。认领身份为 `api:<pid>`，
   新宿主不顶旧身份的租约。
3. **一 tick 一驱动者**。`runAssistGoalTick` 仍归 Supervisor，`runAssistGenerationTick` 仍由一次性
   Worker 承担，都不搬进 API；`worker/main.ts` 的持续分支保留不动，供手工启动时与 API 安全并发。
4. **挂 API 而不是内联 Supervisor**。Supervisor 的主循环是串行派发路径，一次成员唤醒的模型调用在
   租约内可持续数十秒，内联进去会推迟同进程的 Run 派发；API 则是唯一在所有拓扑都常驻的进程。
5. **空闲即等**。候选查询返回空集时不发起模型调用，不为「看起来在干活」制造工作。

## 理由与代价

收益是发布拓扑里第一次存在真实的后台推进者，且改动面只有一个新文件加一行注册。代价与风险：
API 进程多承担了三条轮询的数据库负载（1s 一次候选查询）；API 与手工持续 Worker 同跑时会出现竞争者，
靠 CAS 与行锁收敛，已由用例覆盖；把 tick 挂到 API 也让「谁驱动后台工作」这个问题第一次有了单一答案，
后续若要引入真正的独立 Watchdog 或事件驱动唤醒，替换点在派发器而不在 Owner。

被否决的候选：把持续 Worker 变成默认交付进程（多一个常驻进程与一套生命周期，且不解决桌面侧的
启动入口缺口）；改由前端定时请求触发（违反推进 Owner 收归服务端的既有决定，页面关闭即失效）；
新建第二套调度引擎（重复状态机，违反不新增通用调度引擎的约束）。

## 影响

- 只启 API 与 Supervisor 的栈也会消费成员消息、推进已授权候选、跑完网页导入；文档中的
  `-WithWorker` 前置条件仅对 Assist 生成与 Run 步骤仍然成立。
- 维护排空、暂停/取消、权限撤销语义不变：准入门在 Owner 内部，排空期间既不准入新唤醒，也不清扫
  过期领取，恢复准入后同一条接着走完。
- 未闭合：真实 Tauri 窗口的隐藏/销毁、Job 对象与「明确退出后不再发起本机执行」只有代码路径与
  进程级用例支撑，缺实窗证据；孤儿 `ACTIVE` claim 的收敛仍属既有结构缺口，本轮不扩大范围。
