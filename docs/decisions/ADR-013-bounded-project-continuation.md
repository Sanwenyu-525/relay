# ADR-013：长期协作通过既有领域入口实现有限连续委托

## 状态

Proposed。日期：2026-09-28。用户确认后续优先长期项目协作，本 ADR 的具体授权、调度和对象设计仍待分包确认。未替代 ADR-001、ADR-008、ADR-010，未授权实现。

## 背景

[后续路线](../requirements/post-v1-roadmap.md)希望从单任务委托发展到项目接续、周期计划和有限任务链。现有 Project/Task/Run、Artifact/Verification、Permission/Gateway 与持久命令已有各自责任；增加自动推进不能产生第二个 Task 完成入口，也不能将 Trigger 或计划接受视为工具授权。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 只生成建议，每次人工启动 | 最小实现、授权直接 | 多个已确认小任务仍需重复操作；适合作为 N04/N05 的先行形态 |
| 既有命令上增加有限执行授权与资格检查 | 可复用原恢复、审批与资源语义，行为能解释 | 需设计预算预留、撤销竞争、跨 Run 恢复和真实故障测试 |
| 新建项目级自主 Agent/独立编排平台 | 适合开放式规划和动态分工探索 | 易重复维护执行权/完成状态，扩大部署和测试范围；不符合当前首片需求 |

## 推荐决策

推荐分两步：先交付只产生建议的计划/触发，再在明确接受的有限任务集合上增加应用层连续委托。继续使用单用户同机模块化单体、PostgreSQL 持久事实和命令、LangGraph 的单 Run 图执行。没有测量或功能证据时不引入新队列、常驻服务、多 Agent Router 或另一图引擎。

逻辑上需要区分计划候选、执行授权和触发记录，但不预定新服务或表数量；开工时优先复用现有提案/配置/回执。Project Checkpoint 只保存一致的版本引用集合；AI 导读属于可丢弃的派生内容，不成为第二事实源。

Application 在短事务内校验有效授权、Task 基线、预算预留与领取身份，并调用既有 Delegate 保存必要事实/命令。模型、工具、人工等待均在事务外。撤销与新准入必须共享可序列化的授权检查边界；实际锁序服从既有 Authority/Task/Run/Resource 协议，并由真实数据库竞争测试定稿，不能凭本提案虚构已实现锁。

Trigger 只负责在指定时点提出请求；授权策略决定该请求最多能做什么。权限仍由 Permission/Gateway 每次校验，当前授权与当前权限取交集。Task 完成仍只由 CompleteTask 产生；计划/队列只引用其结果，不拥有另一份“完成”状态。

## 决策原因与代价

先让用户看懂变化和计划，再逐步减少已明确授权范围内的重复操作，能把使用收益与自动化风险分别验证。代价是自主性有限、过期/未知状态会停下、每片都需故障与人工接手测试；它不承诺无限自治或关闭应用后继续运行。

## 影响范围

- 前端：项目接续、候选审阅、授权与停止入口，继续复用现有工作台/token。
- Application/Domain：增加组合用例和有限授权协调；Project/Task/Workflow/Information/Gateway 的写入责任保持不变。
- 数据库：可能新增检查点引用、触发去重与执行授权记录；字段/约束、迁移兼容及保留策略待设计，本轮无 migration。
- API：可能新增专用命令与只读投影；本轮未发布接口，当前 Breaking Change: No；未来按工作包评估，不预先保证兼容。
- 部署：首片随桌面生命周期运行，不安装 Windows 服务，不引入远程运行。
- 测试：来源失效、组合证据、双领取、禁用/撤销竞争、崩溃、预算耗尽与 UNKNOWN；见[后续验收](../testing/verification-plan.md#14-v1-后续长期协作验收提案)。

## 后续

N01 前冻结检查点引用与清理策略；N05 前冻结时区/漏触发/去重协议；N06 前冻结授权和预算协议。可分别接受对应片，不必一次批准全部。若未来增加外部执行器、关闭应用后运行、多用户或远程设备，另立 ADR 明确身份、停机证据和信任边界，不自动沿用本方案的同机假设。
