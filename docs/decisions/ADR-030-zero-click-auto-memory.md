# ADR-030：零点击的自动记忆（自动生效、可撤销、明确标注）

## 状态

Accepted（产品方向由用户 2026-10-20 确认）。后端已实现：迁移 `0125`、结算后提取链、`GET/POST /memory-auto-captures`、`origin` 投影与召回排序、设置第三开关；工作台已接开关与「自动记住」标注。**真实 PG 集成与真实 Provider 质量未验证**，进度只归 CODEX_NEXT_STEP，结果只归统一验收表。取代 [ADR-029](ADR-029-auto-memory-candidates.md) 的「候选 + 确认」环节。

2026-10-21 更正（见 [ADR-032](ADR-032-memory-source-kind.md)）：本 ADR 的实现有两个从未被发现的缺口——`memory_versions` 的 CHECK 仍要求 `confirmed_by = 'user:local'`，真实 PostgreSQL 上每次自动捕获写入都被约束拒绝并被失败静默吞掉（**「自动记住」从未真正落库**）；自动捕获没有写 `origin`，落到默认的 `HUMAN_CONFIRMED`。两处已在迁移 `0130` 与写入路径修掉，并新增来源类别与「由系统判断要不要记」的口径。本 ADR 的产品方向不变。

## 日期

2026-10-20。

## 背景

用户先指认「长期记忆应该是自动保存有价值的内容而不是手动」，在三个落点中选了「自动提取候选 + 一次确认」；随后又指出「要人手动确认感觉很麻烦」。

这条反馈是对的：候选队列只是把「点一下」从消息旁挪进另一个列表，**确认成本没有消失，只是换了个地方**。一个需要用户定期清理的待确认列表，最终会变成没人看的收件箱。

因此确认环节取消。但取消确认必须同时回答一个问题：**没有人工签字的推断，凭什么进上下文？**

## 候选方案

1. **候选 + 确认**（ADR-029）：摩擦未消除，否决。
2. **自动写入、参与召回、标注自动来源、可撤销、限频**（采纳）：零点击；错误推断会进上下文，但每条都可追溯、可撤销、可降权。
3. **自动写入并视为人工确认**（不区分来源）：最省事，但事后无法判断哪些是模型推断、哪些是人的决定，撤销与审计都失去依据，否决。

## 决策

采用方案 2。要点：

- **写入即生效**：普通 AGENT 会话在一轮生成结算后提取，最多 3 条，直接写 Memory；`memories.origin = AUTO_CAPTURE`，`confirmed_by` 记 `auto-capture`（**不冒充人**）。来源冻结为原消息 `(session_id, message_id, content_sha256)`，与手动保存同一条 provenance 表。
- **参与召回，但排在人工确认之后**：同一范围内先取 `HUMAN_CONFIRMED`，再取 `AUTO_CAPTURE`；两者都受原有「最多 3 条 / 8000 字符 / 20 来源」上限约束。召回投影与消息 sources 带 `origin`，界面能标「自动记住」，模型侧仍按 UNTRUSTED_DATA 处理。
- **可撤销，且撤销能止住重复**：一键撤销把该条 Memory 停用（复用既有 retire 语义，不物理删除、保留审计），同时把 `(session_id, message_id, normalized_sha256)` 记为已撤销；之后同一内容不再提取。
- **只提取明确陈述**：决定、约定、偏好、事实性结论；不提取推测、不提取一次性任务细节、不提取寒暄。没有值得记的内容时返回空数组是合法结果。
- **限频**：每会话每日最多 5 条自动记忆；超出只记 activity、不写 Memory。避免噪音淹没真正的人工记忆。
- **失败静默**：超时、非法 JSON、预算不足、Worker 丢失一律放弃这一轮，不写记忆、不改聊天正文、不重试、不换模型；主回复照常完成。
- **可关闭**：`memory-settings` 增加 `auto_capture`（默认 true）。关闭后不再提取；已写入的自动记忆仍按原规则召回，用户可逐条撤销或整体停用。

## 代价与限制

- **错误推断会进入上下文**。标注与降权只能降低影响，不能消除；一条被写错的偏好会在后续多轮里持续起作用，直到有人发现并撤销。这是零点击的必然代价。
- 自动记忆数量会随时间增长，用户可能长期不清理；限频只控制增速，不解决存量。
- 「明确陈述」的判定依赖模型，边界模糊：同一句话可能被不同模型判成事实或闲聊。
- 真实 Provider 的误报率、重复率与成本必须实测；Fake 模型只能证明工程链路。
- 撤销是「停用」而非删除，因此错误内容仍留在审计与历史版本中（这是刻意的：可追溯优先于彻底遗忘）。

## 影响与后续

- `memories` 新增 `origin`（默认 `HUMAN_CONFIRMED`，旧数据不受影响）；新增 `memory_auto_captures` 记录提取批次、撤销状态与去重指纹（新 migration，不改已应用迁移）。
- 召回排序与投影增加 origin；消息 sources 增加 origin 标注。
- **不新增任何常驻面板、不收件箱、不加角标**：自动记忆直接出现在既有「资料 → 记忆」列表里，用 origin 标注「自动记住」，撤销就用既有的「停用记忆」；消息来源处标一句「自动记住」。这是本方案对「别麻烦我」的进一步回应——自动化的收益不能靠再长出一个需要照看的地方来兑现。
- 提取链挂在结算之后，不在数据库长事务内，走既有 `model_calls` 预算。
- 工作包见 `prompts/auto-memory-candidates.md`（已按本 ADR 重写）；成绩只归统一验收表。
