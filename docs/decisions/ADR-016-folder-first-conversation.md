# ADR-016：文件夹入口与对话直接执行

## 状态

Accepted（产品入口、用户意图与复用既有业务 Owner 的原则）。2026-10-18：本地目录基础读取配置与写入档位已由 Application 实施，HTTP/物理合同见 [HTTP §10.86](../api/http-command-contract.md#1086-目录写入档位投影与只读查询2026-10-17-源码实现) 与 [数据库 §98](../database/physical-design-postgresql.md#98-0109-本地目录访问档位元数据2026-10-18-源码实现)。真实 PG/HTTP/磁盘与桌面/Provider 的验收边界归统一功能验收表；ADR 的其他文件夹入口行为不因此自动视为整体验收通过。2026-10-17：**写入档位预设**已按[工作台 §18.1.3](../frontend/workbench-design.md#1813-输入器的本目录写入档位2026-10-17)核定为「每次确认 / 本次任务自动 / 不开放写入」三档，明确不提供「完全访问」，并已实现输入器入口与只读投影。**2026-10-18 第二次接续取代上一句的档位集合与「不提供完全访问」**：用户实机指认后按通用 Agent 口径改为「请求批准 / 自动批准 / 完全访问 / 只读」四档，其中「完全访问」是真实新增档位（迁移 [§101](../database/physical-design-postgresql.md#101-0112-本地目录完全访问档位2026-10-18-源码实现)），只放宽本目录内的文件写入（含删除不再逐次确认）；Git、CLI、浏览器、电脑控制与目录外动作仍按各自策略逐次确认。原「不提供完全访问」与「删除永远单独确认」是 2026-10-17 记录的历史取舍，本段取代其结论但不回写其理由；新的边界（按能力族划分：只放宽本目录 FILE_WRITE）只在工作台 §18.1.3/§18.1.4 与 HTTP §10.86 维护。

## 日期

2026-10-01。

2026-10-17 接续：用户已确认本地目录不应手工配置连接/策略，并要求更新产品文档和生成新任务书。基础文件配置改由应用管理、选目录默认只读、写档位三选一的产品规则已接受并于 2026-10-18 实施；具体规则只归[工作台 §18.1.4](../frontend/workbench-design.md#1814-本地目录权限设置2026-10-18已确认已实施)。本接续细化原权限预设，不改写历史实现成绩，不替代外部服务与特殊能力配置。

## 背景

用户反馈新建任务或打开对话步骤过多，希望像常见 Agent 一样打开文件夹即可工作。当前主协作页先选 Task，创建页要求预期结果、验收标准等信息；目录另在连接、受管资源与权限页配置。源码的 CreateAssistSession 已允许 projectId/taskId 为空，但这不证明无任务会话、目录上下文或真实执行链已端到端可用。

## 候选方案

| 方案 | 优点 | 代价 |
|---|---|---|
| 仅简化任务表单、增加快捷按钮 | 变更小，复用当前 Task 入口 | 用户仍须先建任务，目录配置仍分散 |
| 文件夹先行，对话中明确执行后再点「开始执行」 | 容易区分讨论和执行 | 每次明确请求仍需重复表达执行意图 |
| 文件夹先行，明确执行请求直接进入原执行用例 | 接近用户期望，可保留可靠执行边界 | 必须补目录关联、会话与执行关系、幂等及恢复，不能只改视觉入口 |

## 最终决策

2026-10-17 对本地文件配置的补充取舍：保留逐项手工配置会继续暴露内部能力/动作词表；删除 Gateway 或直接把目录路径当写许可会丢失现有准入与恢复约束。选择由 Application 将用户可见的目录/档位操作落实为原 Owner 管理的基础配置，高级页保留按需入口。代价是必须补齐配置来源、同根复用、幂等/撤销识别及旧设置兼容；不以隐藏表单而仍要求测试预置权限替代实施。

选择第三项。用户明确选择聊天里说「帮我修改这个功能」即可进入执行。工作目录映射到现有 Project/ManagedResource，数据库 Workspace 的语义不变；对话不强制绑定 Task，真正执行时由应用用例准备 Task/ExecutionContract 并调用原 Delegate。详细规则只在[工作台 §18](../frontend/workbench-design.md#18-文件夹入口与对话直接执行)维护，责任只在[领域模型 §12](../architecture/domain-model.md#12-文件夹入口与对话执行的应用边界)维护。

本决策保留原目标→项目状态→任务→执行→成果→验证/人工接受→业务提交闭环。对话改变工作入口，不取代目标与任务作为业务事实；已有 Goal 继承/对齐、Project State 写入及任务完成条件继续有效。

## 决策原因

用户开始工作时通常只有一个问题或一句请求，正式任务定义应在需要执行和追溯时形成。原始用户请求是授权来源，应用用例是授权校验与业务写入入口；模型可以整理请求，不能自行增加权限或扩大任务。纯讨论不创建占位任务，明确执行也不固定增加一次按钮确认。

## 代价

目录身份和项目关联需持久核对；一段对话可推进多项任务，不能把会话永久等同于一项 Task。执行请求需保留原消息、解释后的范围及命令回执；有歧义时需聚焦澄清。真实工具链缺口需要工程实现，快捷入口不能把现有 DRAFT/Mock 路径包装成文件修改能力。

## 影响范围

产品入口、React 导航/协作页、Windows 文件夹选择、Application、Project/Assist/Task/Workflow、权限与受管资源、API/数据库契约及恢复测试。既有技术栈、完成条件、动作审批和 UNKNOWN 规则保留。本轮文档修改 Breaking Change：No；后续 API/schema 变化及兼容策略必须按实际实现记录，不预定为 No。
