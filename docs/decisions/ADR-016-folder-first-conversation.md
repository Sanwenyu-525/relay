# ADR-016：文件夹入口与对话直接执行

## 状态

Accepted（产品入口、用户意图与复用既有业务 Owner 的原则）。具体 API、物理 schema、权限预设和事务锁顺序待实施时核定；尚未实现或验收。本轮用户只授权改文档及提供提示词。

## 日期

2026-10-01。

## 背景

用户反馈新建任务或打开对话步骤过多，希望像常见 Agent 一样打开文件夹即可工作。当前主协作页先选 Task，创建页要求预期结果、验收标准等信息；目录另在连接、受管资源与权限页配置。源码的 CreateAssistSession 已允许 projectId/taskId 为空，但这不证明无任务会话、目录上下文或真实执行链已端到端可用。

## 候选方案

| 方案 | 优点 | 代价 |
|---|---|---|
| 仅简化任务表单、增加快捷按钮 | 变更小，复用当前 Task 入口 | 用户仍须先建任务，目录配置仍分散 |
| 文件夹先行，对话中明确执行后再点「开始执行」 | 容易区分讨论和执行 | 每次明确请求仍需重复表达执行意图 |
| 文件夹先行，明确执行请求直接进入原执行用例 | 接近用户期望，可保留可靠执行边界 | 必须补目录关联、会话与执行关系、幂等及恢复，不能只改视觉入口 |

## 最终决策

选择第三项。用户明确选择聊天里说「帮我修改这个功能」即可进入执行。工作目录映射到现有 Project/ManagedResource，数据库 Workspace 的语义不变；对话不强制绑定 Task，真正执行时由应用用例准备 Task/ExecutionContract 并调用原 Delegate。详细规则只在[工作台 §18](../frontend/workbench-design.md#18-文件夹入口与对话直接执行)维护，责任只在[领域模型 §12](../architecture/domain-model.md#12-文件夹入口与对话执行的应用边界)维护。

本决策保留原目标→项目状态→任务→执行→成果→验证/人工接受→业务提交闭环。对话改变工作入口，不取代目标与任务作为业务事实；已有 Goal 继承/对齐、Project State 写入及任务完成条件继续有效。

## 决策原因

用户开始工作时通常只有一个问题或一句请求，正式任务定义应在需要执行和追溯时形成。原始用户请求是授权来源，应用用例是授权校验与业务写入入口；模型可以整理请求，不能自行增加权限或扩大任务。纯讨论不创建占位任务，明确执行也不固定增加一次按钮确认。

## 代价

目录身份和项目关联需持久核对；一段对话可推进多项任务，不能把会话永久等同于一项 Task。执行请求需保留原消息、解释后的范围及命令回执；有歧义时需聚焦澄清。真实工具链缺口需要工程实现，快捷入口不能把现有 DRAFT/Mock 路径包装成文件修改能力。

## 影响范围

产品入口、React 导航/协作页、Windows 文件夹选择、Application、Project/Assist/Task/Workflow、权限与受管资源、API/数据库契约及恢复测试。既有技术栈、完成条件、动作审批和 UNKNOWN 规则保留。本轮文档修改 Breaking Change：No；后续 API/schema 变化及兼容策略必须按实际实现记录，不预定为 No。
