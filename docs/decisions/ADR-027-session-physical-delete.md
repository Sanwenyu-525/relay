# ADR-027：会话物理删除及其保留边界

## 状态

Accepted，2026-10-18；2026-10-31 修订（阻断面按数据所有权重审、执行请求来源改脱钩凭据、删除路径补齐 0116 之后新建的账本）；2026-11-10 修订（用户决定删除优先：撤销全部业务阻断，外部对象保留、来源引用解除，迁移 0161）。只覆盖「用户显式删除一条会话」，不改变 Task、Run、Artifact、Review 的保留语义，也不开启项目、资料、连接或运行账本的物理删除。

## 背景与候选

用户要求危险操作可撤销，并在两轮澄清中裁定：会话既要「归档可撤销」，也要新增**真删除且不可撤销**；删除只给一个写明不可恢复的确认框，不给撤销条。

现状与冲突：

- 会话只有软归档 `assist_sessions.status = 'ARCHIVED'`，不删行、不删消息；反向命令 `reopenAssistSession` 四层齐全，界面里就是「已归档」分区的「重开这段讨论」。全库既有的物理删除只有学习记录的单条删除与全清。
- 应用角色对 `assist_sessions` 及其多数子表只有 `SELECT, INSERT, UPDATE`，没有任何 DELETE 授权；指向会话的外键全部是默认 `NO ACTION`，没有一条 `ON DELETE CASCADE`。
- 三条成文规则与新需求正面冲突：[契约 01](../../contracts/01-facts-and-ownership.md) A03「历史不删除」、[契约 03](../../contracts/03-verification-and-approval.md)「历史记录保留」「不抹去用户曾批准的历史事实」、[领域模型](../architecture/domain-model.md)「不造删除恢复语义」。

候选 A：不做删除，只保留归档。代价是归档区只增不减，用户无法真正移除敏感或废弃对话。

候选 B：新增 `DELETED` 软状态。代价是名字叫删除却不释放任何字节，还要新增一套「已删除但仍在」的可见性与唯一键规则；用户明确要的是不可恢复。

候选 C：物理删除会话自有的账本行；对被其它对象引用的会话**拒绝删除**并指向归档。

## 决策、理由与代价

采用 C。

**能删的只有会话自有账本**：消息、提案、附件（内容就是 `bytea`，随行消失）、生成中预览、会话工具调用、模型选择、自然语言状态维护请求与其变更、未进入组合检查的影响检查与候选、辅助模型调用账本、会话 diff 基线、会话行本身。删除在仓储层按「子 → 父」逐表显式写出，**不新增 `ON DELETE CASCADE`**：顺序可读、失败整条事务回滚，不让数据库替应用决定级联范围。`conversation_diff_baselines.session_id` 是没有外键的普通列，必须显式删，否则留下悬空账本。

**不能删的是被别的对象引用的事实。** 命令先查七类阻断，命中即整条拒绝、零删除，返回类型化 `SESSION_DELETE_BLOCKED` 与逐项阻止原因（下表是 2026-10-18 初版的理由；2026-10-31 按数据所有权重审后撤销了其中一项、收窄了另一项，见文末修订）：

1. `IN_FLIGHT` —— 仍有在途消息或运行中的执行链（复用既有守卫）。
2. `FORK_CHILDREN` —— 存在以本会话为来源的分叉会话；删除父行会让子会话的「从哪来」永久悬空。
3. `EXTERNAL_CITATIONS` —— Task 验收观察、项目假设、工作片段、项目蓝图把本会话的某条消息当作来源。这些是别的对象的历史依据。
4. `EXECUTION_REQUESTS` —— 本会话发起过执行请求。Task/Run 自身完整，但「这个任务从哪条消息来」属于跨对象来源。
5. `LEARNING_RECORDS` —— 本会话有学习记录；学习记录有自己的单条删除与全清入口，不能借删会话绕过。
6. `ARTIFACT_IMPACT_COMMITTED` —— 本会话的影响检查已进入组合检查；组合检查绑定 Task，属于 Task 事实。
7. `PROVIDER_COOLDOWN_ACTIVE` —— 本会话的模型调用仍在一个未到期的供应商冷却里；删掉这条证据会让下一次调用立刻重打一个刚要求等待的供应商。

**代价必须写明：**

- 被阻断的会话只能归档，不能物理删除。这是保留边界，不是实现遗漏。
- `activity_records` 只增不减且没有指向会话的外键；删除命令自身写一条审计记录，成为该会话存在过的唯一痕迹。
- 被删会话的模型调用账本（token 用量与费率）、学习依据、diff 基线与消息一并永久消失。**故意不提供恢复语义**：没有回收站、没有「取消删除」命令，误删或重启都无法找回。
- 归档与删除是两条通道：归档可能被撤销，删除不会。界面不得把两者合并成一个「移除」动作。

**幂等与并发**：沿用既有会话控制命令的形状——`command_id` + `expected_revision`、行锁、revision CAS、`runIdempotentCommand`。删除成功后行已不存在，重放不能靠「再读一次会话」判定，必须读回执账本：同 `command_id` 同载荷重放返回原回执，换载荷复用抛 `COMMAND_ID_REUSED`。

**权限**：新迁移逐表补 DELETE 授权，只改授权、不改表结构、不加级联。已有 DELETE 的表（学习记录、消息预览）不重复授予。

## 影响与后续

- 契约：[01 A03](../../contracts/01-facts-and-ownership.md) 登记会话删除为例外；[03](../../contracts/03-verification-and-approval.md) 在有效性表与「不抹去历史」段登记会话作用域账本可随删除不可达；[领域模型](../architecture/domain-model.md)在会话责任处写明删除故意不提供恢复。
- 协议与存储：HTTP 契约新增会话删除命令一节；数据库物理设计新增本次授权迁移一节；工作台 §28.1 记录菜单与确认框，设计系统 §6.4 记录不可逆操作不给撤销条。
- 本片不做：项目、资料、连接的物理删除；批量删除；回收站与恢复；删除后的匿名统计；`ON DELETE CASCADE` 改造。以后若要删被阻断的会话，须先解决对应来源的保留策略，不能从本授权扩张。

## 2026-10-31 修订：按数据所有权重审阻断面

起因：用户实际删除会话时大量失败，报错是「请求未能完成，请通过 request_id 在本机日志中核对」——即服务端 500，而不是业务阻断。核对下来有两类原因，都不是「这条讨论不该删」：

1. **删除路径落后于 schema。** 0116 按「会话自有账本 → 逐表显式删除」授予了当时全部子表的 DELETE，之后 0132（撤回基线、撤回请求、保护副本、撤销）、0146／0151（会话待办清单）、0148（子代理补充消息）又建了引用会话或消息的表，只授了 SELECT／INSERT／UPDATE。删到这些表就 permission denied；`assist_delegation_supplements` 的 NO ACTION 外键则直接撞外键。**删除路径必须跟着 schema 一起长**：迁移 0154 补齐这些表的 DELETE 授权，仓储层按「子 → 父」显式清理这一组账本。
2. **判定层与实现层互相矛盾。** `deleteSession()` 早就把 `memory_message_sources` / `memory_auto_captures` 当会话自有凭据清掉（0137 的决定），判定层却仍以 `MEMORY_SOURCES` 阻断——删得掉却先拒绝。

三项修订：

**一、撤销 `MEMORY_SOURCES` 阻断。** 来源绑定记的是「这条记忆从哪条消息的哪一段提出」，消息随会话消失后它已无法核对；它是会话自有凭据，随会话清理。长期记忆正文与版本（`memory_items` / `memory_versions`）**保留**，另有停用入口——删聊天不等于遗忘。

**二、`EXECUTION_REQUESTS` 收窄为 `EXECUTION_REQUESTS_IN_FLIGHT`。** 执行请求行同时引用会话与原用户消息，并承载「这个 Task 从哪条消息来」的授权来源。此前既不能删（那是跨对象事实）也不能置空外键，于是「发过一次执行请求，这段讨论就永远删不掉」。修订采用**受约束的最小 tombstone**（迁移 0154）：

- 去掉指向 `assist_sessions` / `assist_messages` 的两条外键，两列仍是普通 uuid 列——身份留着，完整性不再由数据库代管（与 `conversation_diff_baselines.session_id` 的既有口径一致）。
- 删除会话时把来源消息的**序号与正文摘要**、**脱钩时刻**写进请求行。摘要只能核对、不能还原正文；不复制正文、不复制会话标题——用户要求删除聊天，审计不该变成第二份保存。
- 语义变化只有一条，且是**失败关闭**：`source_detached_at` 非空表示来源聊天已删除，这条请求不能再被推进成新的 Task/Run（应用层 409 拒绝）。已经产生的 Task/Run 不受影响，它们本来就不依赖会话存活。

**三、删除路径补齐 0116 之后新建的账本**（迁移 0154 的授权部分）：0132 的撤回基线、逐文件条目、撤回请求、保护副本、撤销行；0146／0151 的会话待办快照、事件、轮次归属；0148 的子代理补充消息。这些都是会话自有的执行账本，不是被别的对象引用的外部事实。字节库（`assist_message_snapshot_blobs`）是内容寻址、跨会话共享的，这里只解引用、不删行，容量由它自己的保留清理负责。

**仍然阻断的场景**（各有明确的保留 Owner，不因为「让删除更好用」而放宽）：

| 阻断项 | 为什么仍然阻断 |
|---|---|
| `IN_FLIGHT`（在途消息） | 正在生成的那一轮既不该进历史，也不该被凭空抹掉（与归档共用同一道栅栏） |
| `FORK_CHILDREN` | 分叉子会话是独立讨论，各有自己的生命周期；父行删掉后「从哪来」会永久悬空。`SUBAGENT_CHILDREN` 已于 2026-11-10 撤销（见文末修订），子代理会话改为主会话级联 |
| `DELEGATION_LEDGER_REFERENCED` | 委派账本是父会话的执行史，清掉它等于替父会话抹掉一次委派发生过的事实 |
| `TASK_ACCEPTANCE_CITED` / `HYPOTHESIS_CITED` / `WORK_SEGMENT_CITED` / `BLUEPRINT_CITED` | 别的对象把本会话的消息当作来源，这些是它们的历史依据 |
| `LEARNING_RECORDS` | 学习记录是跨会话的用户知识，有自己的单条删除与全清入口，不能借删会话绕过 |
| `ARTIFACT_IMPACT_COMMITTED` | 影响检查已进入组合检查，组合检查绑定 Task，属于 Task 事实 |
| `PROVIDER_COOLDOWN_ACTIVE` | 删掉这条证据会让下一次调用立刻重打一个刚要求等待的供应商 |
| `MEMORY_COMPACTION_ACTIVE` | 整理正在进行，删掉会让这次整理的结果无处落地 |
| `EXECUTION_REQUESTS_IN_FLIGHT` | 这条执行请求还在解析中，是真正的在途执行 |

**代价与遗留**：

- 分叉关系与「单独删子代理会话」仍按保留边界阻断：父会话有分叉子会话不能删，子代理会话被父会话委派账本引用也不能单独删。~~子代理关系双向阻断、一棵委派树整体上暂时不可删除~~（2026-11-10 修订：主会话删除时子代理子树与委派账本整棵级联，见文末）。
- 执行请求的 tombstone 让请求行脱离会话存活：它是可查询、可审计的历史事实，但**不能再被推进**。回滚迁移（恢复两条外键）对已删过会话的库不成立。
- 0154 的 DELETE 授权只覆盖会话自有账本；`tasks`、`memory_items` 仍不可删（集成用例逐项断言）。
- 界面侧同步收口为「一次确认 + 四档结果」：已删／被引用阻断（配可执行动作）／明确失败／**结果未知**。结果未知这一档既不宣称成功也不宣称失败，按原 `command_id` 核对回执后再下结论——工作台 §28.1 有细则。

## 2026-11-01 补充：撤回反向引用的解除时机

独立验收发现 0154 的授权补齐仍漏了一枚外键：0132 给 `assist_messages` 加了 `withdrawn_by_recall_id REFERENCES assist_message_recalls (id)`（NO ACTION、非延迟），而 `finalizeRecall()` 是唯一写入方。删除路径按「子 → 父」先删撤回行、后删消息，于是**撤回结算过的会话一删就撞外键**，仍落成 500。

决定：**只在确定整条会话将被物理删除的那一版事务里**，清完撤回子表（逐文件条目、保护副本、撤销行）之后、删撤回行之前，按 `session_id` 解除本会话消息的 `withdrawn_by_recall_id`，随后消息与撤回行一并消失。

- 范围刻意收在 `session_id` 上，与既有的 `update assist_messages set goal_id = null where session_id = ...` 同一口径：撤回来源不承载独立事实，消息本身就是被删的那一批。若真出现跨会话的异常引用，它不会被这一步静默改掉，而是照旧以外键失败暴露——**不关外键检查、不吞数据库异常**。
- 换行、编辑、撤回与撤销路径都不允许做这一步：那些场合消息仍活着，改掉它等于抹掉「这条消息是被哪一次撤回撤掉的」历史。
- 回滚同样成立：事务中途失败时消息、撤回账本与这枚反向引用一行不少（集成用例在真实 PG 上注入失败点验证）。

界面侧同日修正：批量删除的「核对回执」核对到已删之后，必须按**确切 sessionId** 同时把该行从活跃投影、归档投影与勾选集里收掉——分组副本派生自这两份列表，跟着消失。仍核对不到的那条一行都不动；核对只读回执，不重发删除命令；全部核对到位时与「批量全删成功」同一终态（提示卡片自己收起）。确认卡片的设计与删除语义未变。

## 2026-11-10 修订：子代理会话随主会话级联

起因：用户在工作区里删除会话时，四条「子 Agent · 只读调查」始终删不掉，结果是「已删除 0 段，4 段未删除」。核对真实库：它们是 `parent_session_id` 非空的子代理会话，被父会话的 `assist_delegations.child_session_id` 与委派尝试的结论消息引用；反过来父会话又被 `SUBAGENT_CHILDREN` 挡住。两侧互相引用，整棵委派树谁都删不掉。这不是数据问题，是 2026-10-31 保留边界留下的死结。

重新按数据所有权判断：子代理会话是 `delegation` 命令在父会话里创建的只读执行体，不接收用户消息、不参与会话列表的业务语义，也没有独立的用户讨论生命周期；委派账本、尝试与补充消息记录的是**父会话**的一次执行史。把它们当成与父会话平级的独立讨论，才制造了「父子都不能删」的边界。

决定：

- **主会话删除时整棵级联。** 同一短事务内按「委派账本（尝试、补充消息、账本行）→ 更深层子会话 → 直接子会话 → 主会话」清理；仍不新增 `ON DELETE CASCADE`，仓储层显式写顺序，失败整条回滚。审计记录只增加 `fact_refs.deleted_subagent_sessions` 的身份列表，不复制子会话标题或正文。
- **单独删子会话仍拒绝。** `DELEGATION_LEDGER_REFERENCED` 保留：子会话被父会话账本引用时，删它等于让父会话的执行史失去结果落点；用户应从主会话删除整棵子树。左栏也不再列出子代理会话（入口归主会话的「子代理委派」面板），读侧与删除 Owner 对齐。
- **子会话自己的外部保留事实仍是硬阻断。** 子会话若带学习记录、Task 验收观察等引用，父会话级联整条拒绝并回滚，不为「清空」替别的对象删依据；在途消息同样挡住。
- **`SUBAGENT_CHILDREN` 撤销。** 它不再出现在 `SESSION_DELETE_BLOCKED` 的阻断项里；`FORK_CHILDREN` 不变（分叉是独立讨论，不是执行史）。

代价与遗留：删除主会话会一并移除所有子代理会话与委派账本，这是不可撤销的；界面在确认框里写明「委派子会话随所属主会话一起删除」。仍在执行的委派会以 `INVALID_TRANSITION` 挡住整条删除，等结束后重试。集成用例覆盖「父带子会话与委派账本整棵清理」与「子会话带学习记录时整条拒绝、一行不少」；组件用例覆盖左栏不列子代理会话与按目录清空。

（2026-11-10 后续修订已撤销「单独删子会话仍拒绝」与「子会话带学习记录整条拒绝」，见下一节。）

## 2026-11-10 修订：删除优先，外部引用解除（取代此前全部阻断项）

起因：用户明确「直接改成可以删除就好了，需要保留的不会轻易删除的」。删除是显式、不可撤销的用户动作；服务端不再替用户判断「这段讨论是否值得保留」，也不再因为别的对象引用了其中一条消息而把会话锁死。

决定：

- **撤销 `SESSION_DELETE_BLOCKED` 与 `listDeleteBlockers`。** 在途消息、分叉、委派账本反向引用、验收观察／假设／工作片段／蓝图引用、学习记录、已进组合检查的影响检查、供应商冷却、工作记忆整理、执行请求解析，全部不再挡住删除。
- **顺序改为「解除外部引用 → 删会话自有账本 → 删会话行」**，同一短事务、失败整条回滚。
- **外部对象保留，只解除来源指针**：
  - 分叉子会话保留，`forked_from_session_id` 置空并推进修订；
  - Task 验收观察、项目假设、工作片段置空 `source_message_id`；
  - 蓝图提案置空 `skill_message_id` 并写 `source_detached_at`（0161 放宽 SKILL 来源 CHECK 与冻结触发器，`origin` 仍为 `SKILL`）；
  - artifact 影响检查／候选置空 `assist_session_id` / `assist_message_id`（0161 允许 NULL 并补列级 UPDATE），候选组、已提交的组合检查全部保留；读取路径把来源已删的检查显示为稳定失败（`SOURCE_DELETED`），不再 404；
  - 单独删除子代理会话：父会话委派账本保留，`child_session_id`、尝试结论消息引用与补充消息已读指针置空；拿子会话消息当来源的补充消息整行删除；
  - 学习轮次、会话级记录开关与由该会话派生的学习证据随会话删除，知识点身份保留（证据 CHECK 要求来源消息与会话同时存在，不能只置空）。
- **在途消息可删。** 消息行消失后，Worker 的结算、预览与用量写入按原身份找不到行，不会复活会话；仍在进行的外部模型调用可能自然结束，但结果无处落库。这是删除在途会话的已知代价。
- **不变**：修订冲突、跨 Workspace 404、命令幂等与回执、审计只记身份与行数、删除不可恢复。

代价与遗留：

- 删除会话会让外部对象失去「从哪条消息来」的来源，但对象本身与其余事实保留；这是用户明确选择的取舍，不再提供「先解除引用再删除」的强制顺序。
- 0161 的列级 UPDATE 授权与两条可空列改变了解除引用所需的权限面；回滚（恢复 NOT NULL）只对没有置空过来源的库成立。
- 0161 放宽蓝图冻结触发器只放行「来源消息随会话删除」这一种变化，仍禁止改 origin/candidate/baseline/source/摘要，也不允许把来源重新指回消息。
