# ADR-029：长期记忆的自动候选提取（人工确认不变）

## 状态

Superseded by [ADR-030](ADR-030-zero-click-auto-memory.md)（2026-10-20 同日修订：用户指出「要人手动确认感觉很麻烦」，确认环节取消；本文的候选表与「候选不是记忆」边界作为历史保留）。

## 日期

2026-10-20。

## 背景

用户指出「长期记忆应该是自动保存有价值的内容而不是手动」。当前实现是纯手动：只有用户在某条已完成消息上点「保存为长期记忆」才产生 Memory（HTTP §10.99、工作台 §40）。

手动路径的真实问题不是操作繁琐，而是**人不会去点**：有价值的约定散落在几十轮对话里，等想起来时已经找不到那条消息。因此「发现值得记住的内容」这一步应当自动化。

但 [ADR-028](ADR-028-memory-layers.md) 的候选方案 2 曾明确排除「从聊天自动提取并确认事实」，理由是把模型推断变成长期事实、违背人工确认边界。本次用户在这三个落点中选择了「自动提取候选 + 一次确认」，即：**自动化只发生在「发现」，不发生在「确认」**。

## 候选方案

1. **自动提取候选 + 一次确认（采纳）**：轮次结算后模型提取 1–3 条候选进入待确认区；用户点确认才生成 Memory，忽略则不再对同一来源重复提议。代价是每轮一次额外模型调用与候选噪音；换来「人不用主动找」，且长期事实仍由人签字。
2. **自动存为「未确认记忆」，可直接召回**：零点击，召回时标注未确认。需新增状态与召回过滤，错误推断会进入模型上下文，只能靠标注与来源追溯兜底。
3. **全自动保存并视为已确认**：与 `confirmed_by`／不可变版本／召回语义直接冲突，需改契约、迁移与验收标准，未采纳。

## 决策

采用方案 1。要点：

- **候选不是记忆**。候选表与 Memory 分离，不参与召回、不进入模型上下文、不计入来源；只有 `ACCEPTED` 时产生的 Memory 才按既有规则召回。Memory 的唯一写入 Owner 仍是 Information。
- **提取时机**：普通 AGENT 会话一轮生成 `COMPLETED` 并完成结算之后，按 assistant message 幂等，每轮最多触发一次、最多 3 条候选；会话 `remember=false`（一次性模式）不提取。
- **输入边界**：只送这一轮的用户原文与助手正文（有上限），不重发全历史；不读取工具正文以外的新来源，不扩大权限。
- **确认即来源**：接受时候选携带 `(session_id, message_id, content_sha256)` 冻结来源，正文可编辑但 hash 仍取**原消息**；范围仍只能是全局或原会话 Project。忽略是终态，同一 `(session_id, message_id, 归一化正文)` 不再重复提议。
- **失败不打扰主流程**：提取使用会话冻结模型并走既有 `model_calls` 计量；超时、非法 JSON、预算不足、Worker 丢失一律**静默放弃这一轮**，不写候选、不改聊天正文、不重试、不换模型，主回复照常完成。
- **可关闭**：Workspace 设置新增独立开关（与「自动使用记忆」「自动整理」并列），关闭后不再提取；已存在的候选仍可确认或忽略。

## 代价与限制

- 每轮一次额外模型调用，成本随对话轮次线性增长；用「每轮最多一次 + 最多 3 条 + 输入上限」约束，但不做语义去重（不引入向量库），因此仍可能出现措辞不同、实质重复的候选。
- 候选质量取决于模型，抽取可能漏掉真正重要的约定，也可能提出琐碎事实。产品上不能宣称「已记住全部要点」。
- 候选会短暂占用界面空间；忽略机制必须真的能止住重复提议，否则会变成噪音源。
- 接受仍是人工动作，因此「没人点」只被缓解、未被消除；这属于方案 1 的自觉取舍。

## 影响与后续

- 数据库新增候选表（新 migration，不改已应用迁移）；API 新增候选列表／接受／忽略三条端点；Assist 主流程增加结算后的提取分支；设置增加一个开关；前端增加待确认区（复用保存弹层的来源与范围校验）。
- **不改** ADR-028 的召回规则、确认语义、短期窗口与压缩边界；本 ADR 只把「发现」自动化。
- 实现工作包见 `prompts/auto-memory-candidates.md`；真实 Provider 的提取质量与成本必须单独取证，不能用 Fake 模型证据代替。
