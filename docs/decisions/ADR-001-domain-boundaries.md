# ADR-001：领域独立写入，应用层协调跨聚合事务

## 状态与日期

Proposed，2026-09-19。尚未确认为 Accepted；不记录为已有实现。

## 背景

Task 完成必须同时核对 Run 执行权、验证依据、控制意图与外部动作，再更新必要 Project State。把全部对象放进 Project 聚合会放大加载和并发范围；完全独立提交又可能出现 Task 已完成而 Run 或关键 State 未同步。

## 候选方案

| 方案 | 优点 | 代价 |
|---|---|---|
| Project 包含所有 Task、Run、产物的大聚合 | 单入口直观 | 历史持续膨胀，锁范围过大，职责混合 |
| 独立领域模块，各自提交并靠事件最终补齐 | 有利于独立部署 | 引入补偿、中间状态与恢复复杂度，不适合当前单机闭环 |
| 独立聚合，应用层在单数据库中协调必要短事务 | 事实归属清楚，关键业务状态原子一致 | 依赖统一事务基础设施，未来拆服务需重设计 |

## 推荐决策

采用第三种。各模块公开写入口保护自身规则；应用层组合入口并控制事务。Repository 不跨模块暴露，不允许参与模块提前独立提交。读投影可跨模块查询。外部调用、内容保存和人工等待不进入数据库事务。

## 原因与代价

契合单用户、同机、模块化单体的范围，使执行权、控制请求和完成提交能够以数据库事实裁决竞争。代价是跨模块用例必须明确锁顺序、幂等与并发测试，不能宣称各模块可直接独立部署。

数据库原子性只覆盖数据库。文件与外部副作用仍按 Gateway 意图、不可变产物及恢复契约处理，不用本决策掩盖分布式副作用问题。

## 影响与后续

影响后端应用层、领域入口、数据库 Repository 和恢复测试；不指定框架版本或具体 API。详细责任见[领域模型](../architecture/domain-model.md)，业务约束见[恢复与提交](../../contracts/04-recovery-and-commit.md)。

原始规范与数据库选择到位后复核并决定是否接受。未来如需多进程或远程执行，先核验现有隔离与事务前提；若需独立数据库，另建替代 ADR，不能直接把内部调用替换为异步消息并保留原子性承诺。
