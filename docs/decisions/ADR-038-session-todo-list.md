# ADR-038 会话级待办清单（todo_write）

- 状态：Accepted
- 日期：2026-10-30（2026-10-30 补充工作轮次归属、调用身份幂等与版本基线）
- 相关：ADR-018（Assist 会话）、ADR-022（Agent 主循环）、ADR-031（会话直写）

## 背景

长任务在会话里跑时，用户看不到“现在做到哪一步”，模型下一轮也容易丢掉方向；上下文压缩与
进程重启之后，“上一版清单”只能从历史消息里猜。需要一个会话级的待办清单：可写入、可恢复、
界面与模型读同一份事实。

## 决定

1. **归属在工作轮次，不在 Session 也不在项目。** 一条用户消息开启一个工作轮次，作用域键为
   `turn:<message_id>`；没有用户消息（自动化入口、测试通道）时回落到 `session`。同一会话里
   任务 A 收尾后用户再提一件独立任务 B，B 是新的轮次，**不继承** A 的清单。
2. **唯一写入口是模型侧的 `todo_write`。** 界面只读，不提供本地勾选；它不创建 Run、不改变
   Task / Run / Verification 的任何完成事实，也不重启已停止的任务。
3. **一次写入 = 一条版本化事件 + 行快照，同一事务提交。**
   `assist_session_todo_events` 只用于恢复、审计与幂等核对；`assist_session_todo_snapshots`
   一会话一行，是 UI 与模型唯一读取的投影，只代表**当前**轮次。
4. **幂等按原调用身份判定，不按内容、也不只看最新快照。** 身份是
   `(session_id, tool_call_id)`；历史调用在快照推进之后被重放，返回它当初写下的那一版，
   不递增版本、不再写事件。同一调用 ID 换一份载荷是身份伪造：`TODO_TOOL_CALL_CONFLICT`
   明确拒绝。这也覆盖“快照已提交、`session_tool_calls` 未结算就退出”的故障窗口：恢复时
   重新结算同一条 `REQUESTED` 行，结果与当初一致。
5. **版本 CAS 与基线。** 首次写入的基线是 0（`expected_version` 可省略或写 0）；已有快照时
   必须带上读到的版本号，缺失拒绝（`TODO_VERSION_REQUIRED`），不一致拒绝
   （`TODO_VERSION_CONFLICT` 并告知当前版本）。写入成功版本 +1，事件表
   `(session_id, scope_key, version)` 唯一，并发抢同一版时只有一版落地。
6. **读取按可见性收口。** `GET /assist-sessions/:id/todos` 先过 `readAssistSession()`：跨
   Workspace 或不存在的会话与其它 Assist 读取同一口径（404），不因为它是独立投影就绕开会话
   可见性。
7. **上下文注入读当前轮次的权威快照。** 每次真实模型调用前按消息重读；压缩、checkpoint 恢复、
   进程重启后读到的是同一份，不从历史消息重建。长清单注入只列进行中项、未完成项与最近一条
   完成锚点，其余折叠成摘要。
8. **条目身份尽量稳定。** 模型可以带回 `id`；不带时先按内容对齐，再按相似度（唯一最佳匹配且
   达标）认作同一项的改名。**不按列表位置认身份**——重排时位置会变。
9. **并行上限只有一个配置入口。** `assist_sessions.todo_parallel_limit`（1–8，默认 1）。
   原先未接线的环境变量入口已删除，不留下看起来能配、实际不生效的开关。

## 后果

- 同一会话的多个工作轮次各自有进度，新任务不会被旧清单误导；代价是跨轮次的长任务需要模型
  在新轮次重新声明一次清单。
- 快照只保留当前轮次，历史轮次的进度可查事件表但不能当作当前清单读取。
- `todo_write` 没有 Gateway Operation，0060 的“SETTLED 必须有 Operation”约束对它单独放开。
## 第三轮补充（2026-10-30）：轮次顺序、工作连续性与请求摘要

第一轮把清单按工作轮次归属，但快照行只要 `scope_key` 不同就允许覆盖：上一轮的迟到写入
会把当前轮次的投影换掉。第三轮用三条可验证的事实关掉这个口子。

1. **轮次顺序（`scope_seq`）。** 快照与事件都记下开启该轮次的用户消息 `seq`。快照 UPSERT 的
   更新条件是 `(scope_seq, version)` 行比较：旧轮次的写入一律比不上新轮次。写入前还会先
   比较一次顺序，旧轮次提交直接返回 `TODO_SCOPE_STALE`，不静默丢弃、也不改写当前投影。
   历史调用按原身份重放仍返回它当初那一版（`IDEMPOTENT`），但不动当前快照。
2. **工作连续性。** 「继续」「补充」「这里不对」不是新任务。规则只有一条：只有最新一轮做
   延续判断——上一轮清单仍有 `pending`/`in_progress` 项时，新一条用户消息延续同一作用域，
   版本继续递增；清单已全部收尾时才是新作用域，版本从 1 重计。历史轮次的写入不适用
   延续（否则它们会借着延续写进当前轮次），用户写 `新任务：` 或 `/newtask` 前缀时强制开新
   作用域。这条规则不依赖模型自述，也不靠每条消息无条件重置。
3. **规范化请求摘要。** 事件里存 `request_digest`：基线版本 + 每条的自带 id + 内容 + 状态。
   同身份重放要摘要逐字相同；只改状态、只改基线版本、或换一个条目 id 都算异载荷，返
   `TODO_TOOL_CALL_CONFLICT`。`null` 的历史事件（0150 之前）回退到 `(content, status)` 序列
   逐条比较：条目 id 是服务端为前端稳定 key 维护的内部身份，原始请求没带 id、服务端规范化
   时补了 id 的那批调用，原样重放不因新增列被误判成异载荷（2026-10-30 执行链整改）。
4. **结算不当成完成。** `settleTodoWrite` 返回 false 时先回读账本：已 `SETTLED` 且摘要相同
   才算幂等成功，否则重试一次；仍不行就抛 `TodoSettlementIncomplete`，行留在 `REQUESTED`。
   恢复路径是具体的：每次生成 tick 在租约清扫之后跑 `reconcileTodoWriteSettlements`
   （2026-10-30 执行链整改），按原调用身份核对——事件表里已有该调用的走幂等重放并补结算，
   不新增事件、不递增版本；事件表里查无此调用说明写入事务从未提交，保持 `REQUESTED`
   可诊断，不重新执行、不伪造结算成功。清单已 durable，不因账本没结算而回滚。
5. **普通 Agent 的主循环。** 主循环的进入条件原来只看「有没有外部只读工具」，于是没有任何
   连接的会话落到单次生成路径，模型根本拿不到 `todo_write`。现在「可以维护待办」也是进
   主流程的理由；它不授予任何外部能力。

## 第五轮补充（2026-10-31）：工作身份冻结（迁移 0151）

第三轮的连续性判定在**写入时现算**，实测留下两个真实缺陷：

1. **插话静默切换作用域。** 插话消息 seq 更大，会改变「最新一轮」的判定：同一轮里
   插话前的写入延续旧作用域、插话后的写入却落进它自己的 turn 键——一次生成中途
   清单身份被静默换掉（TL-31 复现）。
2. **恢复重算误判归属。** 崩溃后重算 `resolveScopeKey` 时，延续轮次的调用会被判回
   它自己的 turn 键，即使更晚的用户消息延续的是同一份工作。

决定：

- 新表 `assist_session_todo_turn_scopes`（会话 × 用户消息一行，迁移 0151）：
  `scope_key` 是这一轮归属的工作作用域，`basis` 记录判定依据——
  `OPENED`（开启自己的作用域）/ `CONTINUED_UNFINISHED`（延续未完成清单）/
  `FORCED_NEW_PREFIX`（用户写明「新任务：」或 /newtask）。
- **归属在首次判定时冻结**，读写共用同一份：上下文注入、写入、界面读取走同一归属；
  此后重启、插话、迟到写入都不重算。判定依据只来自服务端事实（用户消息原文、当前
  快照完成态、轮次顺序）——模型写入不改变归属，不能靠猜静默切换。
- 并发首次判定用 `on conflict do nothing` + 回读：先到者定案，同一轮次只有一个归属，
  不随观察顺序漂移。
- 历史回填只补「作用域开启轮次」这个可从 `scope_key` 直接还原的事实；延续归属无法
  从存量数据重建，留给未来首次判定现算。历史重放不受影响（走事件表，不依赖归属行）。
- 事件、快照、CAS、`scope_seq` 的语义全部不变：`scope_seq` 仍取**作用域开启消息**的
  seq，快照行依旧是唯一当前投影，轮次顺序闸门照旧拦截旧轮次写入。
