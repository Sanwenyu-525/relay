# 成熟项目参考与复用策略

日期：2026-09-19。用户已明确：研究成熟项目的设计与经验，但不要求复制源码或引入其框架；语言只是实现方式。技术栈以延迟、吞吐、内存表现为优先，当前推荐 TypeScript-first，Rust 保留研究对照。具体依赖与集成方式仍待验证，见 [ADR-006](../decisions/ADR-006-typescript-first.md)。决策状态见 [ADR-005](../decisions/ADR-005-reuse-first.md)。

## 1. 本次方向调整

此前设计先定义业务契约，再计划自行实现 Runtime、恢复器和工具适配；这容易忽略已有经验。本次改为：业务约束作为验收标准，先研究已有设计，然后判断采用成熟库、协议集成或按本项目边界实现。机制借鉴本身是有效成果，不以依赖数量或复用代码行数评价。

产品目标、三种工作模式和验证闭环保留。Java 不再是固定前提；优先验证 TypeScript API/Worker 共用业务代码，原 Rust 与跨语言方案保留比较依据。避免机械翻译框架，也不为接入参考项目而增加辅助进程、数据库和状态机。

## 3. 如何借鉴与复用

按模块选择以下方式，先记录问题与设计依据，不能把“参考过 README”称为完成源码研究：

1. 直接依赖库：适合模型客户端、解析、工具定义等通用能力；通过实际兼容测试后锁版本。
2. 通过官方协议/SDK 集成：适合已有完整 harness；本项目保存业务身份与执行引用，并显式适配事件、取消、审批及恢复。
3. 借鉴机制后实现：语言无关地吸收事件边界、状态推进、工具准入、恢复等设计；可以是首选，而非只有无法直接复用才允许。说明原机制解决的问题、本项目保留/改变了什么，避免重新探索已知陷阱，也避免移植不需要的复杂性。
4. 有限源码改编或 fork：仅在扩展点不足、必要改动明确时考虑；记录上游 commit、具体文件、许可证/NOTICE、修改与升级策略。不是默认开工方式。

## 4. 业务边界与技术机制

| 责任 | 复用原则 | 本项目仍要验证的事实 |
|---|---|---|
| 模型请求、流式事件、工具调用循环 | 优先现成 SDK/harness；不重写通用 Agent 平台 | 实际输入来源、调用身份、成本未知情况及取消结果 |
| 调度、checkpoint、恢复 | 比较现成 runtime；不预设自行开发引擎 | 每项状态有唯一 Owner；重复恢复不重复业务效果 |
| Context | 复用消息、token 和检索基础能力 | 必需验收/规则、来源版本与裁剪证据由产品契约决定 |
| Tool Gateway | 复用工具执行与集成能力，保留必要准入适配 | 实际工具不可绕过权限；UNKNOWN 未核对不能换执行器重发 |
| Verification | 复用测试工具、schema/checker 和评测组件 | 明确验收、独立证据、确切产物版本；模型说完成不等于 PASS |
| Project/Task/State、Handoff、Workbench | 实现本项目业务，通用存储/UI 仍可复用 | HUMAN/AI 执行权、完成凭据、状态写入权和历史追溯 |

若引入外部执行端，产品 Run 与 harness session/thread/turn 必须明确关联，不假定一一同义。执行端事件保留其来源和身份，重复事件先去重；外部完成仅表示执行结果待验证。产品事实写入仍经应用用例，执行端不能直写业务表。

框架 checkpoint 与本项目业务完成事务通常不共享原子提交，即便同用 PostgreSQL 也不能据此假定同一事务。PoC 必须覆盖一边已提交、另一边丢响应的恢复。不把同一内部游标同时交给自研恢复器和框架推进；若现有 Run/Step/Attempt 表与框架重叠，应先修订物理设计再生成 migration。

工具有两种可验证接入方式：所有动作进入本项目 Gateway；或选定 harness 能落实等效准入并提供核对证据。不具备这两种能力时，只能限定在无真实写副作用的研究环境，不能用一个外围 wrapper 宣称已满足权限契约。

## 5. 开工前研究与最小验证

P00 分为研究/验证与工程搭建两段，不增加一套平行任务编号。当前源码证据与机制采用表见[研究记录](../research/p00-source-study.md)：

- 对上述五项做定向源码阅读，固定 tag/commit，记录实际模块路径、测试入口、已知限制与许可证；不复制整仓进业务源码，不把第三方 AGENTS 当本项目指令。
- 在已有研究上补 TypeScript + AI SDK Core 的审批恢复、UNKNOWN 和 Provider Spike，规范见测试计划。按需研究 AI SDK/Kysely 等源码并锁版本；先比较责任与运行成本，不重跑无关实验。不要为了证明“复用”强行引入框架。
- 用最小 PoC 验证关键假设：固定输入 → Fake 或可控模型 → 受控工具 → 产物 → 验收 → 人工等待/恢复。若测试框架本身，必须使用真实框架；若测试借鉴后的设计，要明确哪些是本项目实现。性能对照区分持久化、流式和模型等待成本，不强行用不等价测试排名。
- 验证重复/迟到事件、审批后参数变化、中断后续接、外部成功但回执丢失，以及业务完成前后崩溃。检查点恢复成功不能掩盖重复副作用。
- 交付一张采用表：需求 → 上游文件/机制 → 复用方式 → 本项目适配/自研差异 → 证据。无法复用的部分给出具体原因；无凭据项标未验证，不伪造实测。

通过后，更新技术选型、部署边界和所影响的 schema/契约，才进入 P00 工程搭建及 P01。P05/P08/P09/P12 执行已验证的分工，不重新从头编写一套 Agent 基础设施。

## 6. 论文与来源记录

实现和论文区分四类贡献：上游能力、集成适配、业务设计、实验验证。参考机制引用原项目及版本；采用代码遵守相应许可。不能把集成数量或现成框架功能写成本项目原创。研究贡献仍需围绕可验证的问题与对照实验确定。
