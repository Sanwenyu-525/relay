# V1 之后的长期项目协作路线

角色：后续增量的范围、优先级、依赖和未决问题的唯一主表。初稿：2026-09-28；规划更新：2026-10-11。状态：**规划 Draft / 具体协议 Proposed**。用户已选择长期项目协作主线，并在本次逐题访谈中确认下文标明的首轮产品范围与默认行为；其余候选和工程协议仍待分包核定。本次规划同步不构成新增开发授权或发布承诺，也不否定既有切片实现。

当前实现与验收只看 [CODEX_NEXT_STEP](../../CODEX_NEXT_STEP.md)。本路线不延长 [M01–M07](../../prompts/stack-migration.md) 的目标，不将其未完成项移到下一版，不启动 goal、模型、通知或定时任务。原始远期目录见[产品总纲第 106–108 节](../../Personal_Workflow_OS_Master_Spec.md#106-v15)，本页细化其推荐实施次序，未选择的候选仍保留。

## 1. 要解决的问题与完成图景

让用户隔几天回来仍能知道项目的真实进展、判断新成果、保护自己的修改、复用已有知识，并在明确授权的短任务链内让 AI 继续推进。第一目标是减少重新理解和重复交代的成本；功能数量与自动运行时长不作成功指标。

推荐黄金路径：离开前保存接续点 → 返回后比较事实变化 → 选择需要处理的成果和问题 → 修改后看到相关影响 → 审核并收录可复用知识 → 确认下一段计划 → 在有限授权下执行 → 遇到决定或停止条件回到人工待处理。

比较的方向：

| 方向 | 收益 | 代价与本次选择 |
|---|---|---|
| 长期协作优先 | 直接连接已有 Project/Artifact/Knowledge/Review，先验证日常价值 | 涉及来源、版本和人的理解，不能只做摘要页面；用户已选择该主线 |
| 开发执行器优先 | 扩展编码任务的执行深度 | 外部回执、审批穿透与故障核对成本高；保留为后续可选分支 |
| 自定义平台优先 | 允许不同项目配置自己的工作方式 | 编辑器和兼容性会先增加产品复杂度；放到真实重复需求出现之后 |

## 2. 基线与增量的分界

2026-09-28 的源码定向核对只证明存在复用入口，不代表它们已独立验收；开工时必须重新核对确切基准。

| 已有入口 | 后续增量 | 不重复建设 |
|---|---|---|
| 项目恢复 Skill、Activity/Trace、`application/state-queries.ts` | 明确保存的接续基线、跨时间比较与接续点 | 不再生成第二套 Project State |
| `application/lineage-queries.ts`、`artifact-impact-checks.ts`、`artifact-text-locks.ts` | 跨成果的有限批次提案、冲突重算与组合证据 | 不把直接引用 `complete: false` 冒充完整影响图，不重做 V1 原文锁定和手动检查 |
| `application/information-commands.ts`、知识阅读与显式收录 | 人工知识编排、带来源的整理候选、重复与过期提示 | 不把收录、验证、模型外发合成一个开关 |
| Today/Focus、Task 提案、蓝图与验收方案 Skill | 周期计划草案、可解释的重排和容量提醒 | 不重建任务列表或任务状态机 |
| `application/attention-notifications.ts`、持久 Run command/outbox | 用户启用的特定时间/事件请求、有限连续委托 | V1 必须介入提醒继续按既有规则；提醒不是调度器 |
| Skill/Pack 固定版本与 Profile、来源视图 | 用户可编辑的受限声明、差异审查、版本 Eval | 不创建第二套 Runtime 或动态代码插件 |

相对代码路径以上均位于 `apps/api/src/`。工作台继续消费现有 API；没有对应写命令的编辑入口必须先设计契约，不从 UI 直接写数据库。

## 3. 推荐分期与依赖

“V1.1”是本次建议的协作打磨批次标签，不是已有发布版本；V1.5 沿用既有远期方向。N 编号用于后续工作包，不替换 M/P 编号，不代表已经开工。不设无依据的日历工期；N00 基线和每包设计评审后再估算实现、反例修复和桌面验收工作量。

| 工作包 | 建议批次 / 优先级 | 用户得到什么 | 最小新增范围 | 依赖 |
|---|---|---|---|---|
| N00 使用基线与体验收口 | V1.1 / 首先 | 能发现最费时、最易误判的真实步骤 | 固定任务集、延迟/成本/返工记录、瓶颈定向修复；本机可查看记录 | M01–M07 必需出口通过 |
| N01 项目接续与检查点 | V1.1 / 核心 | 看到可追溯的项目变化，并找到依据 | 首片手动命名点/查看/比较；日常上次查看基线与返回轻量核对为后续增量（2026-10-09） | N00 |
| N02 跨成果共创 | V1.1 / 核心 | 一次审阅同一来源变化带来的多个候选修改 | 有范围的候选组、逐项差异/选择/冲突，逐项新版本及组合验收入口 | N01；V1 锁定/影响功能通过验收 |
| N03 项目知识整理 | V1.1 / 核心 | 把成果和经验组织成可读、可核对的项目知识 | 手动导读编排、候选收录/归类、相似候选与来源更新提醒 | N01；复用 V1 知识读写 |
| N04 周期计划与重排建议 | V1.5 / 核心 | 根据目标、依赖和用户容量得到可接受的下一段计划 | 手动发起下一段工作计划、输入本次可用时长、解释变更、逐项接受、过期重算 | N01、N03；N02 有结果时作为输入 |
| N05 有限触发与提醒控制 | V1.5 / 条件进入 | 在指定时刻提醒继续项目，主动发起下一段计划 | 一次性时间提醒、持久去重、暂停/禁用、错过后最多补同一条待处理 | N04；时间/时区和持久请求协议核定 |
| N06 有限连续委托 | V1.5 / 条件进入 | 已确认任务链可在预算内继续，必要时交回人 | 单项目、显式任务集合、串行自动 Delegate、停止条件和进度依据 | N04、N05；执行授权方案确认 |
| N07 声明式个人配置 | V1.5 / 可选 | 把已反复使用的协作方式保存为配置 | 先编辑有限 Skill/Profile 参数及本地 Pack 组合，预览、固定版本与 Eval | N03、N04 的实际重复使用证据；不依赖 N06 |

2026-10-02 规划接续：用户确认 N01 之后优先交付 N02 成果联动，随后推进 N03 知识整理。N02 与 N03 仍互不依赖，可以分别开发；这一选择确定交付优先级，不新增硬依赖，也不自动要求并行 Agent。N04 继续依赖 N03；N05、N06 必须单独验收，不因计划建议效果好就同时放行。N07 不阻塞主线。

### N00 使用基线与体验收口

2026-10-02 规划接续：用户确认首个真实交付与验收样板采用小型开发项目，完整路径为「打开目录 → 对话提出修改 → 真实改文件并检查 → 审阅成果 → 隔日继续」。据此先检验真实执行、成果判断与接续的使用收益；其余两种固定路径仍保留。此选择仅确定规划优先级，不扩大实施或真实模型外发授权。

该样板的有效测量依赖[文件夹入口](../frontend/workbench-design.md#18-文件夹入口与对话直接执行)相应切片和 M06 真实工具链出口；文件夹入口不作为 N00/N01 所有切片的新硬依赖。测量准备与 N01 既有首片核对可独立推进，不重建已有实现。实际实现与验收范围继续以当前阶段入口及功能验收表为准。

- 固定三种真实路径：隔日接续项目、修改一个被引用成果、把确定成果收录并再次用于任务。记录项目规模、输入版本、模型配置、权限、运行基准和失败样本。
- 区分 UI 受理反馈、排队到领取、首个可见内容、最终产物持久化、人工审阅、总完成时间；不将 Mock 时延当真实模型时延。
- 新增观测优先复用当前 Trace/模型调用记录；只保存必要结构化时间和引用，不默认采集正文、屏幕、全局行为或上传遥测。定位确切瓶颈后才改性能。
- 出口是可重跑基线和优先问题清单。V1 必需验收缺陷仍回原模块关闭，不借 N00 放宽 V1 出口。

### N01 项目接续与检查点

- 用户显式保存名称与可选接续说明；系统捕获一致的 Project/Task/当前选用成果、Decision/Rule/Knowledge 版本引用及未决事项。精确纳入集合、大小上限、保留/删除策略在设计中冻结。
- 返回时选择该点与当前事实比较；事实差异和 AI 解读分开，摘要中的判断能跳到来源。未读、已查看、已接手、已完成不能共用一个状态。
- 隔日打开目录的默认呈现已于 2026-10-02 确认，规则只在[工作台 §15.1](../frontend/workbench-design.md#151-隔日打开目录的事实接续卡2026-10-02已确认规划)维护；该呈现增量不扩展已冻结的接续点引用集合，也不等于已实现或验收。
- 默认不因打开项目改变接续基线；活动 Run 可以在一致性快照后继续，UI 说明这是捕获时点而非“项目已停机”。缺失或失权的来源明确不可用。
- 首片仅保存/查看/比较。根据旧点生成恢复配置建议是单独可选片，走当前 revision 的提案；不能回滚整库、文件效果、审批、PASS 或执行权。

2026-10-09 接续：日常返回的默认查看基线及获授权核对归[工作台 §18.9](../frontend/workbench-design.md#189-自然语言状态维护与接续摘要)，上述“不改变基线/仅查看比较”继续限定命名接续点与已冻结首片。新日常增量须核定查看确认、版本集合、核对权限/预算及停止恢复协议后另行实施；不扩展现有首片成绩，不增加后台自动快照或自动 Resume。

### N02 跨成果共创

2026-10-02 用户确认首场景采用已明确关联的 Markdown 项目文档：功能/API 说明变化后，为相关使用说明、设计说明或测试计划提出修改候选。真实代码修改和检查仍由原执行链完成；从代码差异推断文件/测试依赖不纳入本首场景，须另行设计与验证识别范围和漏检。

- 用户主动从确切前后版本发起影响检查；沿已登记关系形成有界候选组，推测关系另列。图有截断、环或未知影响时显示范围和缺口。
- 逐项展示源变化、目标基线、锁定区域、拟改内容与需要重验的条件；用户可选取独立条目。对存在依赖的候选必须明确联动或拒绝不完整选择。
- 最小片采用逐项命令与逐项回执，明确部分成功；不承诺跨多个成果全有或全无。批次只是候选和处理结果的关联，不持有另一套成果正文。
- 人工编辑、锁定变化或来源更新后，受影响候选过期；不能以新正文悄悄重算后沿用旧批准。组合版本检查单列，不把多个单项 PASS 相加当整体 PASS。

### N03 项目知识整理

2026-10-02 用户确认首个交付形态为项目知识导读，按架构约定、重要决定、使用说明和参考资料组织来源入口。人工编排与来源呈现规则归[工作台 §12.4](../frontend/workbench-design.md#124-项目知识导读n03-形态2026-10-02规划已确认前后端均已接入)；开发经验卡保留为后续候选，不纳入首轮。

- 先提供可人工编辑的导读/集合：链接目标、决定、资料与确切成果版本，不复制第二份正文或当前状态。历史固定引用和跟随当前的导航用途必须能辨认，AI 输入始终落到确切版本。
- 用户主动请求整理；AI 产生“收录哪些、归什么类、与已有内容有什么关系”的候选。已有收录命令与新笔记版本继续复用。
- 2026-10-09 的明确收录指令可承载对应确认，沿[工作台 §18.9](../frontend/workbench-design.md#189-自然语言状态维护与接续摘要)处理；自动提炼仍只形成候选。统一对话入口不重做首片导读，也不由知识内容静默升级 Rule/Decision。
- 发现相似条目只提示，不自动合并/删除；新总结是有来源的新版本，不能凭模型意见覆盖 Rule 或 Decision。资料失效提示不自动改写历史引用。
- PDF 作为可选下一片：先根据用户真实资料样本决定正文提取、页码定位、表格和扫描件范围；OCR/Office/语义检索不一起承诺。引入解析库前再核对正式版本、许可、资源限额与可信边界。

### N04 周期计划与重排建议

2026-10-14 基础前后端片核定结构化估时、固定容量与逐项应用协议（HTTP 契约 §10.74、数据库设计 §82）：用户手动输入，保守串行建议，诊断接受独立建 Task；自然语言入口、完整重排、UI 和实用收益后置。以下保留目标规格，其中工程协议待核定的历史描述已由本片协议接续，当前阶段与成绩仍归原主文档。

- 2026-10-02 用户确认首轮采用手动发起的「下一段工作」计划：用户填写本次可用时长，结合选定目标、当前任务依赖与必须介入事项，形成一段可审阅的小计划。估时为建议并可改，不根据聊天或操作习惯自动画像；一周计划保留为后续候选。
- 输出候选任务、顺序、延后原因、资料/权限缺口和需人工处理的决定。沿现有提案与 Task 写命令应用；接受计划不自动 Delegate，也不批准工具动作。
- 活动任务不被静默改写；重排涉及验收或输入契约时走原版本/停止规则。部分应用必须报告每项结果，重复提交不重复建任务。
- 第一片不接外部日历，不新增 Calendar/Work Session 完整模块；待用户实用证明容量输入不足，再选择独立日历分支。

二轮规划已确认：本次可用时长指从本段开始到用户离开的时间窗口，计划须把执行、等待和必要审阅纳入预计完成时间，人工投入另列；有重叠的时间不能重复相加，未取得依据的时间保持未知。该窗口用于计划建议，不自动成为 N06 执行授权有效期或在途动作的硬停止期限。

关键任务估时未知时，先提出有时间边界和明确输出的诊断候选，根据诊断结果再更新后续计划；后续任务继续标为估时未知，不因标题、截止日期或模型猜测承诺本段可完成。诊断也只是一项待接受的计划候选，接受计划仍不自动 Delegate。现有 Task 的优先级、截止日期和 BLOCKS/INFORMS 可复用，结构化估时、容量和整段候选协议尚需 N04 实施前核定，不把 Today 的 Pin/Later/Focus 当时长预算。

用户确认容量不足时优先推进所选目标的主线与必要前置，再按剩余容量安排独立任务，并说明延后原因；可以只完成一次有明确输出的诊断，不以完成更多小任务掩盖主线缺口。排序依据须来自明确目标、已登记依赖、原优先级和截止日期；未设置优先级、未登记依赖及模型判断分别保留未知/建议，不自动写成新的硬事实。

用户确认诊断预算用完仍未定位时，交付已查证据、排除项、未知问题及下一步候选，由用户决定是否继续投入，不自动占用原留给后续工作的时间。原修复任务保持未完成；诊断成果只按自己的确切验收条件判断，不能降低或沿用原修复任务的完成条件来宣称报错已修复。相关呈现归[工作台 §19](../frontend/workbench-design.md#19-下一段工作计划n04已确认规划)，本轮规则仍为未运行规格。

### N05 有限触发与提醒控制

2026-10-14 基础片核定一次性时间、独立代次/发生、应用生命周期扫描和原通知结算协议（HTTP 契约 §10.76、数据库设计 §84）：当前 API/客户端可创建、编辑、暂停/禁用/继续、读取与处理事项；只有主动改实际时刻产生新代次，原待处理保留。以下产品规则仍为完整目标；设置/待处理 UI、Windows 原生投递、确定性时钟/故障组合与收益出口不从基础数据/真实 API 重开检查推断通过。

- 2026-10-02 用户确认首场景为一次性指定时间的「继续项目」提醒。每条提醒绑定明确项目与时刻，触发只持久化提醒/待处理；用户点击进入原计划入口，填写本次可用时长并主动发起 N04 计划。模型请求另外核验来源和预算，不因设置提醒取得外发许可。
- 首版仅此一次性时间场景；固定周期、自动生成复盘及业务事件触发留待另选。触发不调用模型、不启动任务链、不改成果或自动收录知识。
- 用户确认仅应用运行期间触发，退出后不运行；下次打开时，错过的有效提醒最多形成一次待处理，重复重开或扫描不重复补。多个提醒的投递可合并，原事项身份独立保留；不自动补跑计划或模型。时间输入、时区/时钟变化和过期配置判定的工程协议在 N05 实施前冻结。
- 二轮用户确认提醒保持创建时确认的同一实际时刻，保留原设置时区；设备或显示时区变化只改变呈现，不自动改触发时间。修改触发时间须显式编辑并沿原配置版本/命令核对；显示偏好不推进提醒配置。原待处理身份不能因改时间、显示时区或配置而消失。呈现归[工作台 §20](../frontend/workbench-design.md#20-一次性继续项目提醒n05已确认规划)。
- 保留 V1 运行中必须介入通知语义。新提醒只在有效新事项出现时投递，不反复提醒已解决事项；静默时段/频率规则不能吞掉应用内未决事实。
- 暂停、禁用与并发触发有持久记录；关闭未来触发不等于撤销已经形成的待处理或用户另行发起的计划请求，分别走原处置/取消入口。

### N06 有限连续委托

受控修改/检查接续（2026-10-14）：沿原注册工具、范围授权、单次审批、变化集和配置检查，支持普通文件修改、检查失败后修正重查及原会话明确 MODIFY 方法。规格归 HTTP §10.79，复用 0085 JSONB，无新迁移。创建不签发有效 Run 授权，明确链授权后由原 Delegate 逐项签发本 Run 范围，期限不超过本链且不跨终态；检查脚本变化需重新圈定，不覆盖 DENY 或替代人工验收。以下旧切片保留时点；UI、自定义方法、活动续期、真实 Provider/Windows 和完整 N06 后置。

2026-10-14 基础片沿原 Owner 接单项目固定 Markdown 队列、独立明确授权、累计任务/模型调用上限、原验收完成后串行接续、持久暂停/撤销与重开人工确认；协议归 HTTP §10.77、数据库 §85、ADR-021。没有外部工具动作、UI 或新通用图；来源/工具资源绑定、活动中无缝续期、完整并发/故障、Windows/PV06/PV08 和收益仍按后续出口接续，不从本片推断通过。以下保留完整产品规则。

- 2026-10-02 用户确认首片为单项目的有限任务链自动继续：一次明确执行请求覆盖选定、已确认且可执行的任务集合，依赖固定；请求同时限定来源、工具/资源范围和必须停下的条件。接受计划本身不授执行权。

- 二轮用户确认授权到期时阻止新准入，并通过原持久控制入口请求当前任务在安全点暂停；请求尚未安全应用时显示“暂停中”，核实后才显示“已暂停”。已完成事实保留，未决外部动作/UNKNOWN 先按原身份核对，不因到期重发、释放隔离或宣称已停。续期与到期、暂停与完成竞争须重新核验原授权/任务基线，不能由旧定时请求暂停后来独立获授权的执行。呈现归[工作台 §21](../frontend/workbench-design.md#21-有限任务链的授权与接续n06已确认规划)；N04 计划窗口结束不自动触发本规则。

入口体验见[工作台第 27 节](../frontend/workbench-design.md#27-内置-skill-与聊天命令)，方法定义见[扩展专题第 9 节](../architecture/relay-skills.md#9-内置工作方法与可定制-skill)，恢复责任见[运行架构第 8 节](../architecture/runtime-context.md#8-会话压缩与消息文件恢复)，未运行规格见[测试计划第 26 节](../testing/verification-plan.md#26-内置-skill命令压缩与消息文件恢复验收规格)。首版通用摘要为技术推荐，其他 Provider 原生压缩是否同步接入尚未确认；不因“参考 Codex”默认引入完整上游运行时。

## 10. 验收证据与投入判断的范围和分期

2026-10-11 确认设计，2026-10-14 开始基础实现。统一定义归[总纲 §0.14](../../Personal_Workflow_OS_Master_Spec.md#014-验收证据与投入判断)，交互归[工作台 §29](../frontend/workbench-design.md#29-验收证据与投入判断)，规格归[测试计划 §27](../testing/verification-plan.md#27-验收证据与投入判断验收规格)。**第 1/2 批基础数据链和第 3 批工作段记录/复盘接口与客户端已实现，其他能力按下述范围接续**；实际结果仅归统一功能验收表。本轮按用户授权只接前后端功能，UI 后续重构。

### 10.1 首版范围与批次

首个验收切片服务单个 Agent 交付 Task，先解决证据分散：默认核对已登记条件，AI 查漏按用户明确请求开展；交付消息与 Task 详情消费同一投影。主动选入的外部材料可先保留并标待核实，材料导入不形成正式 CheckResult 或 PASS。首版汇总已有证据及补救建议、原有处理入口，不建立完整执行检查闭环。

| 批次 | 本增量范围 | 进入依赖与边界 |
|---|---|---|
| 第 1 批 | 补强现有 Task 验收证据入口；主动选入纯文本测试输出、日志及 Markdown，新增确切材料关联与聚合投影；找证据阶段的开始/结束、暂停/继续计时，以及原流程基线和对比记录 | 复用现有 Task 验收条件、产物版本与合法资料入口；计时及试验记录须先于价值对比可用，正式假设系统不构成本批前置 |
| 第 2 批 | 用户明确建立的假设验证；对明确登记前提或关联假设的 Decision，在相关依据变化后准备复审候选 | 复用第 1 批证据和观察记录；决定复审沿 N03 的既有 Information Owner、版本及来源，不自动使 Decision 失效；假设新增写入责任和对象协议另行核定 |
| 第 3 批 | 有可靠观察基线后的用户主动工作段产出复盘；在 N04 基础上的用户主动范围推演，比较固定可用时间下全部做、缩小范围或推迟部分任务 | 复盘依赖可核对的预期与实际记录；保存预期仅记录既有目标/Task 基线，不创建或启动任务，不修改当前计划。推演依赖 N04 的计划候选、容量与应用入口；两项不新增相互硬依赖，方案选择不自动执行 |

以上批次仅表示本增量的相对依赖，保留已确认的 **N01→N02→N03** 交付优先级；实际开工范围与顺序仍以当前阶段及用户授权为准。推演不能绕过 N04，也不能因估时未知承诺完成日期；临时回顾没有历史预期基线时保留 UNKNOWN，不用当前状态补造过去预期。

首版之外保留：被动全仓材料采集、PDF/Office/截图解析、自动猜测历史决定前提、完整执行检查闭环、固定周期复盘，以及增加资源的推演维度。

### 10.2 当前复用入口与新增缺口

下表保留 2026-10-11 源码核对时的入口和缺口。2026-10-14 已补第 1/2 批基础数据链、第 3 批工作段预期/完成引用/用量/事件及临时回顾，并接 N04 基础估时/容量/逐项应用与其上的主动范围比较/方案选择客户端。协议归 HTTP 契约 §10.67–75、数据库设计 §75–83。范围推演第一片只比较同一容量下的任务集，缩小保留必要前置、推迟传播下游，选择生成新计划候选再逐项应用；不缩减原 Task 验收或授执行权。交付消息双入口/UI、自然语言发起、自动疑似事件提取、真实 Provider 解释/分析质量与正式收益试验仍后置或待验，不借基础功能升级完整 N04 出口。

| 可复用事实 | 本增量仍需补齐 |
|---|---|
| [TaskAcceptanceEvidence](../../apps/workbench/src/components/TaskAcceptanceEvidence.tsx) 已聚合 Task 验收、CheckPlan、Artifact、Run Trace 与完成依据 | 单 Task 外部材料选入及条件关联、同一投影在交付消息下呈现；历史 Trace 匹配不能单独证明当前证据适用，不以组件存在证明新增视图已完成 |
| [LiveCreateProjectFlow](../../apps/workbench/src/views/LiveCreateProjectFlow.tsx) 在新建项目时选取非空 UTF-8 `.md/.txt`（最多 256 KiB），保存为项目 Knowledge；[KnowledgeView](../../apps/workbench/src/views/KnowledgeView.tsx) 支持手动笔记、纯文本/Markdown 及同项目确切 Markdown ArtifactVersion 收录 | 现有本地文件选择器不是单 Task 附件入口；新增 Task、验收修订、条件及被测版本到确切材料版本的关联。文本导入保存正文版本和摘要，文件名作为标题，尚未建立原文件路径、命令执行身份或受验对象的可信关联 |
| [information-commands](../../apps/api/src/application/information-commands.ts) 和 [information-queries](../../apps/api/src/application/information-queries.ts) 具备资料版本、来源引用及确切正文读取/摘要/可用性核对；正式 CheckResult 写入由 [verify-run](../../apps/api/src/application/verify-run.ts) 及受约束的 [review-decisions](../../apps/api/src/application/review-decisions.ts) 处理 | 材料聚合查询、关联缺失及待核实状态；外部日志作为资料不证明条件通过，未发现可把任意日志转成正式 CheckResult 的可信导入入口，不以新增关联绕过原 Verification/Review |
| [model-call-repository](../../apps/api/src/model/model-call-repository.ts) 与 [model-call-recorder](../../apps/api/src/application/model-call-recorder.ts) 有逐次用量、预算及调用身份记录 | 账本覆盖范围与成本口径仍须核对；人工耗时、预期工作段、返工和介入的事件/确认统计需补齐，未知或缺失不记零，不由模型猜测人工时间或返工因果 |

### 10.3 实施与试验前置

| 前置 | 开工或对比试验前须核定 |
|---|---|
| 写入责任与对象版本 | 假设 Owner、身份/版本、验证方法与来源、候选和人工确认结论的关系；明确登记的决定前提/关联假设与来源变化引用。假设结论不升级为正式 PASS、需求接受或 Task 完成；需求/Goal 写能力不能由本设计推定已有 |
| 材料关联与读取 | Task/验收修订/条件/被测版本和确切材料版本的关联 Owner、来源可信度、缺失/失效表达、权限和正文读取范围；不另建 Task/Run/Review/Verification 事实源，不补猜不完整材料的关联 |
| 计时、预期与事件统计 | 找证据有效计时、暂停及总经过时间的持久化/恢复，其他时间补录的来源标记；工作段开始时预期引用与确认、无历史基线的 UNKNOWN；接受产出、返工、介入及真实模型用量/成本的统计范围、去重和确认依据。记录工作段不触发原任务执行 |
| 一致性与用户控制 | 幂等、revision、迟到结果、并发编辑、停止/恢复及撤回的边界；候选、结论和正式业务效果分离，记录或建议不能自动取消 Task、修改计划或取得执行权 |
| 价值试验 | 明确相近任务样本与可比口径，交替原流程/新视图并保留原流程基线；主指标找证据耗时，辅助总验收耗时，准备/关联成本单列且计入总耗时。相对降幅的具体百分比在基线后、对比试验前确定并冻结；漏验或把旧证据当当前结果作为正确性护栏，样本数和具体数值仍待核定 |
| 结论、接口与兼容 | 证据充分可靠且收益未达冻结目标时，Agent 默认建议停止当前方案下一阶段投入，由用户确认；证据不足不作结论。必要 API/数据库、Breaking Change、migration、升级与回滚、模型请求的来源/权限/预算及恢复协议分别核定，本节不预造端点、表或完整执行闭环 |

产品详细规则仅在总纲维护；试验规格与后续实际成绩分别归测试计划和统一功能验收表。产品确认当轮仅同步文档，未修改当前阶段或原验收成绩；2026-10-11 应用户后续要求交付[分批实施任务书](../../prompts/evidence-and-investment.md)，默认执行第 1 批 A–D，后两批分别检查授权与前置。本次提示词编制未启动产品开发，不把任务书存在视为已下发实施指令。
