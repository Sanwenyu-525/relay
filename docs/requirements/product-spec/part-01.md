## 0.1 一句话定义

**Personal Workflow OS** 是一个以 **Goal / Project State** 为长期工作状态，以 **Task** 为人机协作与工作分配单位，以 **Workflow + Verification** 为 AI 执行闭环，并可根据不同 Project / Task 类型切换 **Workbench** 的个人 Agent 工作系统。

2026-09-29 体验重心调整：用户指出现有页面偏向传统 SaaS，并要求只改造文档。产品前台应让用户围绕目标与 Agent 持续协作，直接理解执行进展、操作产物并作出必要判断；项目与任务管理支撑这条主线。具体入口、导航与布局仍为设计提案，统一见[工作台第 14 节](../../frontend/workbench-design/part-03.md#14-以目标协作为中心的工作台改造)。本次不改代码、不批准自动执行、不改变领域 Owner 或既有完成条件。

## 0.2 协作形态补充（2026-09-25，Proposed）

2026-09-28 决策接续：其中锁定、手动影响检查与人工介入提醒已有用户逐项确认，具体行为统一见[工作台 10.1](../../frontend/workbench-design/part-02.md#101-已确认的锁定与影响检查规则)与[11.5](../../frontend/workbench-design/part-03.md#115-已确认的人工介入提醒规则)。这是对应产品规则的确认，不表示本节全部探索已定稿、已实现或已通过验收。

来源：用户提供的 Agent 产品形态讨论及本轮项目评估，并要求补充到文档。此节保存产品探索方向，不代表相关能力已实现、验收通过或已加入当前开发工作包；当前进度仍以 [CODEX_NEXT_STEP](../../../CODEX_NEXT_STEP.md)为准。

建议的产品表达：**围绕真实项目成果，让人与 AI 持续推进、局部修改、可靠交接，并用证据确认完成。** 在既有 Goal / State / Task / Artifact 闭环上，以目标托管为主线、成果共创为主要操作方式、守护机制发现值得处理的变化。

| 方向 | 核心体验 | 需要解决的边界 |
|---|---|---|
| 目标托管 | 用户回来时能看到当前事实、完成证据、阻塞和下一步，并从真实状态接续 | 托管责任须明确结果、证据、可修改范围、人工决定、资源预算及停止条件；维护下一步建议与自动执行下一步是不同权限 |
| 成果共创 | 人与 Agent 操作同一份成果，支持局部调整、差异审查和版本追溯 | 依赖须绑定来源与版本；确定影响、待复核内容和模型推测分开；新版本不能继承旧版本的验证或批准 |
| 守护机制 | 在授权监控范围内发现变化，准备建议，在值得处理时提醒用户 | 监控授权不等于修改授权；需合并重复提醒，未变化或不可行动时保持安静；不能把推测直接写成事实 |

专属任务页面围绕业务对象及其关系组织，例如论文的“论点—证据—章节”，而不只是为聊天生成不同布局。优先探索用户确认的明确引用与版本关联，不预设通用知识图谱或新增运行时。具体关系模型、影响传播规则和写入口仍待设计。

即时工具型界面可作为以上体验的辅助：围绕当前问题展示权重比较、影响范围或版本差异；受控组件只调用既有授权业务入口，生成界面不增加写入权。流程内嵌型 Agent 可复用这套闭环，在确定流程中的必要节点提供判断。实时教练、世界/仿真型 Agent 作为其他产品形态保留认知，不纳入当前 Relay 交付范围。

本方向深化既有定位，不以“长期目标”或“持续运行”本身作为独有能力，也不据此替换现有执行器。优先验证一条真实项目流程；候选场景与交互判据见[成果共创与变化守护](../../frontend/workbench-design/part-02.md#10-成果共创与变化守护探索)，阶段边界见[范围补充](../v1-scope.md#协作形态探索补充)。

## 0.3 三个核心关键词

### Stateful

系统始终知道：

- 这个 Project 为什么存在
- 当前做到哪里
- 已经做了什么
- 哪些 Decision 仍然有效
- 下一步是什么
- 当前有哪些 Risk / Blocker
- 哪些工作由人做、哪些交给 AI

### Delegated

每个 Task 由用户决定：

- **Me**
- **AI Assist**
- **Delegate AI**

系统支持 Human ↔ Agent 之间持续交接，而不是每次重新解释上下文。

### Verified

AI 输出不等于完成。

任何委托任务最终必须进入：

```text
Artifact
→ Verification
→ PASS / RETRY / HUMAN
```

Worker 无权自己宣布任务完成。

## 0.4 AI 并行开发中的注意力与验收依据

2026-09-26 补充。来源：用户提出以下两个问题，希望 Relay 能够解决，并要求将讨论更新到相关文档。问题与产品目标作为本次需求输入；具体交互、接入方式和评价协议仍为 Proposed，不代表已实现、已验收或已调整当前工作包。

1. **注意力分散。** 开发者在一个项目中委托多个 Agent，或同时推进多个项目；等待执行期间不断切换，返回时又要恢复上下文。统一窗口只能减少找入口的成本，仍需解决反复查看、无效打断和重建理解的问题。
2. **验收依据不足。** AI 快速产出代码后，开发者对具体实现的熟悉程度可能下降，难以识别重要场景与遗漏。需要分别补足实现理解和业务要求，不能仅以增加测试数量替代明确“必须保证什么”。

本次产品目标：**让开发者把有限注意力放在关键决定上，并把 AI 的产出变成有依据、可理解、可接手的项目成果。** 这是既有长期项目协作定位的深化；General、Thesis、Development 的通用核心保留，优先建议用 Development 场景验证效果。

建议围绕三项体验形成闭环：

| 体验方向 | 用户应能回答的问题 | 责任边界 |
|---|---|---|
| 统一待处理队列 | 哪些事情现在需要我，为什么需要我，延后会有什么影响？ | 基于既有 Task/Run/Review/控制事实汇总；展示优先级不改变执行权、审批或业务状态 |
| 上下文恢复摘要 | 上次确认了什么，离开后改变了什么，现在如何接手？ | 结论关联来源、时间与版本；事实、建议和未知分开，没有比较基线时不虚构变化 |
| 面向需求的验收视图 | 哪些重要行为已验证，哪些仍缺依据，能否接受当前成果？ | 关联需求、验收条件、变更影响与真实证据；现有测试通过不等于重要要求完整覆盖 |

补充考虑：待验收成果积压可能成为新的瓶颈，应探索与人工处理能力匹配的并发限制；实现与测试可能共享同一个误解，应以事先明确的要求、既有回归和实际运行证据校核；多个任务分别通过不能替代最终组合版本的验证；交付说明应帮助用户持续理解行为、设计原因、影响与限制。上述风险是设计动机，不是本项目已测得的结论，也不承诺自动发现全部缺陷或影响。

外部执行工具的接入需要可信的任务关联、状态、产物版本与验证回执；聊天摘要或模型自报完成不足以确认业务结果。首个候选闭环优先复用一个真实执行入口，再评估扩展，不由此新增多 Agent Router 或大量 Connector。

具体交互由[工作台第 11 节](../../frontend/workbench-design/part-02.md#11-ai-并行开发的注意力与验收体验)维护，分期边界见[范围补充](../v1-scope.md#ai-并行开发体验补充)，候选场景、基线与衡量方法见[验证计划第 11 节](../../testing/verification-plan/part-02.md#11-ai-并行开发体验验证提案)。Agent 数、代码量与测试数量不能单独证明这些产品目标已达成。

## 0.5 文件夹入口与对话直接执行（2026-10-01，产品规则已确认）

来源：用户反馈新建任务和打开对话步骤过多，确认选择「打开文件夹后直接对话，在聊天里明确要求修改或执行即可进入执行」。本轮授权仅为更新文档和提供实施提示词；本节不是实现或验收声明。

默认入口调整为「打开文件夹 → 对话 → 按用户意图讨论或执行」。新对话不要求先填写任务名称、预期结果或验收标准；纯讨论不制造正式 Task。明确的执行请求由应用用例准备必要任务与执行契约并走原 Delegate 入口，不普遍要求再点击「开始执行」。目标或范围存在实质歧义、缺少所需权限或命中现有动作审批时，才在原对话中处理必要判断。正式任务管理和 GUI 执行入口继续可用。

这里的文件夹是用户当前工作目录，数据库 Workspace 仍是作用域与配置边界；Project、Task、Run、验证及业务完成的职责继续分离。详细交互统一归[工作台第 18 节](../../frontend/workbench-design/part-04.md#18-文件夹入口与对话直接执行)，责任及恢复归[领域模型第 12 节](../../architecture/domain-model/part-01.md#12-文件夹入口与对话执行的应用边界)，取舍见[ADR-016](../../decisions/ADR-016-folder-first-conversation.md)。本节接续 2026-09-29 的入口提案；那次「不批准自动执行」仅描述当时范围，本次也不授予无用户请求的后台持续执行权。

### 0.5.1 普通 Agent 的连续工具主流程（2026-10-15，已确认、待重构）

用户确认将普通 Agent 收敛为：**原用户消息与当前上下文 → Agent 请求必要工具 → 应用校验并执行 → 结果返回同一工作轮次 → 原会话回复**。普通聊天读取、执行候选、明确写请求的原 Task/Run 接续及原消息结果投影已有实现；真实运行范围与未验边界只以统一功能验收表为准。状态维护解释入口仍保留独立 Owner，不据此宣称所有普通聊天分支均已合并。

1. 普通消息由一条逻辑主流程负责推进和回复，不再固定拆成无工具聊天、执行意图解释、项目状态维护解释三个独立模型分支。Agent 可在同轮继续调用工具；“一条流程”不限制为一次模型调用，也不取消确定性的模板选择和业务校验。
2. 已绑定唯一有效目录时，“看一下这个目录下面的文件”足以授权基础只读查看，默认先列直接子项，必要时按问题读取，不默认遍历整个仓库。用户无需重述目录、填任务表或固定再次点击开始；真正的歧义、权限审批及冲突仍需处理。
3. 纯讨论、列目录、读取与解释文件不为凑执行入口创建占位 Task/Run；只读动作须有可恢复的消息、工具和 Gateway 记录。需要修改文件、运行检查时，由同一主流程衔接原 Task/Run 执行入口；业务状态变更沿各对象原应用用例，不另建事实 Owner。
4. 原会话展示与实际回执一致的进度、结果、失败和必要决定。文件读取请求不被追问要维护什么项目状态，执行中不并行生成“没有读取能力”的通用拒绝；未调用或读取失败不能声称已经读过。
5. 目录绑定记录作用域，权限由应用用例按用户可见的目录访问选择建立；2026-10-17 的主动选目录与默认只读规则见 §0.5.2。仅恢复已有绑定、模型请求工具或读取外部文本均不构成重新授权；暂停、取消、UNKNOWN、Artifact 版本、验证、人工接受和业务完成边界保持。
6. `ASSISTANT`、`LEARNING` 的既有身份与能力边界保持；显式 Skill、方法和专用验证协议继续适用，不为统一普通聊天而合并全部模型调用协议。

交互归[工作台 §18.10](../../frontend/workbench-design/part-07.md#1810-普通-agent-的连续工具主流程)，Owner 与恢复归[领域模型 §12.6](../../architecture/domain-model/part-02.md#126-普通-agent-主流程的应用边界)，取舍归[ADR-022](../../decisions/ADR-022-agent-conversation-main-loop.md)，验收规格归[测试计划 §17.2](../../testing/verification-plan/part-03.md#172-普通-agent-连续工具主流程)。本节接续 §0.5 和 §0.8.1 的入口要求，不移除业务确认条件或授权无请求的后台执行。

### 0.5.2 本地目录无需手工连接配置（2026-10-18，已确认、已实施）

用户指出本地文件操作仍要配置连接与策略的使用负担，并授权修改产品文档和生成新实施提示词。日常文件工作统一为 **选择目录 → 本目录权限档位 → 发消息**，不要求用户手工建立 FILE_QUERY/FILE_READ/FILE_WRITE 连接或逐动作策略。

主动选择目录时，以一行清晰提示说明读取范围，由应用完成该目录的基础只读准入，默认不开放写入；已有拒绝、停用或上层限制继续有效。写入档位为「只读／请求批准／自动批准／完全访问」（2026-10-18 由三档接续为四档），用户主动选择写档位后，由原应用 Owner 配置必要内部事实。目录限制、Gateway、Task/Run、基线、确切动作审批与审计保留；「完全访问」只放宽本目录内的文件写入，含新建、修改与删除不再逐次确认，Git、CLI、浏览器、电脑与目录外动作仍按各自策略逐次确认，非完全访问目录的删除不因自动档位免确认。外部服务的连接/凭据配置与特殊能力设置继续按需提供，不能为了基础文件读写把高级设置变为必经页面。

完整用户行为、旧配置兼容和生命周期以[工作台 §18.1.4](../../frontend/workbench-design/part-05.md#1814-本地目录权限设置2026-10-18已确认已实施)为主，工程边界归[领域模型 §12.2](../../architecture/domain-model/part-01.md#122-用例与事务)，取舍接续 [ADR-016](../../decisions/ADR-016-folder-first-conversation.md)。当前实现和验收边界分别以代码与[统一功能验收表](../../testing/overall-acceptance-2026-09-28.md#当前功能验收表)为准；产品规则的落地不代表真实 Provider、Windows 窗口或当前桌面运行实例已验收。

## 0.6 Agent 协作行为（2026-10-03，已确认设计）

本轮逐题访谈确认：产品 Agent 默认是**有判断的项目搭档**，能讨论、质疑并提出推荐；明确执行要求后，在当前授权范围内主动推进。常规实现选择可自主处理；改变目标、扩大作用域或权限、引入重大架构取舍时，先说明具体影响并取得必要决定。

当前任务完成并通过所需验收后，默认报告结果、建议下一步；只有用户明确授权了连续工作的范围与预算，才自动进入下一项任务。人格与主动性不改变 Task/Run、Gateway、Review、Artifact、验证和业务完成的职责，也不授予无请求的后台执行权。

用户选择本轮产出**完整目标 Agent 设计，并标明待开发行为**，随后明确授权把提示词接入运行代码。输入/输出设计与剩余增量统一归[Agent 提示词与输入协议设计](../../architecture/agent-prompt-design.md)，运行公共核心由 [agent-system-prompt.ts](../../../apps/api/src/workflow/agent-system-prompt.ts)维护，评价归[测试计划 §18](../../testing/verification-plan/part-03.md#18-agent-提示词与输入协议评价目标设计)。现有入口已接入公共核心，目标协议其余部分仍为 Proposed；不代表完整 Agent 已实现或已验收。

## 0.7 会话内可折叠执行计划（2026-10-03，推荐设计）

来源：用户以 OpenCode 的会话执行清单为参考，要求比较其他 Agent 的机制、补充项目文档并提供实施提示词。本轮仅交付设计和提示词，未启动本功能开发或验收。

多步骤执行在原对话中提供可折叠计划，让用户看见当前步骤、已完成项、实际依据与尚需处理的问题；简单问答和一步操作不强制生成清单。首片推荐只服务已关联正式 Run 的会话，纯讨论继续自然表达，不为展示计划创建 Task 或 Run。

正式 Task 拥有目标和验收条件，Run 拥有一次执行，计划项是该次执行的工作分解。计划更新不授予工具权限、不改变冻结执行契约、不自动创建子任务或启动下一项任务。步骤完成、检查通过和业务完成分别表达；全部勾选仍须经过原 Verification、Review 和完成用例。

基础工具、结构化状态与折叠界面采用成熟机制。Relay 的推荐改进是关联真实执行依据、恢复后重读当前状态、明确过期或未知证据；本节不承诺自动证明每个步骤正确，也不把这些工程能力宣称为已确认论文创新。研究选题和效果评价仍归[评价协议](../../research/评价协议.md)。

上游机制及采用差异归[研究对照 §1.3](../../research/p00-source-study.md#13-会话执行计划机制对照2026-10-03)，工程归属归[运行架构 §2.4](../../architecture/runtime-context/part-01.md#24-会话执行计划的归属与持久更新推荐设计)，交互归[工作台 §22](../../frontend/workbench-design/part-06.md#22-会话内可折叠执行计划推荐设计)，未运行规格归[测试计划 §19](../../testing/verification-plan/part-03.md#19-会话执行计划验收规格)。后续执行输入见[专项提示词](../../../prompts/conversation-execution-plan.md)，不替代当前阶段与工具循环工作包。

## 0.8 状态驱动与轻量起步

2026-10-04，用户确认产品原则：Agent 的核心是**依据真实状态持续推进目标**，创建目标和任务不能让用户先填一套复杂表单。本轮验收开发提示词并细化产品约束，没有实施新的创建入口或宣称运行能力通过。

用户先用自然语言表达想达到的结果；应用与 Agent 复用已有 Goal、Project State、Task、来源和有效约束，整理必要对象、下一步与可判断的完成条件。名称、已有项目关联和已知信息不要求重复填写；无法可靠得出的关键结果、范围或权限才聚焦澄清，未知信息不编造成已确认事实。正式表单保留为详细编辑入口。

持续推进须能说明已完成什么、正在做什么、为何阻塞及下一步的依据，完成后通过原业务用例更新状态，再次进入复用原身份和当前事实。一次回复结束、聊天摘要或任务数量都不代表目标推进；同一授权范围内接续不等于默认启动跨任务链或后台运行，N04/N06 的授权边界不变。

这细化既有 V1 Goal/State/Task 与对话入口，不新增编排器或第二套状态。目标表达、正式对象创建、READY、Delegate、动作批准和业务完成分别成立；内部必须保存的结构化信息不等于必须由用户逐字段填写。交互归[工作台 §18.7](../../frontend/workbench-design/part-07.md#187-目标与任务的轻量起步)，规格归[测试计划 §17.1](../../testing/verification-plan/part-03.md#171-轻量创建与状态接续)，实现与结果只看当前事实源。

### 0.8.1 自然语言维护项目状态

2026-10-09。用户指出状态承接仍依赖过多表单，经逐项讨论确认以下规则并要求同步文档。**产品设计已确认；确认当轮仅更新文档。后续有限工程切片已进入实现与验收，当前阶段只归 CODEX_NEXT_STEP、结果只归统一功能验收表；以下仍为完整产品要求，不能据此宣称增量已全部实现。** 目标是把整理、登记与衔接状态的工作交给 Agent，让用户表达意图、使用成果并作出必要决定。

主交互为：**用户表达意图 → Agent 推进工作并维护项目事实 → UI 展示变化、成果和需要用户决定的事**。对话统一覆盖已有目标、需求、任务、计划、进度、阻塞、决策与知识，各页面保留查看、核对、详细编辑及无模型人工路径；对象的成熟度和写入职责不因统一入口改变。

| 已确认规则 | 产品边界 |
|---|---|
| 明确指令生效 | 对象、内容和范围足够明确的修改或收录指令本身可作为该项用户确认，复用已有信息并沿原写入/接受入口生效，不普遍要求再填表或点击接受。讨论、模型总结、自动提炼和发现的仓库修改仍是候选；缺少实质信息、冲突、失权或命中动作审批时处理对应问题 |
| 连带影响 | 直接要求的调整生效，相关进度和阻塞依据实际事实更新；改变另一项既定承诺时先说明影响，再用一句具体问题取得决定。例如延后导出不自行决定延后发布或取消发布要求 |
| 外部进展 | 用户报告在其他工具中完成工作后，在已有权限内主动核对成果、检查依据及原完成条件，满足原完成规则后更新状态和下一步。用户报告有来源标记，缺证据或仍需人工体验时保留相应待核对/待验收事实 |
| 返回核对 | 返回项目时自动做轻量核对并整理接续摘要，运行已有授权和预算范围内的相关可信检查；本选择不增加持续后台监控、自动修复、恢复 Run 或跨任务执行权 |
| 日常比较基线 | 相对上次实际查看项目摘要时的状态说明变化；首次或无可用基线只展示当前事实。手动命名接续点继续保留，日常查看不改写该点；未解决事项持续显示 |
| 核对深度 | 优先读取差异、核对证据并运行相关轻量检查，全量或耗时检查另行提出；无变化且证据仍适用时复用结果，未检查、失败、错误和过期分别表达 |
| 变化呈现 | 默认摘要说明改了什么、当前结果和下一步，展开查看变化前后、依据与影响；失败、冲突、重要影响和必要决定直接可见 |
| 摘要位置 | 返回核对结果在项目顶部的可展开接续卡更新；用户指令产生的实际变化回执留在原对话。两个位置消费同一项目事实，不复制业务状态 |
| 纠正与撤回 | 支持自然语言纠正和撤回本次整组可撤回的状态调整；已有后续依赖或冲突时先说明修正影响。撤回保留历史，不自动撤销外部效果、恢复旧批准或继承旧验证 |

本规则接续 §0.10 中的候选处理：足够明确的用户修改指令可以表达确认，发现变化和生成建议仍不等于确认。接受计划与执行授权继续分开；修复和新任务执行沿用明确请求或已有有效授权。助手档的只读边界继续有效，不能因对话成为统一入口而获得业务写权。

交互和示例归[工作台 §18.9](../../frontend/workbench-design/part-07.md#189-自然语言状态维护与接续摘要)，责任与恢复归[领域模型 §12.5](../../architecture/domain-model/part-01.md#125-自然语言状态维护的应用边界)，范围及分期归[范围补充](../v1-scope.md#自然语言状态维护与自动接续补充)和[后续路线 §7](../post-v1-roadmap/part-01.md#7-已确认的未来软件协作能力)，未运行规格归[测试计划 §24](../../testing/verification-plan/part-05.md#24-自然语言状态维护与自动接续验收规格)。日常基线的捕获/查看协议、检查范围与预算、批次撤回/补偿及缺失的领域写入口在实施前核定；不在本轮冻结新 API、表或编排器，不提升 M/N 出口。

|---|---|
| 自动创建主会话 | 用户明确提出独立新需求时创建；歧义时先问一句，同一需求的补充继续原会话。创建不自带执行授权 |

## 0.10 需求驱动的软件协作

2026-10-06。用户基于已有产品文档逐题讨论未来功能，确认整体方案并要求写入文档。**本节产品选择已确认；工程协议、实施分期与效果阈值待核定。** 本轮仅记录设计，不声明能力已实现或验收通过，不改变当前开发授权和阶段状态。

### 目标与讨论范围

面向持续推进长期软件项目的个人负责人，同时支持从零开发与已有软件迭代，覆盖需求、设计、开发、验收、发布及维护。以项目组织工作，沿用自然语言轻量起步；Agent 先复用已有文档、有效决定、需求和项目事实，只澄清真正缺失的信息。General、Thesis 的已有范围继续保留。

首要收益是减少用户转述、分派、衔接和催进度的操作；需求误解、变更返工和隔日接续理解成本同时作为效果检查条件。自动生成的候选数量、Agent 数量或运行时长不能代替这些收益。

### 已确认的未来功能

| 能力 | 产品规则 |
|---|---|
| 需求工作区 | 按用户可使用的功能划分需求项，页面、模块和版本用于分组；场景、边界、完成标准、未决问题及关联工作围绕需求组织。由产品维护有效需求，需求项视图与完整文档视图表达同一份有效要求，支持导出明确版本的仓库文档。尚未确定的想法保留在同一清单，标为待讨论，与当前有效要求分开展示 |
| 变化守护 | 自动发现仓库需求文档修改，准备差异和更新候选，由用户决定哪些变化生效。对同一需求的不同来源修改提供原要求、来源对照、分歧、影响和处理方案。影响调查覆盖已登记关联，并调查代码、接口和测试的潜在关联；明确关联、模型推测、尚未检查的范围分别表达 |
| 动态计划 | 需求已更新、前置工作完成或出现阻塞等重要事实变化后，自动准备下一步计划候选。每个项目维护一份当前计划草案，合并相关变化，说明新增、调整和延后的原因；可补充实现有效需求所缺的任务，产品扩展想法仍留在待讨论需求中。正在审阅的版本保持固定，后续变化提示有更新 |
| 体验原型 | 涉及页面交互且交互复杂或存在分歧时，按需提供可操作原型。按具体使用流程确认，同时保留页面整体评价；未讨论路径保持可见。原型反馈关联对应需求并整理为修改候选；原型确认与正式功能验收分别记录 |
| 项目知识 | 工作完成后，结合成果和实际证据提出有复用价值的新经验候选，包括重要约定、故障根因、方案取舍和经过验证的做法；普通进度留在工作记录。候选附来源、适用条件和未知部分，确认后进入已有知识导读。项目做法变化时主动提出适用性复核候选，用户选择保留、修订或转为历史；后续引用展示复核状态 |
| 集中审阅与接续 | 按同一需求汇集相关的需求、计划和知识建议，关联项目级计划的相关部分，不复制另一份计划。允许分阶段确认，必要前置和受影响工作清楚呈现；必要调整完成前，受影响工作不能按过时要求继续。返回项目时沿用事实接续，有比较基线才说明期间变化，未确认候选不描述为有效需求 |

### 冲突、拒绝与有效事实

产品当前有效要求与来自文档、对话或原型的修改候选须能辨认；发现修改、生成建议、用户确认和实际执行分别表达。2026-10-09 接续：明确用户指令作为确认的条件归 §0.8.1，不把所有对话都解释为修改候选或要求额外接受点击；普通讨论、自动总结和来源变化仍是候选。仓库导出文档不是第二个业务写入 Owner，人工修改先形成可核对候选，沿领域入口生效。需求的组织粒度不替代 Task 的执行单位或 Artifact 的版本、验证责任。

候选有依赖时允许分阶段确认；已经确认的部分、仍需决定的部分和暂时不能继续的相关工作分别呈现。新输入使旧候选过期时保留原来源并重新准备，不沿用旧批准。视图分组不改变既有事务、执行权或业务完成边界。

被拒绝的建议在相应项目中保留理由：相同依据和条件下不反复重提；相关条件有实质变化时，说明新依据后才重新提出。用户可明确选择持续排除，直到主动解除；不得借重新生成候选、改写措辞或换来源标识绕过该决定。这不是默认跨项目偏好学习。

### 与既有设计的关系

沿用有判断的项目 Agent、Me / AI Assist / Delegate、正式完成闭环、版本与来源、安全控制，以及 N01 接续、N03 知识导读、N04–N06 首轮规则。明确执行请求仍可在授权内直接推进，不增加普遍的二次开始按钮；生成或接受计划不授予执行权，新增任务候选不自动进入旧任务链授权。原型、调查结论和知识候选不能代替验证 PASS 或人工接受。

本节确认自动发现和准备候选的产品方向；启用来源、模型外发授权、生成预算、触发合并及运行/退出/重启策略仍须工程核定。该方向不自动成为应用关闭后的常驻运行、无限模型调用或跨项目执行承诺。具体需求写入 Owner、对象关系、同步协议与版本契约也待设计，不凭产品名称直接冻结新表、API 或通用编排器。

详细交互和导出场景归[工作台 §24](../../frontend/workbench-design/part-07.md#24-需求驱动的软件协作)，路线衔接和待核定项归[后续路线 §7](../post-v1-roadmap/part-01.md#7-已确认的未来软件协作能力)，未运行验证规格归[测试计划 §22](../../testing/verification-plan/part-04.md#22-未来需求驱动软件协作验收规格)。后续进入实施须另行明确范围，并按所属文档核定协议与验收条件。

### 项目事项与外部 Agent 共享任务协作

2026-10-23，用户通过逐项访谈确认并授权落成文档。**产品规则已确认，工程协议待核定；本增量待实现、未验收，本轮不启动开发。** 本段拥有产品规则，不改变既有阶段、在途专项和开发顺序。

目标是在 Relay 内置需求与缺陷管理，使不同工具中的外部 Agent 围绕同一套任务事实协作，减少人工转述、分派、催进度与交接。先用于 Relay 自身开发，按通用项目能力设计；第一版的“A2A”指共享任务协作，不构成标准 A2A 协议支持承诺。内置主子 Agent 委派仍按 §0.9 的独立范围核对，不以其存在证明本闭环已实现。

| 已确认选择 | 产品规则 |
|---|---|
| 事项与任务 | 第一版覆盖需求、Bug、关联开发任务及验收结果。事项表达为什么做、预期与完成条件，Task 表达具体执行工作；一条事项可关联多个 Task，不另建一套 Task/Run 完成事实 |

| 开发与独立验收 | 默认独立 worktree 开发，结果绑定确切提交或变更快照；开发者不能领取自己提交结果的独立验收。不同身份只是必要条件，不能单凭两个身份断言独立验收成立 |
| 自动返工 | 验收退回附具体失败项与证据，原开发 Agent 再次连接并领取后修复。默认最多返工三轮，项目可调整；退回后重新提交算一轮，达到上限或出现争议转人工。基础设施故障单独记录，不冒充业务验收失败 |
| 失联与接手 | 超时后标记失联待核对；确认原执行已停止、核对已有改动后才重新分派。心跳过期不证明进程停止，旧执行迟到提交不能越过执行权检查 |
| 需求与验收变化 | 保存新版本，受影响执行标记范围待核对；确认沿用旧范围或切换新范围后再推进。旧验证与批准保留历史，不能自动适用于新条件 |
| 集成与完成 | 独立验收通过后，人批准确切变更，再执行集成及必要回归；成功后才能经原应用完成用例完成任务并判断事项是否满足全部条件。集成失败保留待处理，不假装完成 |
| 日常入口 | 现有项目内增加“事项”，聊天可登记、查询、分派和处理；详情页用于查看、编辑和确认，不另建完整禅道式管理后台 |
| 禅道衔接 | 新事项在 Relay 试运行，旧事项继续在禅道处理。每条事项只有一个当前登记处，不做双向同步、不自动迁移；后续迁移另行决定。在本增量可用并明确启用前，当前登记规则仍按禅道接入文档执行 |

闭环：**登记 → 分析与拆分 → 人确认范围 → 开发领取 → 提交版本与证据 → 独立验收 → 退回返工或等待人工批准 → 集成与回归 → 业务完成并更新项目状态。** 排队不代表已运行，模型自报、提交成功、验收通过和人工批准均不能单独冒充完整完成。

Relay 凭据只约束其接口，不控制外部工具在本机已有的文件或命令权限；返工上限不等于单次外部运行的时间、费用上限。额外授权、条件放宽、范围争议及恢复 UNKNOWN 均沿原权限和人工决定边界处理。

取舍归 [ADR-033](../../decisions/ADR-033-external-agent-shared-tasks.md)，实施范围及待核定项归[后续路线 §15](../post-v1-roadmap/part-02.md#15-项目事项与外部-agent-共享任务协作)，责任归[领域模型 §22](../../architecture/domain-model/part-02.md#22-外部-agent-共享任务的应用边界)，交互归[工作台 §46](../../frontend/workbench-design/part-14.md#46-项目事项与外部-agent-共享任务)，未运行场景归[测试计划 §43](../../testing/verification-plan/part-07.md#43-外部-agent-共享任务协作的目标验收)。

## 0.11 会话模式与人设助手（2026-10-05 已确认设计）

用户在同一个聊天框里需要两种东西：一种能把活干完的 Agent（改文件、建任务、跑检查），一种是有固定人设、**可读不可写**的助手。既有会话只有一种身份，「这条消息能走多远」由模型当轮判断而不是用户预先决定，因此本节把权限等级上提为**会话身份**。

- 会话建立时冻结一种身份：普通 Agent，或人设助手。之后不改写；**切换模式等于换会话**。
- 用户自建具名助手：名字、角色描述、口吻、可选只读目录范围。范围只能缩小受管根。
- 助手会话可用只读工具读真实代码与已选资料版本；**不建任务、不委派、不写入、不申请动作审批**。
- 助手归档后既有会话冻结发消息，历史仍可读。人设快照冻结的是文本，不冻结能力：连接被删后下一轮就少一个工具。
- 「一次性问答」是助手会话的一个开关，不单独占一档。

本助手片不包含多角色同场协作、长期角色记忆、跨项目路由、助手的写能力或 ADR-017 的有界委派。2026-10-23 新确认的项目长期团队归 §0.18 与 ADR-034，不将现有只读人设助手自动升级为有写权限的成员；有界委派当前源码边界见运行架构 §10.1。

取舍与代价见 [ADR-018](../../decisions/ADR-018-assistant-conversations.md)，范围边界归[范围矩阵](../v1-scope.md#会话模式与人设助手补充)，工程责任归[运行架构 §2.6](../../architecture/runtime-context/part-01.md#26-会话级只读工具轮次)。本节与 §0.9 是两种不同的协作形态：§0.9 是主 Agent 派发子执行，本节是你与一个有名字的只读助手对话。

## 0.12 学习模式

2026-10-10。用户围绕完整学习模式分轮确认十五项产品选择，并确认整体方案后要求写入文档。**产品设计已确认；本轮仅文档，工程协议待核定，未实施、未验收。** 本节拥有产品规则，不改变当前开发授权、M/N 阶段或软件完成条件。

### 目标与已确认规则

面向长期软件项目的个人负责人，围绕真实项目学习架构、前后端技术、技术栈、术语和 AI 协作方法，提升准确表达目标、比较技术方案、识别遗漏和判断成果的能力。手工编码占比可以下降，理解系统、作出取舍和核对结果仍是必要能力；本功能不以术语数量、学习时长或课程完成率代替这些收益。

| 选择 | 已确认产品规则 |
|---|---|
| 学习范围 | 项目带学为主，支持脱离当前项目自由学习；已有资料和项目知识导读可作材料，不另建一套知识正文 |
| 教学方式 | 默认简短讲解和具体案例，可选复述、方案比较或指出遗漏等理解检查；用户可跳过、追问或要求深入 |
| 进入方式 | 用户主动进入；Agent 可建议值得了解的取舍，不自动开课或在开发中持续插入教学 |
| 状态范围 | 个人学习状态跨项目共用，保留具体学习场景和来源；某个项目的表现不直接证明所有场景都能运用 |
| 记录依据 | 根据自然对话和可选练习增量记录；讲解过、用户自述、实际回答表现分别注明，用户可查看和纠正，不使用看似精确的掌握百分比 |
| token 成本 | 只读取当前相关的简短状态与资料，历史依据按需查阅；随本轮交互更新变化，不额外调用模型做常规评估或整段复盘，界面读取已有记录不重新生成总结 |
| 学习路线 | 大主题先给少量主题组成的简短路线和当前推荐，随目标调整，允许跳转，不一开始生成完整课程 |
| 隔日接续 | 简短说明上次学到哪里并推荐继续；遇到不确定处再复核，不仅因时间过去自动降级 |
| 转入开发 | 明确要求实现后进入普通执行会话，带上目标、选定方案、约束和未决问题；不在学习会话原地扩大权限，执行仍核对当前项目事实 |
| 记录粒度 | 按实际接触的具体知识点记录，按主题归组；逐步积累，不预建庞大知识树或知识图谱 |
| 矛盾与纠正 | 新表现与旧依据矛盾时标记待复核、指出具体误解并保留必要依据，后续根据新表现修正；用户明确纠正时及时记录其自述，不把一次口误覆盖为全面降级 |
| 状态展示 | 原对话显示简短变化，展开查看状态、依据、缺口与路线；另有轻量查看入口，默认摘要加展开 |
| 资料依据 | 项目问题优先结合真实代码、文档和有效决定；涉及版本、技术选型或其他不确定结论时，按需核对权威来源，项目事实、推荐方案和假设示例分别表达 |
| 用户控制 | 支持纠正、删除、全部清空及本次不记录；清除后从新交互积累，不自动翻旧聊天重建，原聊天按原会话规则管理并说明清除范围 |
| 权限边界 | 学习模式允许应用经专门入口保存个人学习记录，对项目保持只读；修改文件、需求、决定或执行工作转入原执行入口 |

学习状态表达接触情况、已有表现、具体缺口及其依据和时间，不压成一个总分；未观察到某项能力不等于不会。教学后的认可、答对练习或记录为能解释，不是 Knowledge 已验证、Rule/Decision 生效、Task 完成或软件验收的依据。矛盾记录与用户纠正仍区分评估和自述。

### 首版边界与责任

首版闭合自然语言进入、简短路线与教学、可选检查、个人状态增量、查看与纠正、隔日接续及明确转执行的路径。完整课程体系、大型知识图谱、自动出题库和后台复习提醒不进入首版；不通过该功能默认引入学习模型训练、通用自动画像、长期角色记忆或后台自主工作。

个人学习记录的专门写入是本次新增的未来设计，不扩大 §0.11/[ADR-018](../../decisions/ADR-018-assistant-conversations.md) 中普通人设助手的纯只读权限。学习记录属于用户的学习评估，项目事实继续由原 Owner 维护；具体会话类型、状态写入 Owner、来源/版本、并发与停止恢复、删除防复活、API/数据库兼容和成本/效果阈值在实施前核定，不从产品名称推定已有接口。

交互归[工作台 §26](../../frontend/workbench-design/part-08.md#26-学习模式)，状态与权限责任归[领域模型 §13](../../architecture/domain-model/part-02.md#13-学习模式的状态与权限边界)，范围及依赖归[范围补充](../v1-scope.md#学习模式补充)和[后续路线 §8](../post-v1-roadmap/part-01.md#8-学习模式的范围与实施前置)，未运行场景归[测试计划 §25](../../testing/verification-plan/part-05.md#25-学习模式验收规格)。效果检查关注用户能否写出更明确的指令、识别方案遗漏、定义和审查验收条件，并同时核对实际 token 增量，不以短回复宣称成本或学习效果已验证。

## 0.13 内置工作方法与会话控制

2026-10-11，用户已逐项确认并要求直接制作文档，该日“新增产品设计已确认，未实施、未验收”为当时状态。2026-10-24 校准：方法/命令、模型选择与长短期记忆已有各自接续，当前实现及成绩分别读取所属专题与统一验收表，不以本节旧日期统称未实现。**消息文件回退的完整增量仍待实现、未验收**；本节不授权代码开发，不改变当前阶段和既有功能成绩。

内置 Skill 在四项项目协作能力之外覆盖通用工作方法，首批新增代码审查、故障诊断和文档维护，可在本次合法行动范围内实际开展工作；普通自然语言可选择方法。个人/项目定制使用可读、可外部编辑的 `SKILL.md` 目录，官方定义保留，定制独立版本。方法的范围、输入输出、启用和冻结规则统一见[扩展专题第 9 节](../../architecture/relay-skills.md#9-内置工作方法与可定制-skill)。

聊天 `/命令` 同时承载 Skill 调用与系统操作，英文固定名与中文别名共用行为。菜单选中只插入输入框，补充并发送才运行。会话控制支持压缩、新会话和当前会话模型选择，业务状态撤回复用原用例；详细语义见[工作台第 27 节](../../frontend/workbench-design/part-08.md#27-内置-skill-与聊天命令)。

压缩优先适配 DeepSeek 的接续、缓存和成本，手动与自动共存，不能等到接近上下文上限才整理；摘要默认由当前工作模型生成。模型窗口偏好为 256K–512K tokens，与应用工作预算、触发阈值分别管理，参数和效果需实测。文件恢复由用户消息下的撤回按钮发起，回到该消息发送前，包含后续本会话相关修改；运行中先安全停止，其他来源的后续修改按冲突处理。确实撤销已完成成果时重开受影响任务进入新验收周期。工程责任统一见[运行架构第 8 节](../../architecture/runtime-context/part-02.md#8-会话压缩与消息文件恢复)。

2026-10-30 接续确认：应用工作上下文预算支持 256K、512K、1024K 三档及跟随默认，按会话保存，新请求冻结；压缩根据有效预算压力提前触发，保留近期原文与可追溯检查点，不能选了大档仍被原固定128KB工作限制拦住。所选预算仍受实际模型窗口和完整调用预算校验约束，不承诺所有模型都支持1024K。

同日接续授权修复长会话容量：整理按活跃窗口有界分批推进，不因已压缩的累计原文超过10000条而无法继续整理；资料注入与工具结果增长也纳入容量判断。批次失败保留最近成功检查点与原文，已执行工具不能因压缩被重放，活动协议装不下时明确停止，不静默丢弃内容。

以上入口不另建 Runtime，不扩大纯只读助手权限，不将聊天摘要变成业务事实，也不让压缩或文件恢复恢复旧批准/PASS。重要取舍见 [ADR-019](../../decisions/ADR-019-builtin-methods-and-conversation-checkpoints.md)，分期和待核定项见[后续路线第 9 节](../post-v1-roadmap/part-01.md#9-内置工作方法命令与会话恢复的范围)，未运行规格见[测试计划第 26 节](../../testing/verification-plan/part-05.md#26-内置-skill命令压缩与消息文件恢复验收规格)。

2026-10-24，用户要求补齐文件回退产品细节，推荐默认归[工作台 §27.3](../../frontend/workbench-design/part-08.md#273-用户消息下的文件撤回按钮)：原聊天保留，回退事实参与下一轮上下文及摘要核对，不自动重跑被撤回动作；提供有条件的单层“撤销这次回退”，可恢复范围、存储/清理与冲突结果可见；实际文件恢复与历史成果查看、试用版本切换分别表达。新增默认及容量数值仍为推荐，未逐项确认，不提升为 Accepted 实现；原恢复范围、停止、权限、历史保留和任务重开规则继续有效。

2026-10-15 补充：模型选择增加独立「免费模型」分组，支持按服务商目录自动更新及手动刷新。首版范围、免费定义和更新规则归[后续路线 §9.1](../post-v1-roadmap/part-01.md#91-免费模型分组与自动同步)，模型冻结和调用准入归[运行架构 §8.6](../../architecture/runtime-context/part-03.md#86-模型目录会话选择与免费调用边界)。2026-10-16 用户新增单模型额度耗尽后自动切下一个免费模型，完整规则归[§9.1.1](../post-v1-roadmap/part-01.md#911-免费额度耗尽自动接续)；账户总额度、半截输出与未知结果不能用换模型绕过。本轮仅验收并更新开发任务书，不补产品实现。

## 0.14 验收证据与投入判断

2026-10-11，用户逐项确认五项功能范围并要求写成文档。**产品设计已确认，使用收益待试验验证**。新增切片未实施的原表述属于 2026-10-11 设计时点；当前实现及接续范围只见后续路线和 CODEX_NEXT_STEP，实际成绩归统一功能验收表。本节拥有产品规则，分期与工程前置归[后续路线 §10](../post-v1-roadmap/part-02.md#10-验收证据与投入判断的范围和分期)，交互归[工作台 §29](../../frontend/workbench-design/part-10.md#29-验收证据与投入判断)，未运行规格归[测试计划 §27](../../testing/verification-plan/part-06.md#27-验收证据与投入判断验收规格)。不扩大当前 M/N 工作包或改变 N01 → N02 → N03 的既定优先级。

背景是用户知道需要检查哪些内容，但证据散落在聊天、日志和文件中，难以判断是否对应当前交付。先改善单个 Agent 交付 Task 的验收，再用实际观察判断功能投入、复核关联决定、回顾有效产出和比较下一段计划。功能数量、模型回复数和执行次数不代表有效产出。

### 0.14.1 验收缺口视图

首片围绕已有 Task 的验收条件，帮助用户找到对应证据并作出接受或拒绝判断；完整需求或项目发布就绪视图仍按原后续设计推进。默认确定性核对已登记条件与已有证据，AI 查找遗漏仅在用户明确要求时进行，其建议先作为候选，不自动修改验收条件。

同时汇集 Relay 内部证据和用户主动选择的外部纯文本日志、测试输出、Markdown 说明。材料复用原正文与版本机制；需明确 Task、验收修订、条件、被测产物或改动版本，以及材料的确切版本和来源。关联不完整的材料允许留存，清楚标为待核实，不能补猜被测版本，也不能因导入、引用或用户确认收录而转为正式 CheckResult 或 PASS。

显示已执行与否、关联是否成立、版本是否匹配、当前是否适用；未运行、失败、工具故障、证据缺失、过期和待核实分别表达。旧 Trace 匹配不证明当前适用，多个单项 PASS 不证明组合通过。已有正式验证、人工接受与业务完成继续遵守[验证与批准契约](../../../contracts/03-verification-and-approval.md)。

主要入口在交付消息下，先呈现结论范围和关键缺口，再展开证据；Task 详情消费同一投影。首片提供补救建议与原处理入口，不新建执行检查、读结果、刷新证明的完整闭环。后续执行补救仍须沿原检查配置、权限、预算和动作身份处理。

### 0.14.2 假设验证与首个价值试验

假设验证是可选能力，适用于投入较大、不确定性高或存在明显分歧的想法。Agent 可以建议记录，只有明确用户请求才创建；“把这个想法记成假设”可承载本次建档确认，复用已有事实，不强制再填表。记录待验证主张、方法、判断标准及来源，数据和结论保留其适用版本。Agent 计算、整理并提出结论，由用户确认当前结论；它不等于功能 PASS、需求接受或 Task 完成。

首个试验验证验收视图的功能价值。选择若干任务与材料规模相近的样本，交替使用原流程和新视图；只在同一个任务上先旧后新不能单独证明收益，需考虑熟悉材料造成的影响。

- 主指标是找到验收条件对应证据的耗时；辅助观察是收到交付至接受或拒绝的总耗时。
- 材料选择与关联的准备成本单独记录，并纳入总验收耗时。缺失成本保持未知；找证据更快但总成本增加时不能宣称整体节省。
- 首批提供轻量开始、结束、手动暂停与继续计时，只测找证据阶段；保留有效计时、暂停记录及总经过时间。准备成本和总耗时可由用户一句话补充。计时暂停只改变试用记录，不控制 Task 或 Run。
- 最小改善目标采用相对原流程的降幅。先测原流程基线，再在正式对比前冻结具体比例、样本及比较口径；当前没有已确认百分比。保留原始时长、失败与误判，不挑选有利样本。
- 漏掉必要缺口或把旧证据当当前结果不能算成功。方法可靠、证据充分且收益未达预设目标时，默认建议停止当前方案下一阶段投入并保留依据；新证据可支持重新讨论。证据不足则无结论，不自动判为失败。

轻量计时、基线和对比记录先用于首片试用，完整假设管理不是它们的隐含前置。停止投入只是建议，不能自动取消 Task、调整项目计划或撤销既有决定。

### 0.14.3 决定复审

首版只覆盖明确登记的决定前提或关联验证假设，不推测历史上未记录的决策理由。Relay 记录相关依据变化后，自动准备复审候选，在相关回执及项目摘要中显示原决定、变化依据、影响与需判断事项；这不授权后台扫描或持续监控任意外部来源。

候选经原信息与决定入口处理，保留来源、版本及历史关系。候选生成不自动把 Decision 设为失效或 SUPERSEDED，不取消任务、不开始新工作；是否替代决定及其后续影响仍由用户明确判断。依据或决定基线再次变化时，旧候选的适用范围须重新核对。

### 0.14.4 有效产出复盘

用户围绕一段明确的工作主动发起复盘，例如一个功能或选定 Task 集合；固定周报、月报视图留待后续。主要流程是在开始时复用已确认目标、任务和预期保存基线，结束时比较预期与实际。用户一句话可说明“接下来做这几项，结束后复盘”，保存基线本身不创建任务、启动 Run 或改变当前计划。

临时发起回顾时可圈定任务并读取历史预期；找不到当时基线的部分保持未知，不能根据实际结果倒造当初预期。区分预期、按确切条件已验收产出、返工、人工介入、实际模型用量与成本，并显示未完成及其原因。

Agent 可从合法可读记录提出疑似返工或介入事件，候选与正式统计分开展示，用户确认后纳入；多次重跑不能直接认定为返工或推断原因。沿用实际调用与业务记录，未采集时间、用量或成本不补零；推断和统计不能成为第二套 Task 状态。

### 0.14.5 计划推演

在 N04 的下一段计划基础上，用户主动发起推演；Agent 发现相关问题可建议启动，首版不自动生成推演候选。固定可用时间，比较“全部做、缩小范围、推迟部分任务”的范围取舍。增加时间或执行资源作为后续维度，不进入首版。

候选绑定同一明确事实基线，展示任务范围、依赖、延后理由及资料、权限、容量和估时缺口。估时来源不可靠或未知时，只作范围与依赖比较、必要诊断建议，不承诺完成日期；基线变化后须复核受影响候选。选定方案通过原计划与对象写入口处理，不直接改活动 Task，也不自动 Delegate 或授予执行权限。

本增量沿原唯一业务 Owner、版本、短事务、权限、验证、人工接受及完成路径。材料关联、假设与结论记录、计时及工作段基线、复审和统计候选的具体写入 Owner、持久化、幂等、revision、恢复与 API/数据库兼容在实施前核定；本节不预造运行接口或表结构。
