### 43.1 就绪候选由服务端推进；界面只呈现阶段（2026-10-20 第二轮，已实施，实机未验）

上一轮把推进入口留在了本页：读到 `auto_start` 的 READY 投影后由 effect 调
`POST …/applications`。用户指出真正的问题——**关掉页面之后那条已经明确授权的请求还走不走？**
本轮把推进责任收回服务端，界面只负责「说清楚现在到哪一步、卡在哪、要不要你决定」。

- **撤掉「计划执行方式」本设备偏好**（设置 → 执行策略里的下拉，键
  `relay.workbench.planExecution`）。它是同一件事的第二次确认，也是前端必须持有推进责任
  的唯一理由；目录写档位与逐动作审批已经表达授权。遗留的本地键不再读取，也不代为清理。
- **执行摘要不再提供「按这个目标执行」**。`READY`/`TASK_PREPARED` 显示「正在准备执行」，
  `DELEGATED` 显示「正在执行」；正常路径上没有任何按钮。
- **唯一的按钮是「继续原请求」**，只在服务端自动推进失败（阶段 `FAILED`、还没有 Run）
  时出现。失败原因是服务端写回原请求的**具体**一条（缺哪个连接、缺哪个目录、会话已有
  在途 Run），原样显示在摘要里——用户关掉页面再回来仍然看得到，不需要重述目标。
- **内部身份不进日常界面**：`task_id`/`run_id`/`revision` 不再出现在按钮文案里，
  入口改成「查看执行详情」。
- 摘要文案统一为用户语言：「不需要再确认一次：准备完成后会直接继续」「删除会在执行前
  单独请你确认」「文件内容在读取真实内容后决定」。

推进器、失败登记与阶段语义归[运行架构 §2.10.1](../../architecture/runtime-context/part-02.md#2101-推进-owner-收归服务端与能力事实说明2026-10-20-第二轮)，
投影字段归 HTTP §10.107。仍未闭合：无目录操作会话、普通检查仍随 Run 进入正式验收、
真实 Windows/WebView2 与真实 Provider 未验。

### 43.2 执行摘要的边框盒必须容纳自己的内容（2026-10-20 用户截图，已实施，实机未验）

用户在「正在准备执行」卡片上画箭头指「样式有问题」。实机截图里能看到两件事同时发生：
卡片下边框在「当前目录：…」半行处截断，而「新建 · aa.md」「不需要再确认一次：准备完成后
会直接继续。」这些**同一张卡的行画到了边框外面**，于是整块只剩一条绿色细线。

- **成因**：`.execution-summary` 为了不把转录区压没而写了 `flex: 0 1 auto; min-height: 0`
  （§43.1 的前一轮），可它同时是 `display: flex` 的列容器且没有 `overflow`——被压到比内容矮时，
  边框盒缩小、子项按 `overflow: visible` 继续往下画。压缩本身是对的，缺的是「盒子自己承担溢出」。
- **修法**：`.execution-summary` 加 `overflow: auto` 与 `overscroll-behavior: contain`。
  有空间时与原来完全一致（不出滚动条）；被压缩时内容在盒内滚动，不再越出 `border` 与圆角，
  也不再出现「正文断在半行、剩下的字跑到卡片下面」。
- **验证**：真实 Chromium 探针复现了修前修后（`output/ui-zoom/execution-summary-probe.html`，
  同一 flex 上下文两列对照：修前子项底边 459 落在卡片底边 288 之外，修后 `scrollHeight` 264 >
  `clientHeight` 92 即内容被盒子收住）；`conversationDiffLayout.spec.ts` 9/10，唯一失败是既有的
  「文件夹细条名宽 35.28 < 40」，与本条无关。真实 Windows/WebView2 窗口未复验。

## 44. 聊天目标与计划模式

2026-10-20，产品设计已确认；后续已接入模式选择器、计划卡与目标卡源码，真实 Provider、Windows 窗口及独立验收仍未闭合，实际成绩只归统一功能验收表。行为定义唯一归[总纲 §0.15](../../requirements/product-spec/part-02.md#015-聊天目标与计划模式)，以下维护目标交互，不表示全部场景均已验证；不复用旧本设备「计划执行方式」偏好作为模式状态。

### 44.1 入口与计划卡

输入框旁只显示当前模式，不摆下拉选择（2026-10-22，DEV-0105）：普通模式不占位；计划/目标模式显示一枚静态徽标与「退出」键，退出即切回普通模式（活动目标先安全暂停）。徽标本体按 2026-10-25 用户指令收紧：文字只写档名「计划」「目标」（不缀「模式」二字，识别交给图标与字色），目标档图标为「箭插在靶心」的自绘靶子（lucide 无对应字形，24 viewBox、stroke 2 与 lucide 同格），计划档沿用 Compass；常态不铺胶囊底、与同排工具 chip 一样直接落在卡面上，悬停才起 `selection.hover` 底。进入模式用「+ → 命令」里的 `/plan`、`/goal`，或直接输入 `/plan 内容`、`/goal 内容` 一次提交；菜单点击仍只预填。新会话默认普通模式，恢复旧会话读取保存的模式与状态。模式是会话行为约束，不增加人设或执行权限。

`/plan` 讨论保持正常聊天，形成计划后显示会话内计划卡：目标、范围、步骤、验证方式、待定事项和版本；支持查看及用自然语言提出修改。默认存会话，需要时导出文件。「按此计划执行」绑定选定版本进入 `/goal`，沿用需求与讨论；过期或冲突版本须核对后再执行，不静默改用另一版。写入试验先解释范围并取得授权。

### 44.2 目标状态条与控制

目标状态以**输入卡上方的一行状态条**常驻显示（2026-10-25 用户指令，参照 Codex 的目标行；此前是转录区顶部的整张目标卡）。单行只放「目标图标、服务端状态芯片、目标正文（超长截断）、轮次/成功条件计数、动作」；点击单行展开详情区——目标正文全文、计划版本、当前步骤、简短进展、停止原因与待澄清问题、成功条件逐条状态与依据、步骤与轮次历史（各自折叠）。展开是本地视图偏好，不发命令；无目标时整条不渲染，不占位。状态条在输入卡**外**上方，与回执/档位说明同一列的裁定一致：条的出现与展开不改变输入卡自己的形状。运行时提供「暂停」「取消」，暂停后提供「继续」；完成时展示成果与验证依据，阻塞或额度耗尽时显示具体原因。重新打开会话仍显示原记录。

**取消目标要先确认（2026-10-23，禅道 #153）**：`取消目标…` 是终止性操作，按 §13.2「没有反向命令」那一列走 `AppDialog` 事前确认，不直接发命令。确认框标题「取消这个目标？」，正文说明两件事——不再继续推进，以及已经发生的修改与外部操作不会回滚、无法恢复——并把「暂停」作为可恢复替代指出来；初始焦点压在「再想想」，确认键用 danger。确认后才发原 `controlGoal(cancel)`：命令身份、重放与在途安全结束规则都不变，也不给撤销条。点击前不再依赖「先取消再解释」——后果说明在动作之前给出。

**单行版式（2026-10-25；DEV-0103 的三层分层随单行化收进展开区）**：状态芯片沿用「文字 + 色点」，颜色不是唯一线索；动作键收成紧凑形态——「暂停」「取消」为图标键（后果与含义在 `title`/确认框里说明），「继续」「确认完成」带文字，二者是这条事实的主行动，只靠图标不足以区分。窄窗（≤48rem）先收掉轮次计数，状态与目标正文仍在一行，动作键不折行。展开区内容超过 `42vh` 时在区内滚动，单行状态条与动作键不被证据挤走。字段、服务端 `actions`、轮次事实与业务状态均不因版式变化。

不提供应用额外的总时长、轮次、调用次数预算上限。额度耗尽后保留现场，恢复额度后点「继续」接续原目标；继续失败保留原状态并给出原因，不新建另一份目标，不循环自动尝试。额度信息未知时明确未知，不编造余额、重置时间或完成。

暂停、取消及转计划模式先显示处理中，在途行动安全处理后才显示已暂停/已取消或完成模式切换；取消不表达撤销已发生的副作用。询问进度不停止执行，补充要求融入后续；与原目标冲突时暂停受影响行动并展示待澄清事项。活动目标中「先讨论」安全暂停后进入 `/plan`，之后执行采用明确选定的计划版本。完成、等待人工验收、阻塞及额度耗尽分别呈现，不以步骤勾完表示目标完成。

**停止中的目标按目标状态投影，不按会话模式宣称去向（2026-10-24，DEV-0105 退回项修复）**：卡外模式说明行在目标 `PAUSING`/`CANCELLING` 时说明「正在安全停止」，并只报目标事实——暂停后可从目标状态条恢复、取消后终止不再推进；**不再写「停下后才会进入计划模式」这类按会话模式推算的句子**。服务端切走 GOAL 时会话模式立即落 CHAT/PLAN、目标才慢慢停下（`chat_mode` 与目标状态是两条投影），退出到普通模式时旧文案是错的；当前在哪一档由模式徽标承担，说明行不重复宣称。投影输入是服务端目标状态（`AssistView` 传 `goalStatus`），不是本地在途推断；目标停止结束（PAUSED/CANCELLED）后说明行随轮询消失。回归锁在 `tests/chatPlanGoal.spec.ts`（CHAT/GOAL/PLAN 三档停止文案、退出接线、重载恢复）。

### 44.3 实现状态与已知差异（2026-10-21 实施者自检）

已落地：模式状态徽标与「退出」（显示服务端持久模式，退出即切回普通模式；进入模式走命令菜单与 `/plan`、`/goal`）、命令菜单仅预填与「命令 + 正文一次提交」、计划卡（版本列表、SUPERSEDED 标记、按确切版本执行、复制 Markdown）、目标单行状态条（输入卡上方常驻，服务端 `actions` 决定可用控制、成功条件逐条状态与依据、停止原因与轮次事实收进展开区；2026-10-23 起「取消目标…」先走 `AppDialog` 确认，见上节；2026-10-25 从转录区顶部整卡收成单行，见 §44.2）、卡外模式说明行。推进、结算、额度授予与恢复链归[运行架构 §9](../../architecture/runtime-context/part-03.md#9-聊天目标与计划模式的运行边界)，接口归 [HTTP §10.108](../../api/http-command-contract/part-08.md#10108-聊天目标与计划模式2026-10-20-源码实现)。

**已知差异——计划导出文件未实现。** 现计划卡只提供「复制 Markdown」；「需要时导出文件」这一独立写操作需要新的 Gateway 写入来源（导出类），涉及 origin 登记、迁移 CHECK 与审计，本轮未做。落地前不得用会话直写或模型写工具代劳：导出必须是用户明确请求后的一次独立写操作，不能成为规划时自动写项目的理由。差异已在[功能验收表](../../testing/overall-acceptance-2026-09-28.md)记为剩余项。

### 45.1 软件功能的试用反馈与返工

2026-10-24，以下交互选择已确认，本增量待实现、未验收。背景是用户希望围绕实际使用效果直接反馈，减少逐项填表与人工转述；首个场景为 Relay 自身的软件功能／需求，产品归属见[总纲 §0.17.7](../../requirements/product-spec/part-02.md#0177-围绕成果工作的专用工作台)。

| 环节 | 已确认交互 |
|---|---|
| 查看功能 | 围绕同一功能持续呈现当前有效要求、成果及版本、可体验入口、验证缺口与反馈返工。沿现有对象与入口组织，不要求另建一级页面 |
| 自由试用 | 默认直接打开成果自由体验，保留少量必要检查提示及未确认项；可随时自然语言反馈，不强制逐步向导。打开页面、未反馈或勾选提示不自动算通过，用户说“这版可以”后仍核对必要条件与确切版本 |
| 认可与剩余检查 | 2026-10-24 已确认：用户说“这版可以”而必要检查尚未完成时，保留其对已体验部分的明确认可，绑定实际体验版本与可确定的范围；不把未体验部分推定为已接受。直接列出还差什么、为什么需要检查及继续检查入口，沿原 Owner 登记认可与剩余项，不另建完成状态。认可范围有实质歧义时就近澄清；必要条件满足后才能沿原流程正式完成。新版本不继承这次认可，记录失败或回执未明时不显示已登记 |
| 明确缺陷 | 在原授权范围内立即交给负责 Agent 修复，用户继续体验当前版本；修复使用独立工作副本，新版准备好后由用户选择切换，不在试用中静默更新当前版本。新增需求或有实质歧义的反馈先说明影响并取得必要决定 |
| 反馈与复验 | 反馈关联当前功能及体验版本，可从现场取得的已有信息不要求重复填写；同一问题的连续补充归入原反馈。新提交逐项说明修复、未解决内容及对应验证依据，保留原反馈；期间要求变化须重新核对，不能沿旧理解直接交付 |
| 切换新版与试用数据 | 2026-10-24 已确认：兼容且能安全沿用时，优先保留已填写或创建的试用数据，同时保留从干净环境验证的入口。存在数据结构变化或冲突时，切换前说明影响并先保存当前现场，由用户选择转换数据或从干净环境开始；不静默清空。未提交输入纳入现场保存范围；无法可靠保存时明确指出未保存内容并暂停切换。转换方案不可用时如实说明，不提供虚假的转换成功。保留数据不代表新版本已验收，反馈仍绑定实际体验版本 |
| 跨功能体验 | 默认按完整使用流程集中体验，例如“创建项目 → 添加任务 → 执行 → 查看成果”，同时保留单项入口；反馈归到相关功能，归属不明时留在流程下待调查，不要求用户先定位技术层。功能与整体流程的结果分开记录，未受影响且证据充分的功能可单独确认 |
| 主观反馈 | 对“页面太乱、用起来很烦”等反馈，先在可读范围内调查，给出具体问题及推荐改法；用户确认改法后执行，有实质歧义才追问。对“把三个按钮合并到菜单里”等明确修改指令，按已有授权推进，不普遍追加方案确认 |

取舍：自由体验减少操作负担，必要检查提示用于暴露漏验；边试边修减少交接等待，同时需要稳定的体验版本；主观反馈先给改法，多一次必要决定以减少无效返工。修复提交、检查通过、人工接受和正式完成仍分别成立，新版本不自动继承旧批准或证据，跨功能归并展示不合并独立的完成条件。

## 46. 项目事项与外部 Agent 共享任务

2026-10-23，**交互规则已确认、待实现，未验收**。产品规则归[总纲专题](../../requirements/product-spec/part-01.md#项目事项与外部-agent-共享任务协作)，工程范围归[路线 §15](../../requirements/post-v1-roadmap/part-02.md#15-项目事项与外部-agent-共享任务协作)。本节只维护交互，不新增视觉 token 或独立管理后台。

### 46.1 入口、登记与查看

项目内增加“事项”入口，需求与 Bug 可查看说明、来源、优先级、完成条件、当前版本及关联 Task；事项详情引用任务、执行、产物、验收、批准和集成记录，不复制业务状态。聊天支持“登记这个 Bug”“把这条交给开发 Agent”“查看等待我确认的事项”等明确操作，按原自然语言入口核对项目、对象、范围及权限；信息不足时就近补齐，普通讨论不自动登记或开放执行。

详情页用于编辑和复杂确认，聊天明确指令可表达同等决定，无需普遍再填表。登记、生成拆分建议、确认范围与实际执行分别呈现；进入可领取队列时显示等待外部 Agent 领取，不显示已经运行。外部工具实际连接并领取后才显示执行者及执行记录，用户能区分范围已授权与 Agent 尚未上线。

### 46.2 开发、验收与人工处理

- 任务显示角色要求、领取者、确切执行基准、关联 worktree 和当前结果版本；独立验收引用同一提交及条件，不能只显示一条“已测试”的聊天结论。
- 退回显示失败项、证据、待返工及剩余轮数；基础设施故障单独解释。达到上限、争议、权限不足或范围变化时给出实际原因及人工处理入口，不显示自动运行承诺。
- 失联显示待核对的原执行与改动，明确超时不代表停止；接手操作依服务端准入，不提供绕过资源核对的“强制继续”捷径。
- 修改需求或验收条件后，展示版本差异、受影响执行及沿用旧范围/切换新范围的决定；历史证据保留适用基准，不继承到新版本。
- 独立验收通过后，人能对照确切变更、条件及证据批准集成；批准后分别显示待集成、集成中、失败、回归及最终完成的真实投影。集成失败或回归失败保留下一动作，不因批准成功显示全部完成。

上述阶段是界面语义，具体枚举与按钮协议待工程核定。暂停/取消/重开沿原入口，重开不自动授权执行；Loading、空结果、读取不全、失权、冲突、未决请求及 UNKNOWN 分别显示，重读不得被旧响应覆盖。按钮消费服务端当前可执行动作，不能由页面推断授予权限。

### 46.3 试运行与证据边界

启用后新事项在 Relay 试运行，旧事项继续在禅道处理。引用旧事项时保留当前登记处和原链接，不把历史导入快照当作最新状态，也不自动迁移、双写或同步关闭。尚未启用时不向用户宣称可以在 Relay 登记执行本闭环。

验证场景归[测试计划 §43](../../testing/verification-plan/part-07.md#43-外部-agent-共享任务协作的目标验收)；页面原型、受控 API 和 jsdom 不能代替真实外部 Agent 接入或 Windows 窗口验收。

## 47. 长期 Agent 团队私聊群聊与工作概览

### 47.1 成员与定向交流

项目能按需添加长期成员，提供产品、设计、开发、测试等模板；协调者建议增员时展示职责和原因，由用户决定，不自动创建全套角色。成员详情显示稳定身份、职责、运行方式、模型和当前工作；模型默认继承项目、可单独配置，不能把模型名称或会话标题当成员身份。成员归档、更换协调者及运行端变更的具体交互待协议核定。

### 47.2 项目群聊与工作概览

群聊支持指定成员接收，未指定由协调者接住并按需邀请。成员间可发起有对象、有目标的讨论；展示被邀请者、问题、关联任务/版本及当前结论，避免同一消息触发全员重复响应。讨论未解决、需要决定或已结束可辨认，摘要可追溯原交流；群聊中的“已完成”不能直接关闭 Task。

工作概览聚合当前授权工作、成员职责与实际执行、任务依赖、成果和待决定事项；私聊、群聊、事项详情及概览使用同一事实源。主要动作回到原授权、Task、Review 或集成入口，技术详情按需展开，不要求用户在群聊里人工抄送进度。

真实阻塞、重要风险、需要决定及成果待批准主动通知；普通交流与工具过程集中汇总并可查阅。相同问题合并提醒，保留各来源，不将通知已读、延后或关闭当成业务决定或任务完成。

### 47.3 运行、消耗与异常

区分等待事件/下次巡检、可领取、外部成员等待连接、实际执行、暂停处理中、已暂停、范围待核对和失联等事实。成员长期保留不意味着持续调用模型或永久在线；关闭窗口继续本机推进，明确退出/关机后停止，重启展示实际核对与恢复情况，不许以 Loading 隐藏未知外部效果。

不提供强制项目/成员累计费用、时长、轮数或调用次数配额；可展示真实消耗及不可观测部分，不能误导为免费或无限账户额度。服务商额度耗尽、模型不可用、权限变化及用户暂停有明确原因和接续路径；备用模型仅按用户配置使用，不静默切换。原默认三轮返工后人工处理等规则仍可见，不能因“额度不限”让返工无期限继续。

成员、群聊或运行端切换不得丢失草稿、未决请求、当前任务和原控制意图；失权清除不可读投影，过期/迟到结果核对身份和版本。具体按钮、生命周期枚举、归档及恢复协议待工程核定；本轮不声称已覆盖这些界面。

验证归[测试计划 §44](../../testing/verification-plan/part-07.md#44-长期-agent-团队与跨会话协作的目标验收)，真实内置/外部运行、浏览器和 Windows 分别取证。

## 49. 原型借鉴三项：用户消息复制、稍后处理、长任务列表分组与限高（2026-10-24，已实施，实机未验）

背景：用户提供页面原型 `GPT页面原型/Relay_V5.27_基于V5.26原版_跨页面交互一致性综合验证_完整原型.html`（V4.2–V5.27 交互层叠）。逐层对照后确认多数能力已存在且实现更深（目标卡、时间线导航、自适应输入器、今日稍后、会话行菜单、命令面板、会话 diff 归因等）；本轮落地三项核对过代码确认缺失的小成本项。原型中更大的候选（hunk 级撤销与变更时间线、目标与变更记录导出、可见入口功能审计视图）记入[路线图候选](../../requirements/post-v1-roadmap/part-01.md#4-后续候选的处置)，不在本轮实施。

### 49.1 用户消息复制（悬停出现）

助手回复的复制键已存在（§「复制键在左、用量在右」，2026-10-16）；本轮补齐用户消息一侧。用户消息没有用量行可与复制键常驻同排，复制键平时收起（opacity 0），悬停或聚焦（`:focus-within`）才出现；占位恒在，出现时不推走正文。空正文（纯图片消息等）不摆复制键。复制是纯客户端剪贴板动作：不新增命令、不落库；写剪贴板失败只还原按钮可读名，不发成功回执。「编辑重发」需要消息语义与模型重放支持，本轮不做。

### 49.2 人工待处理的「稍后处理」分组

四个分组（必须介入、待判断 Review、当前 Run 待核对、人工任务与受阻 Task）的每条卡片在「下一步」行尾增加「稍后处理」文字键；被稍后的条目移出原分组、进入页底的「稍后处理」分组，可随时「移回原分组」。规则：

- 稍后是**本机查看安排，不是业务状态**：不发命令、不改服务端事实；存储在 `localStorage`（键 `relay.attention.postponed.v1`），读写失败只影响跨刷新保留。这与控制意图必须持久化的规则不冲突——稍后不控制任何执行。
- 稍后键与各分组行键同源（必须介入带 changeKey，其余用对象 ID 并加分组前缀）；完整读取（failures 为空且任务页读完）后按当前快照清理失效键——条目已处理、消失或身份变化（如必须介入换 changeKey）即回到可见分组，不凭半份快照误删。
- 分组标题计数按可见条目走；「与下方分组是同一条」的交叉提示只对照可见条目，被隐藏的条目不再自称列在下方。
- 全部可见分组为空但仍有稍后项时，空态写明「你有 N 项在稍后处理里」，不把「都稍后了」说成「没有待处理项」。

### 49.3 长任务列表的分组行与限高滚动

原型 V5.26 的两条收尾模式，落在执行摘要的两份列表上，阈值内行为不变：

### 50.1 首版范围与布局

复用现有 DevToolsPanel、工作详情、产物版本预览和布局偏好；工具内容占用同一右栏，不另加第四列。推荐“工具”入口打开右栏，顶层按文件/产物、变更、网页组织内容；运行记录、轨迹和执行输出保留既有入口与语义，不要求全部平铺常驻。工作详情与工具通过明确入口切换，Review、停止与结果待核对提示保持可达。无项目或无 Task 的普通会话也能手动打开网页，文件/变更仍按现有资源资格显示；不为看页面而创建 Task。

推荐交互示意：全局导航与会话列表 | 当前对话/任务 | 右侧工具（文件/产物、变更、网页）。右栏可收起、拖宽；窄窗复用现有布局断点和抽屉/单区规则，保留返回对话入口，不叠出多个遮挡层。视觉复用设计系统与 tokens；本轮不新增猜测宽度和颜色。

首版网页支持多个标签：新建、切换、关闭，地址输入、前进/后退、刷新/停止加载、当前标题与实际 URL、在外部浏览器打开。起始页仅提供输入网址、当前作用域已打开页面和已有可用结果入口；不做常用网站推荐、搜索引擎、跨项目全局历史或书签系统。地址栏首版接受完整 http/https URL，不把任意文本自动发往搜索引擎。

已有产物和变更以原组件及确切版本打开；不借此次扩展补做通用文件管理器、任意目录读取、Git 写入或交互终端。现有“终端未接入”仍如实显示。普通文件与 Artifact 不混成同一版本。静态 HTML 产物若需可执行预览，须先通过隔离验证；不将任意本地文件直接导航为网页。

### 50.2 打开、加载与人工使用

用户手动输入 URL 或点击“在工具面板打开”才导航；Agent 给出的 URL 只是候选链接，不自动执行。页面首次加载不启动开发服务或 Shell；本地服务不可达时保留 URL、说明失败并允许刷新/外部打开。内置网页有独立浏览环境，不承诺复用 Chrome 登录态；登录由用户在页面完成，凭据不进入对话或业务日志。

覆盖空白、加载中、成功、失败、停止加载和页面进程异常；旧导航的迟到事件不得覆盖新页面。实际重定向后的地址可见。停止加载不表示撤销网页请求，关闭标签也不能证明外部操作未发生。页面表单可供用户操作，但其提交属于真实网站行为，不能把“人工预览”宣传为无副作用环境。首版 Agent 不读取 DOM、不截图、不点击、不自动填写或提交内置页面；浏览器原生权限、下载和新窗口策略归架构验证门槛。

### 50.3 作用域与恢复

面板布局是本机偏好；页面关联按 workspace + conversation 保存，当前 Project/Task 只是来源关联，不授予权限。任务/会话切换不把旧页改绑到新任务；显示当前作用域，旧页面隐藏后禁止后台打开新窗口或弹出权限请求。首版推荐离开会话释放其网页实例，保留可恢复的描述；返回时由用户重新打开，不能承诺恢复表单与网页内部状态。

只持久化允许保留的页面描述、顺序和选中项；URL 可能带凭据或私密参数，跨重启保存采用保守规则：不保存用户名密码、query、fragment、浏览器存储或页面正文，无法安全恢复时仅保留标签提示并让用户重新输入。登录回调/一次性链接不留恢复地址；不得将 URL 自动上传 Context。重启后展示待恢复页，用户点击才加载，避免自动重放有副作用的 URL；明确展示待打开地址。关闭面板只隐藏当前实例，不暂停或取消 Run；退出应用销毁实例，不承诺网络动作已撤销。

### 50.4 人工验收与后续阶段

查看页面不改变 Verification、Review 或 Task 状态；人工仍走既有业务入口，绑定确切产物版本、验收条件与证据。动态网页只代表观察时状态，不能直接当作不可变 Artifact；需要证据时复用既有产物/附件入口，截图、DOM 或标注的自动采集后置。

后续候选为选区引用、页面标注、截图取证以及 Agent 与人共同操作。它们分别涉及外部内容信任、证据版本、执行权、权限与 UNKNOWN 恢复，首版不预建工具词表、数据库表或空 Provider。首版通过真实 Windows/打包验收后再决定是否启动，不以右栏出现代替能力验收。

### 50.6 文件页签：人工目录浏览与文件读取（2026-10-24 后端补齐，同日前端接线，实机未验）

「文件」页签的目录浏览与工作目录文件读取**已实施**：`POST /projects/{p}/managed-resources/{r}/file-read`（`LIST_DIRECTORY` / `READ_FILE`，迁移 0134，USER_ACTION 来源）复用模型侧适配器与 FILE_QUERY/FILE_READ 连接＋策略准入；动作身份纳入 `command_id`，每次点击是新的读取事实（与 Git 人工读取的冻结语义分界）。机制归[工具适配器 2026-10-24 段](../../architecture/tool-adapters.md)，契约归[命令契约 §10.112](../../api/http-command-contract/part-08.md#10112-人工受管目录浏览与文件读取2026-10-24-源码实现迁移-0134)。

前端落点与交互（`FileBrowsePanel`，挂在「文件」页签受管目录列表之下）：

- **浏览与读文件都是显式命令**：连接按能力分选（浏览用 FILE_QUERY、读正文用 FILE_READ，各自独立配置与回退提示——只配浏览时点文件给出「无 FILE_READ 连接」的明确反馈，不静默）；每次点击生成新 `command_id`（刷新语义），同一命令的重放、回执核对、`RESPONSE_UNKNOWN`/`WAITING_APPROVAL` 四阶段恢复沿用 GitReadPanel 的同一套 sessionStorage 身份保留；ASK 等待时不携带任何结果字段，提供 Review 链接与「批准后沿原命令继续读取」。

## 51. 正式目标管理与项目状态写入（2026-10-24，已实施，实机未验）

正式 Goal（Workspace 级业务目标）与聊天 `/goal` 自主执行目标是两套对象：本节的 `/goals` 页面只读 `goals`、`project_goals` 与 `task_explicit_goals`，不创建 Project/Task/Run，也不与聊天目标合并。入口在项目页头部「目标列表」，不新增一级导航；旧 `/projects?view=goal` 创建入口与深链接保留。

### 51.1 Goal 列表与详情

- `/goals`：Active/Archived/All 三范围、服务端游标逐页读取、按 ID 去重、末页才说「已到列表末页」；续页暂态失败保留已读与游标、可按原游标重试；401/403/404 撤下已读目标并给全页错误态。空态区分「当前范围没有已归档目标」与「还没有正式目标」。
- `/goals/:id`：Goal 标题/说明/状态/revision；关联 Project（含已归档项目与真实归档状态）；编辑、归档、解除关联；只读工作上下文；关联项目进展汇总。
- 编辑只提交 title/description；清空说明提交空字符串。归档需二次确认，保留 Goal ID、项目关联、Task 显式对齐与会话历史；归档后隐藏编辑与新增关联，但既有关系仍可解除。
- Goal 详情中关联 Project 的展示链接到项目总览；当前导入的进展为各项目 `GET /projects/:id`、`GET /projects/:id/state` 与任务首分页；读取失败的项目单列「进展读取失败」，不并入其他项目结论。覆盖说明固定为「全部已读取 / 部分已读取 / 全部读取失败（x/y 个关联项目）」。

### 51.2 解除关联的影响清单

解除前先读 `GET /projects/:id/goals` 的 `explicit_task_ids` 并在确认区逐项列出。提交 `UnlinkProjectGoal` 时携带 `expected_impacted_task_ids` 与 Project 当前 revision；服务端锁下清单变化返回 409 `GOAL_LINK_IN_USE` 与当前 `impacted_task_ids`，界面刷新清单并要求再次确认，不静默清理其他 Task、不自动重发。命令冻结 `command_id`/载荷，结果不明先按原 ID 查回执。

### 51.3 项目改名与 Project State 写入口

- 项目总览「已确认事实」内提供「修改项目标题」；只走 `EditProjectPresentation`，只改 title，不触碰 Project Type、State、Task、Goal 关系、目录或执行记录。归档项目不提供改名。
- 项目总览新增「项目状态」区：阶段（严格按 GENERAL/THESIS/DEVELOPMENT 各自词汇）、下一步 Task（只列本项目已加载任务与 State 当前引用；设为下一步不代表 Task 获得执行资格）、已确认风险、阻塞（PROJECT/TASK/GOAL 三类目标）与解除。所有写入走 `POST /projects/:id/state-commands` 的单一类型化 action；不接受整份 State JSON，按 State revision CAS，冲突时重读并要求重新确认。
- 风险需填写说明、来源引用与确认引用；阻塞需目标、原因与来源引用，不伪造确认依据。风险/阻塞历史与解除状态按服务端投影呈现。

### 51.4 工作上下文与进展

- Goal 详情「工作上下文」以 `status=ALL` 汇集关联项目的受管目录与普通会话；目录入口 `/working-directories/:id` 只显示 `working_resource_id` 精确等于该目录的会话。会话链接沿用 `/agent?session=…&project=…`，不创建、不重绑会话，不授予文件或执行权限。
- 项目总览新增「最近活动」（最近 5 条项目活动，单独读取，失败只影响本区；有更早记录时不让 5 条冒充完整历史）与 State 风险/阻塞展示；阻塞提示同时包含任务事实与 State 登记阻塞，保持来源可辨。
- 所有统计注明覆盖范围：项目列表计数只算已加载页；任务分页、进展项目数、活动条数都不冒充全量。

### 51.5 异常、命令与恢复

- 创建/关联/改名/编辑/归档/解除/State 命令都把成功响应或回执与原 `command_id`、目标 ID、action、预期 revision 逐项核对；错配不宣布成功、不清 pending、不自动换 ID 重发。服务端已回 2xx 但响应契约解析失败同样属于结果未确认：保留原冻结命令并先查回执，不能当成明确业务拒绝清除。
- 暂态读取失败（传输/5xx）保留已读事实与游标；401/403/404 撤下受保护数据并阻止旧数据提交。待核对命令按 API/Workspace/目标作用域暂存，整页重开可恢复。
- 归档项目/Goal 的写入口在界面上不可用，服务端仍作最终拒绝；界面不把「已归档」读成「已完成」。
