## 决定：是否需要性能修复

**不需要立即修复（本轮不实施任何重构）。** 理由：

1. 主包 ~1.1MB（gzip ~302 kB）未造成可测加载延迟：本机生产环境下导航→可交互 P50 230ms / P90 303ms，全部阈值余量 ≥6 倍。1.19MB 解码后 JS 的解析/编译成本已包含在该口径内。
2. 路由静态导入未造成可测切换延迟：六条主路由切换 P50 62–73ms、P90 ≤84ms，全部低于 100ms 优线；静态导入避免了切换时的 chunk 网络请求，是当前形态下的合理取舍。
3. 命令/控制链路（Delegate、CANCEL、面板打开）P50 均 ≤18ms，无交互阻塞信号。
4. 唯一超 1s 的是 API 冷启动（~1.9s），属于进程启动场景（进程 spawn + DB 连接 + schema 核对），不阻塞任何已运行会话的交互。

**保留的风险信号（记录，不阻塞）：**

- 单 chunk 意味着首屏必须下载全部代码。当前桌面单机形态（ADR-007，本机 API/PG、vite/preview 或 Tauri 内置资源）下无弱网场景，gzip 后 302 kB 在本机几乎无感；但若未来出现远程访问形态，312 kB 传输将主导首屏时延。
- 输入→搜索结果时延的主导项是 250ms 防抖，属产品可调参数，非性能缺陷。

**可选的最小改进建议（未实施，仅为后续留档）：**

1. 若页面/依赖继续增长，可做路由级 `React.lazy` 动态导入（`router.tsx` 17 条路由按视图拆 chunk），预期首屏传输/解析量下降至核心壳 + 当前路由；收益需按本协议重测确认。
2. 若需要更快的面板搜索反馈，可将防抖从 250ms 降至 120–150ms，预期输入→结果 P50 降至 ~180–210ms。
3. 建议将本文件口径（冷缓存首屏、点击→h1 可见、命令→收敛）纳入后续 UI 回归的固定采样基线。
