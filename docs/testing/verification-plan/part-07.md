## 37. 周期定时启动任务验收规格（2026-10-18）

产品规则归[后续路线 N08](../../requirements/post-v1-roadmap/part-01.md#n08-周期定时启动任务)，取舍归 [ADR-026](../../decisions/ADR-026-scheduled-task-autostart.md)，协议归 [HTTP §10.94](../../api/http-command-contract/part-07.md#1094-周期定时启动任务2026-10-18-源码实现迁移-0115)，物理设计归[数据库 §103](../../database/physical-design-postgresql/part-05.md#103-0115-周期定时启动任务2026-10-18-源码实现)。

**必须成立的七条。** 少任何一条都不算通过，也不因为其它条绿而放行。

1. **触发真的启动，且只启动一次。** 到点后新建一个 Task（标题/目标/验收来自模板）、Task 进入 `READY`、产生一个 Run；同一时段被重复扫描不会建出第二个 Task；同一 `command_id` 重放返回原结果。
2. **授权在先、准入在后。** 触发不扩大权限；`EXPIRED` 与预算耗尽都把计划置 `EXPIRED` 并留一条说明原因的 `BLOCKED`，不静默停。
3. **以 Task 终态判准入。** 上一轮 Task 不在 `DONE`/`CANCELLED` 时本轮 `SKIPPED`，不建新 Task，且不消耗 `max_runs`。
4. **错过不自动执行。** 应用关闭期间错过的时段记 `BLOCKED('MISSED')` 且 `task_id IS NULL`；只有人工「补跑」才启动。补跑与恢复分发（CreateTask 未提交时）都先做快照准入：必然不可执行（暂停/停用/到期/预算耗尽/归档/旧代次/上一轮未验收）的触发被拒绝或不建 Task（2026-10-25）。
5. **暂停/停用停止新触发。** 状态改变后即使时刻已到也不再扫描；已启动的 Run 不受影响。
6. **墙钟语义。** 跨夏令时仍按本地时刻触发；春跳不存在的时刻顺延一小时，秋回重复的时刻取较早一次；关机多天后只推进一次且结果严格晚于当前时刻。
7. **待处理可达。** `BLOCKED` 触发进入既有 `attention` 投影（`kind='SCHEDULED_TASK_BLOCKED'`），入口指向详情页，不与 N05 提醒混用去重键。

**证据分层（一种不能代替另一种）。**

- **纯单元**：`zoned-time.test.ts` 覆盖上海、纽约春跳/秋回、伦敦、Kolkata(+5:30)、Chatham(+12:45)、Kiritimati(+14)、跨 DST 的每日 09:00、关机三天只推进一次、首次触发严格晚于当前；`scheduled-tasks.test.ts` 覆盖规则/上限/到期/时刻/日期/时区/文本口径。这一层只证明计算与校验，不证明触发。
- **真实 PostgreSQL + 真实 API 进程**：`scheduled-tasks.integration.test.ts` 用 `now() ± interval` 直接改 `next_due_at` 制造到期（只改排期列，不改任何业务状态列），断言 Task/Run 真的落库、`runs_started` 计数、跳过与错过不建 Task、`EXPIRED` 与暂停不再扫描、补跑只建一个 Task、`attention` 投影可达。`scheduled-task-p0a.integration.test.ts`（2026-10-25）补齐故障现场：发生时模板冻结（含未提交 CreateTask 分支）、五类补跑前准入拒绝且零 Task、恢复分发前准入、完成幂等与迟到写入守卫。
- **前端**：`scheduledTasks.spec.tsx` 覆盖列表/详情解析（含未知状态与未知重复类型显式失败）、创建请求的 snake_case 载荷、回执身份核对、重复规则与时刻按时区呈现；`navigation.spec.ts` 复跑确认新增第 5 项不破坏既有选中语义。
- **未验**：真实 Windows/WebView2 窗口、多 DPI、安装态、多实例并发扫描（本片假设单 API 进程，与 N06 一致）、真实模型执行（集成测试只证明 Run 被创建，不证明它跑完）。

**故障与竞争的组合不因单条绿而推断通过。** 崩溃点覆盖现状（2026-10-25）：「CreateTask 已提交后中断」由 `scheduled-tasks.integration.test.ts` 的持久前缀用例（预生成命令身份 + 回执重放 + 唯一约束）覆盖；「CreateTask 未提交时编辑模板」「完成事实在、occurrence 标记丢」「迟到失败写入」由 `scheduled-task-p0a.integration.test.ts` 以 SQL 还原现场覆盖。多实例并发分发仍按 ADR-026 单进程假设，条件更新只是兜底，不据此宣称多实例已验。

## 会话执行的服务端推进与失败恢复（2026-10-20 第二轮）

规格依据：[运行架构 §2.10.1](../../architecture/runtime-context/part-02.md#2101-推进-owner-收归服务端与能力事实说明2026-10-20-第二轮)、[工作台 §43.1](../../frontend/workbench-design/part-14.md#431-就绪候选由服务端推进界面只呈现阶段2026-10-20-第二轮已实施实机未验)、[HTTP §10.107.1](../../api/http-command-contract/part-07.md#101071-服务端自动推进与失败原因投影2026-10-20-第二轮源码实现)。结果只归统一验收表。

后端（真实 PG，`conversation-execution-autostart.integration.test.ts`）：

- 只有 Worker tick、没有任何前端请求时，READY 候选推进到 `DELEGATED`，恰好一个 Task 与一个 Run。
- 重复扫描与人工重复提交同一 `request_id` 只重放原回执，Task/Run 计数不变。
- 推进失败：`status=FAILED`、`clarification.questions[0]` 是**可执行的**具体原因（含能力名，不含「验收标准/任务目标」），候选与阶段命令身份保留，零 Task/Run。
- 已知失败不自动重试（第二轮 tick 为空）；补齐前置条件后沿同一 `request_id` 接续成功，且仍只有一套 Task/Run。

前端（jsdom）：

- `executionSummary`：READY/TASK_PREPARED/DELEGATED 无任何开始按钮；FAILED 呈现服务端原因并提供「继续原请求」；界面文本不出现 `task_id`/`run_id`。
- `folderFirstConversation`：候选就绪时本页**不发** `applications`；失败后点「继续原请求」才发一次，成功后进入执行详情。
- `settingsView`：执行策略面板不再有「计划执行方式」控件；遗留本地键不被读取。

提示词：

- `assist-capability-notice` 单测锁「原因指向真因」：无目录、只读档位、缺连接三类分别措辞；只读档位下的写缺口不进「缺连接」清单；事实块固定声明不是指令、也不构成授权。

不覆盖：真实 Provider 的选择质量与措辞、真实浏览器/电脑操作、Windows/WebView2 窗口、安装态。无目录操作会话与「普通检查不进入正式验收」本轮未实现，不在本规格范围内。

### 已实现的自动化覆盖（2026-10-21，实施者自检）

`apps/api/test/integration/chat-plan-goal.integration.test.ts`（真实临时 PG 18.6 + 真实 HTTP API 进程）覆盖：

- **命令与模式**：`/plan 内容`、`/goal 内容` 发送后在同命令内切换并受理（应用层剥离前缀并与 `chat_mode` 核对一致性）；计划模式拒绝提案意图与 MODIFY 方法；新会话缺省 CHAT、消息带 `chat_mode` 受理；`chat_mode` 经会话 DTO 与 202 回执投影（HTTP 面断言，防 DTO 漏字段）。
- **只读规划**：PLAN 轮次**不声明写工具**，模型请求写操作被 Gateway 准入拒掉且工具账本留下类型化拒绝，本轮照常产出计划；计划信封结算后正文只落 `reply`，版本行按「会话 × 版本号」与「会话 × 源消息」两个唯一键落库。
- **计划转执行**：一份计划两次修改产生 v1/v2 且旧版标 SUPERSEDED；`startGoalFromPlan` 绑定确切 plan_id，已被取代版本默认拒绝、`allow_superseded` 显式放行；目标按该版本冻结条件。
- **持续目标**：目标模式消息建立目标并绑定轮次；Worker tick 结算上一轮结论并按同一目标接续下一轮（多轮推进，不以单轮限额结束）；成功条件缺证据保持 CONTINUE，报告 COMPLETE 只进 `AWAITING_ACCEPTANCE`，人工 `complete` 才 COMPLETED。
- **后台与恢复**：推进只发生在 Worker tick（`runAssistGoalTick`），页面请求不参与；轮次结算按消息唯一键幂等；重复 tick/重复 continue 不产生第二条链；`PAUSING`/`CANCELLING` 先在途安全停下才归一（在途轮次先结算，控制意图优先）。
- **额度耗尽**：预算闸门对 `BUDGET_EXHAUSTED` 目标按 `assist_goal_budget_grants` 授予量放大上限；`resume` 用尽后仍耗尽时保留现场，grant 按可核对事实（失败轮次冻结的模型快照 → 进程配置 → 最小窗口）计算并落账本。
- **领取顺序回归**：`claimNextPendingMessage` 按 `session_id, created_at, id` 排序且一次一条，「发一条再跑一次 tick」不保证轮到它——测试统一显式轮到目标消息，防止再把调度事实当成落库缺陷。

`apps/workbench/tests/chatPlanGoal.spec.ts`（jsdom）**11/11** 覆盖：模式命令解析（`/plan 内容`、`/goal 内容`、别名、正文中的 `/plan` 不误判）、`ChatModeSwitch` 受控值与禁用态、`ChatModeHint` 仅在非普通模式出现且安全停止时说明停止、`PlanCard` 版本标记与执行按钮、`GoalCard` 按服务端 `actions` 渲染控制与 `stop_reason`/`round_count` 事实字段。

未验边界：浏览器实际操作、真实 Provider 意图理解与额度识别、Windows/WebView2 实窗与安装态、独立验收。Fake/受控模型只证明协议、边界与恢复接线。

### 连续插话的定向回归规格（2026-10-20）

规则归[运行架构 §2.9](../../architecture/runtime-context/part-02.md#29-排队消息的插话进入上下文的方式2026-10-19已实施)。自动化覆盖：多条插话按 seq 保留原文且只结算同一轮；请求期间新输入阻止旧工具入账/Gateway；批次中途到达保留首个真实文件读取结果、剩余工具回报未执行且不落 Operation；收尾轮不消费迟到插话；旧插话在其引发的工具之前、新插话在结果之后，tool-call/result 配对完整；**消费插话后模型失败与消费后取消各自收口且不复活占位行，恢复轮上下文仍能读到原要求与插话原文；Worker 崩溃经 `failExpiredLeases` 收口 `LEASE_LOST`，迟到结算被 CAS 拒绝，恢复轮同样读到原文；预算耗尽以 `MODEL_BUDGET_EXHAUSTED` 类型化失败且原文保留**。回归普通主链、会话直写、只读人设与提示词装配。

真实 Provider 检查（`steer-provider.integration.test.ts`，默认跳过）：显式 `RELAY_STEER_PROVIDER_CHECK=1` 且 Provider 配置可用时运行六场景（相关补充、局部修正、改变阶段、明确替换目标、临时提问、关系不清）。硬断言与模型无关：插话原文进入后续请求、被停止工具零账本/Gateway/磁盘改动（场景 C 在 FULL 档位验「先别改，只给方案」后磁盘逐字节不变）、排队行收口；回答措辞与语义选择只记录供人工复核，不作硬断言。Fake/受控端口只证明输入、顺序、规则接线与执行边界；不能凭 Fake 的预设回答宣称意图识别质量通过。未覆盖的重启恢复窗口单独报告。

首个真实小功能仅为推荐验收场景，具体项目/条件/基准及环境实施前选定。协调成本、重复交流、交接遗漏、跨会话恢复耗时、无效唤醒与总消耗共同观察，样本和收益阈值在正式对比前冻结。

## 47. 成果版本管理 P0–P2 验收规格（2026-10-25）

本节补充 Artifact/ArtifactVersion 的 Workspace 归属、人工接受、未知命令恢复与跨成果影响核对。实现状态和本轮实跑结果只记在[统一功能验收表](../overall-acceptance-2026-09-28.md#当前功能验收表)；本规格不把组件测试、临时 PG 或源码检查提升为桌面交付。

| 场景 | 必须核对的行为 | 证据层次 |
|---|---|---|
| Artifact 关联 Inbox Task 与项目 Task | 只接受同 Workspace 的 Task；跨 Workspace 关系被 DB 约束拒绝；既有冲突数据使迁移失败并要求显式修复，不自动改归属 | 真实 PG/HTTP；迁移冲突预检需单独证明 |
| 一次完成接受多个成果版本 | 可跨多个 Artifact 选择确切版本；CompletionRecord、accepted version refs 与 ACCEPTED_BY lineage 保存同一集合；重开后旧集合仍作为历史，当前指针转为非当前 | 真实 PG/HTTP＋工作台状态与呈现 |
| 完成/重开/成果保存响应丢失、超时或 5xx | 原 ID 与完整原载荷可恢复，表单编辑、Task/Workspace 切换、组件重挂载不重建命令；查询回执先于重试；回包身份、对象和内容摘要不匹配时不宣告成功；不能持久化新命令时不发送 | 组件/浏览器故障注入＋真实 API 回执；真实 WebView2 进程重启单独验 |
| 影响检查与正文摘要 | 仅声明当前可检查范围；明确引用/推测/未分析、截断和 stale 分开呈现；999/1000/1001 字阈值准确，恰好 1000 不截断 | 单元＋真实 PG/HTTP |
| 多成果候选组、显式依赖与分项应用 | 只登记已知目标；重查时清除旧范围/依赖；过期 preflight 不留下未发送命令的 pending；应用后从可选项及下一次选择中移除；刷新不清 UNKNOWN pending；明确 4xx 拒绝可修正后重试；应用前复核来源、目标修订、前置与 stale 状态 | Workbench 组件/浏览器故障注入＋真实 PG/HTTP |
| 组合检查与验证缺口 | 只绑定来源 after 与确切已应用版本；跨 Task/超范围被拒；整体结论恒为 `NONE`，逐项显示当前性、可读性和缺少的单项验证；后续变化只标记快照 stale | 组件＋真实 PG/HTTP |
| 任意版本正文比较 | 完全相同、CRLF/LF、仅末尾换行、内部换行与尾换行同时改变均要明确分类；不能把不可见的字节差异归为「仅末尾」 | Workbench 组件回归；必要时以真实磁盘字节复核 |

当前实跑的组件与 PG 套件仅覆盖表中明确记录的场景；真实 WebView2 重启、安装包、IME/DPI 与独立验收须分别记录，不由本节规范或分片通过推定。

## 48. N04 到 N06 联合验收与 P2 稳定性门槛（2026-10-26）

本节规定周期计划到有限连续委托的完整业务路径。阶段通过仍按统一功能验收表逐层记录；受控 Provider 不证明真实模型质量，Chromium 不代替 Windows/WebView2。

| 编号 | 场景与必须满足的结果 | 必要证据 |
|---|---|---|
| N04-N06-01 | 同一 Project 创建有依赖关系的 Tasks，登记用户估时并生成 N04 周期计划；候选只写计划，不启动 Run | Workbench 定向组件测试＋真实 PG/HTTP |

| N04-N06-03 | 由已确认计划项建立 N06 Task Chain；未明确授权时无 Run。授权后先执行首项，等待人工 Review 与 Completion，前项完成后才能创建下一项 Run | 真实 PG/HTTP＋生产 Worker/Workflow；核对 Run、Review、Completion 与链项目录账本 |

| N04-N06-05 | 真实 Chromium 核对计划/范围/授权交互、窄窗和恢复行为；真实 Windows/WebView2 核对原生窗口与实际项目操作 | 浏览器和 Windows 两类证据分别记录 |
| N04-N06-06 | P2 才扩大为 100–200 Tasks、多份计划/范围推演/任务链、长链及历史 Review/Completion，并反复切换项目、返回与刷新；检查顺序、游标、历史归属和恢复后状态 | P0/P1 必需场景闭合后运行；真实数据/持久层结合浏览器与 Windows 操作，不以合成样本代替实际闭环 |
